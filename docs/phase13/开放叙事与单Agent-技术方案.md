## 1. 设计结论与证据边界

采用一个核心创作 Agent，集中组织当前相关人物、场景变化、行动结果和玩家正文。人物身份、动机、关系、个人感知与记忆分别保存；模型调用次数与人物数量脱钩。程序继续准备上下文、执行声明规则、校验候选、生成正式标识与提交结果。

核心创作以一个场景请求生成一份完整候选为常规路径。材料不足、固定判定准备和格式纠正可能需要额外调用；摘要与行动建议仍是已有派生任务。因此，“单 Agent”描述创作职责集中，不承诺整个应用永远只有一次模型请求。

| 设计选择 | 预期收益 | 必须验证的代价 |
| --- | --- | --- |
| 集中安排对话、行动与正文 | 对话相互承接，场景结果和表现一起设计 | 人物是否同质化、是否为剧情方便改变立场 |
| 按完整玩家意图处理一轮 | 普通步骤自然完成，停在真正的新选择前 | 是否擅自承诺、消费或替玩家采取重要行动 |
| 共享相关人物资料 | 模型能安排多方互动和隐藏动机 | 同一模型看见秘密后，人物行为隔离主要依靠生成质量 |
| 事件与正文共同输出 | 减少阶段交接，后续有可追溯依据 | 正文与结构化结果可能不一致 |
| 保留现有世界与提交机制 | 日期、钱物、位置、存档继续可靠 | 校验过重可能降低创作质量或提高失败率 |

上述收益是待验证假设。既有确定性测试能证明事件和事务机制，不能证明集中创作一定有更好的文笔。用户提供的裁缝店文本说明行动处理与节奏存在改进空间；仅凭该样本不能将问题归因于多个 NPC Agent。

## 3. 请求生命周期

架构上的目标流程见[架构方案 6.10](../summary/ARCHITECTURE.md#610-phase13-集中创作职责候选与目标)。本阶段一次请求的处理分为以下操作：

1. 接受玩家原文及界面明确给出的对象、表达范围，取得已有世界变更预约。
2. 读取冻结定义、当前存档、必要个人记录和版本依据；保持玩家原文完整。
3. 准备相关场景、人物、世界安排与可用机制。需要固定判定时先解析规则；首个行动可以在当前快照准备，依赖前段结果的判定使用已验证工作态的检查点。
4. 构建场景上下文并检查容量，调用核心创作 Agent。
5. 如返回合法的补充材料请求，读取获准文件；如返回后段判定检查点，先验证前段再准备规则结果。两种响应都没有可提交结果，继续由同一场景创作职责完成候选。
6. 校验完整 SceneDraft，在隔离工作态中顺序应用节点；需要时使用一次纠正机会。
7. 形成正式事件、个人感知、计划与能力变化，组装现有 Output。
8. 应用层通过既有短事务确认运行及版本，原子保存正文与全部变化。
9. 提交成功后，通过既有版本依据发布资料与建议；生成中正文保持候选状态。

前三步的普通资料选择由程序完成，不固定增加“导演”“规划器”或“审稿人”调用。第六步的工作态只存在于本次生成，不提前写入存档。

### 3.1 意图解析的去向

普通交谈、观察和没有固定规则的行动，语义理解进入场景创作请求。返回的 `input_map` 关联原文片段与处理节点，程序核对原文覆盖、对象及公开/私下范围。一个完整输入不会因为包含数个普通步骤而重复执行人物请求。

含固定判定能力的剧本，在首次迁移中保留现有意图解析用途，先确定至多一个规则及其原文片段。显式指定对象不等于显式指定规则；无法可靠选择规则时，继续使用现有解析和校验。规则是第一个有后果的动作时按起始快照准备；位于后段时按前段实际结果准备，不能提前用开局位置、现金或状态计算。集中输出不得在看到判定结果后改换规则或重新投掷。

复杂输入中的“先做甲，再根据结果决定乙”作为条件意图保留。条件不成立时乙没有执行；乙需要新重要选择时在此前停下。`input_map` 只证明输入关联，不证明模型在语义上完整理解了玩家。

### 3.2 场景创作的调用预算

| 路径 | 核心创作用途的调用 |
| --- | --- |
| 资料已足够、候选合格 | 一次 |
| 需要合法补充材料 | 初次材料请求 + 一次完整创作 |
| 后段固定判定依赖前段结果 | 一次检查点候选 + 一次完整创作 |
| 合格材料下首次候选校验失败 | 增加一次完整纠正 |
| 补充读取后候选仍需纠正 | 无判定检查点时最多三次 |
| 材料读取、判定检查点和纠正都发生 | 该用途最多四次；仍未形成合格候选则失败 |

补充上下文最多一次机会，供冻结材料读取或合法目的地人物资料扩展共用；一次冻结材料申请最多四个文件。判定检查点最多一次，结构/业务纠正合计最多一次。Scene 调用计数在整个场景 attempt 内共享，不随读取、检查点或校验函数重新开始。纠正、读取及错误响应全部计量；条件意图解析和现有摘要任务另记用途，整轮统计包含它们。固定判定准备不是一次模型调用。

### 3.3 后段固定判定检查点

例如“走到仓房，再尝试打开上锁的门”，门锁规则的位置条件必须在移动后检查。当前代码已经按输入片段的工作态准备规则；迁移需保持这一因果能力。

检查点响应为互斥的 `needs_resolution` 对象，包含 rule_id、input_fragment_index、prefix_beats 和 prefix_elapsed_minutes。规则和片段必须是前置意图解析选定的对象；前段节点使用相同节点合同，玩家尝试引用已提供的原文片段，覆盖判定前实际执行的内容。此响应不带正式正文或可提交末态。

程序顺序验证前段，构造隔离工作态，再调用现有判定准备。保存准备记录属于已有短事务，钱物、位置和时间后果仍没有提交。前段未成功抵达、许可未取得或条件不成立时，不能强行准备判定；完整候选应保留失败和未执行结果。

续请求包含原始依据、已验证前段及程序判定结果。最终 SceneDraft 保留前段节点不变，再生成后续结果和整段正文。程序核对前段、规则绑定、条件和已准备修正项；纠正不能改写前段来改善判定。跨 attempt 复用既有准备记录时，实际规则前提与 target/modifiers 必须一致，不一致报冲突而不重新投掷。

该检查点由 turn 场景职责处理，不进入 ContextComposer，不建设通用工具框架。取消、超时、额度耗尽或续请求失败时丢弃整个工作态，保留已有准备记录供合法重试复用。

### 3.4 有界的场景执行循环

程序持有本次 SceneAttempt 的快照依据、已提供来源、读取额度、已验证前段、固定判定与调用计数。模型选择需要何种响应，程序决定是否执行该响应及是否继续。循环只有以下路径：

| 响应或结果 | 程序处理 | 下一步 |
| --- | --- | --- |
| 完整 SceneDraft | 严格解析、来源与工作态校验、正式事件编译 | 通过则交给现有最终提交；失败且有额度则纠正 |
| needs_material | 校验目录 ID、授权、去重和额度，读取冻结正文 | 同一依据下重新构建完整请求 |
| needs_resolution | 验证前段与原文绑定，按该工作态准备既有规则 | 固定前段与判定结果后续请求 |
| 可合法扩展的目的地人物资料缺失 | 按已验证到达/明确目标确认人物，装配其个人视图 | 消耗同一补充上下文额度后重建请求 |
| 再次读取、超限、取消或无法纠正 | 结束 attempt，丢弃候选工作态 | 通过现有 run 状态呈现失败/取消 |

目的地人物资料补全是程序在校验候选时识别的上下文缺失，不新增第四种模型响应对象；未经装配的人物行为尚未获准，补全后重新生成完整候选。

一次请求发送前，先检查同一个取消信号、已有截止时间、剩余调用及输入输出预算。已有 ContextGenerator 的材料续请求和 JSON 纠正不能再各自拥有独立计数；scene 在现有调用边界共享第 3.2 节额度，不通过新建 generator 获得新额度。Provider 失败或截断也计入已发生请求；不额外叠加通用自动重试插件。

循环内只执行资料读取、隔离工作态校验和既有固定判定准备。位置、钱物、计划与正式经历仍在最后一次事务落地。没有新的玩家选择时可以连续完成已授权普通步骤；新的重要选择用 stop 呈现，不让 Agent 在后台继续游玩。首次实现不接收运行中 steering，不改变同世界单写者行为。

## 4. 场景是什么

场景是玩家此次意图在当前世界里得到处理的一段连续经历，不等同于一个地点，也不等同于固定剧情节点。询问、获得许可、步行、进入店铺和检查账册可以形成同一段场景，只要行动方向已经明确，途中没有要求玩家作出新的重要选择。

每个场景请求提供临时的 `SceneFrame`。它由现有快照和规则导出，不成为第二份持久世界状态。

| 字段组 | 内容 |
| --- | --- |
| 基础依据 | run、attempt、context_epoch、scene_version、冻结剧本与提示修订 |
| 玩家意图 | 完整原文、界面对象/范围、已有补写设置、必要规则结果 |
| 起始处境 | 世界时间、位置、当前情境、真实资产和身体状态 |
| 参与者 | 当前同场者、已选路线目的地的相关人物、有限场外到期计划所有者 |
| 当前压力 | 未完成约定、相关冲突、既有风险与允许发展的条件 |
| 创作范围 | 已声明地点、实体、物品、能力、发展材料和可引用来源 |
| 时间窗口 | 单轮上限、窗口内已知到期安排、必须处理或停止的边界 |
| 停止条件 | 新重要选择、关键材料缺失、待准备判定、时间预算或新障碍 |

场景不预先选择“调查/战斗/闲聊”三个固定模式，也不建立自动分支树。不同情境通过相同结构表达，篇幅与互动密度由实际内容决定。

### 4.1 一轮处理到哪里

| 玩家表达 | 可以自然完成 | 保留给玩家的决定 |
| --- | --- | --- |
| 问清最后一次见面发生了什么 | 相关追问、解释、人物自然插话 | 接受委托、给出保证 |
| 获得同意后去店里检查房间和账册 | 征求许可、可行的普通移动、实际观察 | 付费交通、撬锁、拿走他人物品 |
| 看字迹并记下发现 | 比较可见字迹、记录、提出有来源的解释 | 将推测当成结论、选择嫌疑人 |
| 到市场找指定商人谈价 | 前往、找到可接触者、问价与还价 | 接受超出已授权范围的价格并付款 |
| 等待某人回复 | 已有预算内等待、相关事件打断 | 自动跳过新的危险或重要邀请 |

“普通步骤”是当前意图的必要低影响执行，不包括新承诺、未经授权的花费、新风险行动或重要立场。玩家已有明确付款、接受、追踪等表达时按原文执行，不因它重要而再次要求重复确认。

### 4.2 场景节点与对话节奏

一个候选节点表达一个有持续意义的对白、行动结果、观察或外部变化。换说话人、进入新地点、产生新知识或状态变化时形成清晰节点；帽子、雾气、姿态等表现细节不要求逐个建节点。

人物可以在同轮回应其他人的新发言。较晚节点的角色来源只能引用较早节点对其开放的投影；程序顺序计算当时的位置和可接触者。模型集中安排交谈，不再通过每人一轮请求取得下一句回应。

普通场景不要求所有同场人物发言。人物通过用词、信息选择、行动和利益体现差异；不通过每段重复一种动作表现性格。沉默者可以收到获准感知，也可以维持当前计划。

首版候选上限为 24 个事实节点，属于可调工程边界，不是故事必须写满的目标。连续对白可合为同一说话者的一段表达；重要变化优先进入节点，表达预算不足时停在完整的因果边界。不得只截断 JSON 或删除最后几项后提交。

### 4.3 时间与跨地点

节点采用从开局时刻起计算的 `offset_minutes`，单调不减；多人同时说话可以使用同一分钟。最后节点偏移与 `elapsed_minutes` 一致，总量沿用当前 0—120 分钟回合预算。绝对年月日时分由程序计算，模型不写新的权威日期。

移动按已声明连接和路线验证。先更新节点工作位置，再推导后续同场；从未到场的人不获得前一地点的对白。途经地点并不自动授予内部资料，只有实际观察到的信息进入个人感知。

超过窗口的请求仅处理实际完成部分；剩余等待和行动不被写成已经发生。多轮长时段模拟不纳入首次迁移。

## 5. 创作空间

| 内容类别 | 处理方式 | 是否进入持续事实 |
| --- | --- | --- |
| 措辞、段落、感官和临时气氛 | 根据风格自由组织，服务于当前行动 | 通常只在正文中 |
| NPC 对白、态度和实际行动 | 结合本人动机与知识集中生成 | 是，保存归属、听众与结果 |
| 普通调查与日常活动的过程 | 完成已选择方向内的合理步骤 | 有后续意义的发现进入事件 |
| 材料允许的压力、机会和外部变化 | 引用发展材料与当前条件 | 是，保留来源与相关进度 |
| 已确定的秘密、重要线索、历史事实 | 保持既定内容，逐步让角色获知 | 发现事件不会改写作者事实 |
| 金钱、物品、地点和规则效果 | 使用已声明能力提出变化 | 通过验证后进入权威状态 |
| 新重要角色、可交互地点、物品类型或机制 | 首版使用已声明目录 | 未声明对象不能绕过导入定义成为运行实例 |

固定事实定义“已经是什么”；发展材料定义“合理地可能发生什么”。来源是创作依据，不要求作者事先逐字写出所有对白和结果。模型可以创造新处境，但不能用一个“创作自由”标签把任意新组织、关键线索、资源或灾难写入世界。

临时路人和日常陈设可以作为低影响表现。需要跨轮记忆、交付物品或承担后续交互的背景人物必须使用当前已有的背景实体身份；本阶段不实现路人升级或动态重要 NPC。

## 6. 上下文构建

### 6.1 一个入口、三种内容分区

场景创作用途拟为 `scene`，ContextScope 的 recipient 使用主持用途的空值，允许读取的个人范围另由程序列出 selected_entity_ids。该范围进入材料授权与诊断，不伪造一个 NPC 身份代表主持。它沿用 ContextComposer 和材料读取入口；现有玩家资料、建议、个人回顾用途仍按接收者独立裁剪。

同一请求中的内容分为：

1. **世界控制资料**：真实位置、状态、物品归属、作者事实、规则和发展依据；用于裁定，不代表任何人物都知道。
2. **人物资料包**：每人自己的身份、动机、已知信息、个人计划、有关关系与记忆，保留 owner 和来源。
3. **玩家表达资料**：玩家可见处境、近期完整交互、玩家原文与叙事设置；正文采用这一视角及本轮新投影。

这三种分区共享模型输入，但不共享知情资格。角色获得知识仍来自个人投影，资料窗口仍消费玩家投影。新增 `scene` 的授权逻辑须显式实现，不能把现有 `owner` 材料整体改为公开。

### 6.2 构建顺序

```text
稳定系统职责与字段合同
冻结剧本的精简核心规则和风格
相关人物的稳定身份、动机和表达特征
相关地点、作者事实、发展材料与检索命中
近期完整因果组及个人长期回顾
当前权威状态、各人物个人知识和当前计划
本轮安排、判定结果、原文和执行范围
```

稳定内容在前，当前处境和原文在后。材料使用稳定 ID 和确定性排序，当前值与初始值明确分离。历史长文本不能把本轮输入埋在中间；最后说明最新状态优先于旧描述。

当前 ContextComposer 将选入的可选节放在 Required 之前，尚未提供上述分区的完整合同。实施时在现有 Material 内表达分区和优先级，保持一个预算算法；不能仅按缓存需要重排而破坏近期事件的因果顺序。

### 6.3 选择范围

| 材料 | 选择依据 | 完整性要求 |
| --- | --- | --- |
| 主角与输入 | 每次提供当前必要信息 | 原文完整，控制选项明确 |
| 同场人物 | 最新位置，结合本轮关系与意图 | 相关人物核心动机不可只剩姓名 |
| 非发言同场者 | 有观察/利益关系时提供必要资料 | 不因沉默删除其感知资格 |
| 目的地人物 | 已选路线或明确寻找对象 | 到场前不得参加原地交谈 |
| 场外人物 | 到期计划、约定或世界安排选中者 | 仅相关个人资料，不遍历全城 |
| 近期历史 | 当前输入、上一组结果及相关连续组 | 发言、回应与结果成组保留 |
| 旧记忆 | 意图、人物、地点、约定和纠正来源 | 未命中不等于不存在 |
| 作者秘密 | 当前调查或发展所需的固定事实 | 保持作者标签和揭示条件 |
| 详细世界资料 | 地点、人物、物品、明确主题 | 按相关性与预算选择，避免全量常驻 |

只提供当前局部世界，不能因为创作职责集中就把所有人物档案和所有世界书一次发送。人物资料的选择不能只靠名字关键词，否则代词、旧约定和隐含目标会丢失；沿用结构引用、当前位置和记录来源。

selected_entity_ids 是本请求的实际创作人物范围，不等同于数据库里所有合法 ID。对白、计划与人物行动必须来自该集合。到达已有地点后出现未装配人物资料时，可以补充读取其已获准资料并重新构建完整候选；范围扩展由程序根据实际到达、原文目标和来源确认。没有资料不能借“该 NPC 确实存在”推测其性格、秘密或计划。

创作人物集合与听众集合分别计算。未装配完整档案的同场人物可以获得其实际听见的公开原话；这不授予模型替该人物创造动机、对白或计划的资格。范围扩展先验证目标/到达依据，拒绝未经装配的行为，再读取该人物已有记忆、计划和知识；这些运行时资料不伪装为冻结剧本文件，不进入任意文件读取接口。它与 needs_material 共用一次补充上下文额度，额度用尽时缺少必需资料则整轮失败。

材料选择先做授权，再做相关性排序。使用已有 Delivery、Purpose、OwnerID、LocationIDs、EntityIDs、ItemIDs、KnownTo、当前位置与实际经历，不增加作者必填的关键词或新世界书格式。当前核心规则、固定判定、参与人物核心资料和必需世界事项是必需组；详细背景按显式引用、当前地点/对象及稳定 ID 排序。材料目录的摘要仅说明可读取内容，不能被当作已提供的完整事实依据。

### 6.4 人物资料包

首版使用已有字段构建以下视图，不要求作者重写全部人物文件：

```json
{
  "entity_id": "shopkeeper",
  "role": "店主",
  "motives": "担忧亲人，同时不愿让争执公开",
  "known": [{"source_id": "personal-record-1", "content": "争执发生在三天前"}],
  "beliefs": [{"source_id": "personal-record-2", "content": "认为陌生客人不可信"}],
  "current_plans": [],
  "relevant_relationships": [],
  "speech_style": "尽量简短，谈到家庭时回避细节"
}
```

示例 ID 为设计占位，运行时由已有身份和记录生成。`known` 与 `beliefs` 是上下文视图，不是新增第二套知识数据库；无法从旧记录可靠拆分时保留原文及来源，不让模型生成一个猜测的分类后当成事实。

人物资料同时指出当前行为理由和表达特征。避免用精确信任数字替代动机，也不要求角色每次说话都复述档案。主角自身不知道的 NPC 动机只供主持安排，不出现在玩家资料或全知旁白中。

### 6.5 多人物记忆与上下文补全

集中调用继续使用现有 memory 的来源流、Digest、近期完整回合组和有界召回。每个人先独立形成带 owner 的个人视图，再由唯一 ContextComposer 合并和分配整场预算；不能把 withLongMemory 连续作用于同一个 Material，因为当前函数会重置 Optional 和单 scope 窗口。也不能为每个人分别分配完整 12,000 输入额度后相加。

场景经历使用 `columns=[id,seq,actor,kind,content]` 与有序 `records` 行表，保留每条记录的完整内容和 owner 限定别名；规范事件 ID、存储时间戳和归一关系由程序保存，不在每份个人正文中重复。程序解析的原文绑定同样保留完整 text、意图、对象、范围、等待和规则值。请求字段合同标明可选字段，并按已启用能力列出效果类型；本地类型、来源和业务校验保持。提交用的世界身份、epoch 和场景版本进入 ContextScope 与事务检查。

补全次序为当前权威状态和已选人物核心资料、近期完整因果组、当前计划与 Digest.States 中相关的信念/担忧/承诺、本人旧经历召回、详细冻结材料。重要旧证词或承诺有明确来源引用时，按 owner 到既有 archive 取完整组并去重；无法可靠定位时保留检索不足，不让模型补写原话。当前召回是有界关键词机制，不宣称已经具备向量语义检索或任意历史必然命中。

摘要仍是本人的主观记忆视图，不能覆盖权威现金、位置、时间、物品或固定作者事实。本轮上下文裁剪不修改原始经历或推进摘要水位；持久摘要维护按现有连续覆盖和比较发布合同推进。近期尝试与结果成组保留，关键证词不采用首尾截断。个人来源归一逐 owner 执行，第 11.3 节定义持久转换。

补材和纠正从基础快照与已经选中的来源重新构建请求，不在上一份输入末尾反复追加全套人物档案。所有选中人物共享预算与去重规则，来源身份包含 owner。初次实现保留现有摘要维护调度和单独计量，不承诺整个 Turn 只有一个请求，也不新增全局记忆库、向量服务或会话树。

#### 6.5.1 重点记忆与原始经历

| 内容层 | 现有载体 | 进入本轮请求的方式 |
| --- | --- | --- |
| 连续回顾与仍相关的主观状态 | MemoryDigest.Content / States | 按 owner 提供回顾及相关信念、关系、关切和承诺，保留来源 |
| 近期互动 | 尚未摘要的个人来源流 | 按完整已提交回合组提供，尝试、回应和结果共同保留 |
| 旧经历 | 本人的有效 archive | 优先按已知来源定位完整组，再使用现有有界关键词召回 |

三层共同使用场景预算，不另建常驻 MEMORY.md/USER.md，不按人物数量复制完整记忆窗口。Digest 的覆盖水位与来源集合维持现有完整性；选择相关 states 只影响本轮视图。人物档案、当前计划和权威钱物仍由各自现有载体提供。

#### 6.5.2 旧经历定位与召回边界

程序先确认账户、world 和 owner，再确认来源有效性，最后排序相关性。明确引用旧承诺或证词时，只定位已获准的个人来源及其因果组；首次迁移复用现有 archive 与组预算，不新增扫描全部历史的旁路。来源在本次预算内不可达时明确标为受限，不能将未提供原文改写成确定事实。

查询沿用玩家原文和现有场景对象，不增加检索规划模型或任意 SQL/文件工具。结果保留 source/event/run、个人范围与顺序，按第 11 节归一；去重只避免重复输入，不消除个人知情资格。容量不足时移除非必需完整组并记录原因，必需组放不下则报告容量错误，不能把截断的关键证词当成完整依据。

现有汉字双字切分保持。长历史全文索引仅作为后续候选：出现窗口外漏召回或检索耗时证据后，在现有 world 存储与 memory 职责内评估。索引须可从有效个人来源重建，查询先限定 world/owner，再做相关性排序；保留来源失效与原文定位。不接入 Hermes 的原生扩展或外部语义服务，首次迁移不新增索引表或数据库布局。

#### 6.5.3 摘要内容与世界时间

摘要职责文件继续位于 turn 的记忆生成职责中，沿用 content/states 合同与 belief、relationship、concern、commitment 四类。正文描述、人物说法和本人判断分别保留来源；说过、尝试过、观察到、已完成的结果使用准确措辞，不将谎言或推测认证为世界事实。

连续摘要更新保留仍有效的承诺、未解关切和影响当前处境的关系变化；已兑现或取消的承诺按已提交结果表达，不能继续写成待执行任务。失败尝试与尚待处理的目标分别表达，不能把失败记为成功，也不能仅因尝试失败就关闭仍有效的承诺。已经覆盖的原始经历仍保留在 archive，不因重点状态退出本轮输入而删除历史。个人记忆中的关系感受不替代权威关系值。

已提交来源或正式约定有明确世界时点时，按该时点表达年月日与时分。历史相对表述只有在其所属事件的世界时间可定位时才能换算，不能用当前日期反推所有旧事。MemorySource.CreatedAt 是保存元数据，不用作世界时钟；旧记录缺少时间依据时保留原表述和不确定性，不生成精确日期。

#### 6.5.4 有界维护与发布

常规摘要沿用 PrepareLongMemory 的现行触发、维护额度与独立调用计量；后台重建沿用现有 memory_jobs。首次迁移不改变两者调度，不增加逐 NPC、逐轮的回顾 Agent，也不让场景模型自由调用 add/replace/remove 整理记忆。

每次整理生成一份完整摘要候选，统一校验内容、states、来源及覆盖范围，再比较发布 epoch、revision 与 source head。取消或来源变化导致依据失效的迟到任务拒绝发布；另存后任务仍只属于其绑定的 world，不能向新存档发布旧任务结果。达到现行维护或纠正额度时停止本次整理，保留有效旧摘要和未摘要尾部，不清空经历或重置额度继续调用。

可选整理失败时，已有有效摘要与尾部仍按预算装配；必要记忆重建未就绪、来源冲突或必需上下文超限，继续使用现有阻塞/失败合同。正文响应速度不能通过跳过来源校验或提供空记忆获得。

### 6.6 冲突与缺失资料

当前权威状态决定现金、位置、持有物和已结算效果；有效事件与纠正依据决定已经发生的事；冻结作者事实决定预设历史。个人说法保留为说法，旧摘要可以过期或错误，开场材料不重置存档。

当已提交事实与冻结作者事实发生无法解释的实质矛盾时，记录具体来源并保持最近已提交状态，进入已有纠正/检查路径；不静默改写历史以适配当前剧情。新的假设保留不确定性，不填充为已证实结论。

缺少详细资料时可以请求目录中获准的材料，或者在关键未知处停下。无需增加一层总规划请求来判断是否检索。

### 6.7 容量与输出预算

沿用模型窗口、推理预留和完整请求估计。首版继续以当前 12,000 输入上限为起点，阶段基准再决定是否调整。该值不是一般模型能力上限。

裁剪顺序：无关详细背景、无关远期记录、较旧完整因果组，再缩减非关键人物的详细表达资料。完整地点 ID、名称、层级和连接保留为必需图；详细环境参加可选背景预算，当前个人情境继续保留本人来源。稳定人物档案可使用共享字段表，完整保留 owner、身份、资料、外貌及表达样例。原文、当前权威状态、当前关键事实、相关人物核心身份和最新完整因果组属于必需内容；必需内容仍超限时明确失败或要求缩短输入，不偷偷删除。

场景输出同时包含正文和结构化信息，不能直接套用原正文的 768/1536/3072 token 上限。首版由已有篇幅设置提供正文目标，再加经场景样本测量的结构预算；两部分总和仍受 Provider 输出窗口及响应字节上限约束。结构开销不足时调小场景跨度或非关键内容，不能通过破坏 JSON 取得更长正文。

篇幅设置调节展开程度，不设置每轮最低字数。质量指标是有效回应和信息变化，不是字数增长。

### 6.8 选择诊断

复用现有 ContextBuildReport 与模型调用诊断，补充 scene 人物集合、owner、冻结修订、选择原因、整组裁剪、读取/检查点/纠正分类和共享额度。原因使用 core、current_place、explicit_reference、personal_source、due_progress 等内部值；它们不进入玩家 UI。

每次请求应能定位实际提供了哪些来源、哪些只是目录条目、哪些被预算排除。基线版本、材料修订和正式来源用于核查上下文；诊断不默认保存完整私人 Prompt，不宣称仅凭来源 ID 就能逐字重放请求或重现 Provider 输出。必要材料是否提供由程序报告，不能依赖模型声称“我已读过”。

旧经历诊断区分没有命中、检索受限、已提供去重、预算排除和来源失效；只有实际装配的原文才计为提供。检索与摘要质量由 T18、T36、T38、T41—T43 和 E08 对照，不新增玩家常驻记忆面板。

## 7. 缓存与性能

现有 Provider 接入已读取缓存 token 用量，应用计量记录命中与未命中；这不证明请求编排已达到稳定前缀，也不证明存在应用控制的 Provider 缓存。

| 优化 | 目标 | 不能替代的工作 |
| --- | --- | --- |
| 冻结材料解析与只读装配复用 | 减少本地重复加工 | 个人授权和最新状态选择 |
| 稳定提示与材料顺序 | 为 Provider 支持的前缀复用提供条件 | 语义相关性和窗口控制 |
| 检索与完整组裁剪 | 控制输入噪声、保存关键因果 | 长期原始事件保存 |
| 减少串行创作交接 | 降低整轮等待并减少衔接损失 | 真实输出质量与错误恢复 |

缓存策略以真实诊断为准，不在方案中承诺命中比例、费用折扣或有效期。缓存命中的内容仍计入模型上下文容量。世界状态变化后的生成结果不能直接当成可复用响应返回。

稳定前缀限于职责、冻结规则和适用的稳定档案；日期、位置、钱物、个人摘要修订与计划来自本轮基线及已验证工作态。摘要发布后，下一轮读取新修订；同一 attempt 的续请求保持基础快照和已提供来源绑定，不中途替换摘要。不冻结整段游玩记忆以维持前缀命中。

若需要本地装配缓存，其键至少区分账户/世界、冻结材料修订、提示修订和用途；包含个人范围时纳入人物集合与授权依据。动态块另由 context_epoch、scene_version、事件头和相关状态依据控制。先复用冻结内容，不优先建设持久上下文缓存服务。

## 8. 世界推进进入场景请求

既有外部安排、发展事项、个人计划、旧剧情节点与开放事件仍分别保存原有进度。模型看到的是本轮候选窗口，不是全量任务卡列表。

1. 按现有世界时间准备窗口内的作者安排与到期个人计划。
2. 沿用发展相关性、轮转和语义 basis，选取一次有意义的评估机会。
3. 将同场、目的地和有资格进入实际评估的有限场外人物资料纳入 SceneFrame。
4. 模型在完整场景中选择发生、暂缓或不发生，并输出相应来源和评估结果。
5. 程序按节点工作态确认条件、更新实际进度；暂缓不写成已经发生。

首版继续保持有限场外参与，不展开全城模拟。每轮实际处理选中的世界评估对象与至多两名到期计划所有者，沿用已有优先级和轮转，不因合并请求同时评估所有安排。外部变化可以良好、不利、中性或平静；玩家不行动本身不构成必须惩罚的理由。

SceneFrame 中的窗口候选与最终选中对象分别表达：窗口只说明哪些事项可能在 0—120 分钟内变得相关，正式资格由实际经过时间、工作位置、当前状态和已有轮转决定。未来个人计划以 ID、owner 和检查时点提供目录；初始人物资料按当前同场、明确对象和实际到期 owner 装配。节点使计划实际到期时，至多两名缺少资料的 owner 共用一次扩展机会，获得完整个人资料后才能复查或行动。不能用预估 120 分钟提前唤醒实际只过了一分钟的计划，也不能只按开场位置选择发展事项。验证后若选中对象缺少材料，补足仍消耗本场景唯一一次材料读取预算，完整候选重建遵守第 3.2 节的共享调用上限。必要依据仍不足或预算已耗尽时失败，不以“留到下一轮”掩盖遗漏已应评估的事项。

候选节点造成新地点/显著变化后，尚未进入本轮必需评估集合的新发展机会可以按既有轮转留待下一轮；已经符合本轮评估资格的安排与计划遵守上一段的处理合同。不得用“节省调用”为由猜测尚未读取的作者安排。

选中的到期事项须返回合法评估结果，包括有依据的暂缓；实际发生的节点按其发生时间顺序处理。选中的关键安排缺少材料时先补充读取，仍不能形成完整候选则失败，不能因为正文已写完而静默跳过。未选中的一般个人计划复查按已有有界调度延后，复查时间与行动发生时间分别记录；不把每一项到期计划变成阻断场景的硬边界。

新的开放事件候选沿用现有生成数量、冷却和活跃上限，必须在首次迁移验收中覆盖。旧 guided 剧本的冻结节点和结局语义保持，不将其历史存档改写成新的固定分支。

## 9. SceneDraft 输出合同

以下类型属于内部候选合同。运行结果转换为现有 `turn.Output`；玩家 API 与数据库继续使用各自现有结构。

完整候选、补充材料请求和固定判定检查点三种响应互斥。补充读取继续使用已有 `{"needs_material":["已列出的材料ID"]}` 形状，不同时返回正文、节点或部分效果。needs_resolution 只使用第 3.3 节的前段合同；最终响应必须是完整 SceneDraft。

| 顶层字段 | 类型 | 含义 |
| --- | --- | --- |
| `schema_revision` | string | 首版候选合同版本 |
| `input_map` | array | 原文片段、类型、对象、范围、执行节点与未执行说明 |
| `beats` | array | 顺序排列的对白、行动结果、观察和世界变化 |
| `narrative_blocks` | array | 玩家正文段落及支持它们的可见节点 |
| `elapsed_minutes` | integer | 实际经过分钟，0—120 |
| `stop` | object | 结束原因及留给玩家的处境 |
| `progress_updates` | array | 已选世界事项/个人计划的候选进度 |
| `event_offer` | optional object | 已启用开放事件时的触发节点和 0/1 新事件候选 |

input_map 的每项包含 text、intent_type、addressee_id、visibility、beat_ids、status、unexecuted_reason；需要时使用既有 wait_minutes/action_rule_id。text 是连续原文，最多四段，程序计算字符偏移并确认覆盖全部非空白原文。status 使用 succeeded/failed/partial/not_executed 表示处理结果，不能把一个查询未得到答案认定为玩家没有开口。未执行说明只有在确实有剩余意图时填写。

### 9.1 节点字段

| 字段 | 约束 |
| --- | --- |
| `local_id` | 本响应内唯一，如 b1；不是模型指定的正式事件 ID |
| `kind` | dialogue / action_result / observation / world_change |
| `actor_id` | 当前可用人物、玩家或对应世界职责；不得编造实例 |
| `target_id` | 可选人物目标，使用冻结人物 ID 或 `player`；地点和物品由相应效果字段标识 |
| `offset_minutes` | 实际发生时间偏移，顺序不回退 |
| `basis` | 请求已提供来源或更早节点对本人开放的投影 |
| `status` | 行动结果使用 succeeded / failed / partial / not_executed |
| `attempt` | 行动结果对应的尝试；玩家尝试关联 input_map，NPC 尝试使用本人的明确表达 |
| `content` | 作者层事实或该说话者的实际发言，类型明确 |
| `scope` | 对话使用公开或指定私人听众 |
| `recipients` | 获得结果的重要人物与玩家，按当时资格验证 |
| `bystanders` | 实际参与的既有背景实体 |
| `projections` | 行动/观察/世界结果的实际个人感知；对白填空数组，由程序派生 |
| `effects` | 对应节点的移动、状态、关系、物品与计划变化；复用已声明能力 |

| kind | 必需附加字段 | 允许的 effects | 禁止的组合 |
| --- | --- | --- | --- |
| dialogue | scope；公开 recipients 为空，私人 recipients 明确 | 有本人来源的 relationship_effects/plan_updates | 非空 projections、status、attempt、移动、付款和物品转移 |
| action_result | status、attempt；玩家尝试关联原文 | 启用且符合结果的全部能力 | 把未执行动作标记为成功、失败却获得成功才有的资源 |
| observation | 非空个人 projections | 有依据的 relationship_effects/plan_updates | 仅因看见物品而转移归属、凭空扣款或移动 |
| world_change | 有资格的世界材料及进度关联 | 声明能力和传播条件允许的变化 | 无依据更换重要人物、地点或资源目录 |

公共字段为 local_id、kind、actor_id、offset_minutes、basis、content、recipients、bystanders、projections、effects，每个节点都提供，空数组或空 effects 显式表达。target_id 可选；scope 只用于 dialogue，status/attempt 只用于 action_result。内部类型按 kind 区分字段，校验拒绝跨类型字段，不把所有附加字段设为所有节点必填。其他节点的接收者范围由 recipients/bystanders/projections 表达。沉默和“没有新变化”可以没有节点，不要求虚构一条观察填满数组。整轮结果至少有一个可见的有效回应，或者有明确的未执行说明。

对白只输出一次实际发言 content。dialogue 的 bystanders/projections 均为空；公开听众由程序按节点当时位置/旧版本接触名单推导，私人 recipients 沿用已有一至四名可接触听众的合同，排除说话者与重复 ID。程序为说话者与合法听众生成原话投影，记录“本人说过/听见某人说过”，不将说法认证为世界事实。私聊旁观迹象另用 observation，第三人不获得私聊原文。

`basis` 的来源项区分材料、已提交事件和 `beat:<local_id>`。人物节点引用新节点时只取得自己的投影，作者根内容不能成为其个人来源。原始玩家输入由程序单独保存，模型不会通过改写 `content` 覆盖原文。

对白与人物计划的 basis 必须属于本人资料或已收到投影。裁定观察、行动和外部变化可以使用主持获准的作者事实，但由此形成的新个人知识要经过该节点投影。不能因玩家尚未知晓一个房间里的物品，就禁止主持裁定玩家实际打开房间后的发现。

公开对白保存“这个人说了什么”，不是世界认定说法为真。观察可以保存“玩家发现一张纸条”，推测则保存“玩家认为纸条可能来自某人”。知道文件存在不等于取得物品所有权。

### 9.2 正文段落

每个 `narrative_blocks` 项包含 `text` 和 `beat_ids`。关键对话、结果和发现有对应的玩家可见节点；纯表现段落可以没有事实节点，但不能凭空改变后续资源、位置、知识或选择。

玩家没有收到投影的事实节点不能支持正文。对话可以间接转述、合并同义内容，不能把拒绝改成接受、把尝试改成成功。段落引用提供结构检查，不是自然语言语义一致性的证明。

模型不必重复输出一份全量末态。程序从顺序节点计算最终位置、钱物和状态；最终资料投影使用这些值。由此减少“正文、delta、末态”三份内容互相矛盾。

普通语气、姿态、环境描写和过渡句只写正文。关键说法、承诺、发现、实际行动及状态变化才进入 beats；一段连续发言可以合为一个节点。正文负责表达，节点负责持续事实；不要求模型再输出逐人总结、全量记忆、末态表或隐藏推理。行动/发现因人的感知差异仍须明确 projections，不能为减少字数把作者根内容广播给所有人。

### 9.3 结束原因

`stop.reason` 使用 completed / player_choice / interrupted / time_limit。它解释当前场景的结束点，不创建固定选项分支。

`completed` 可以是简短互动的自然结束；`player_choice` 明确指出新的重要选择；`interrupted` 对应本轮真实发生的节点。关键材料不足使用互斥的补充读取响应，仍不能形成完整候选则整轮失败；已经确认“身份未知”等剧情事实可以自然呈现，不等同于上下文缺失。

未执行的原文片段列在 input_map，不因为正文结束而丢弃。仅在用户要求后续行动时保留其意图，不能自动排队到后台继续执行。

### 9.4 能力与进度候选

effects 按本剧本启用能力提供字段，关闭能力时省略该字段并拒绝相应变化。数值变化使用既有类型；不引入任意 JSON Patch。

| 字段组 | 模型提供 | 程序绑定和计算 |
| --- | --- | --- |
| movements | entity_id、from、to、route | 当前节点的正式行动/结果来源，移动后的同场名单 |
| state_effects | entity_id、state_id、delta 或 value | 类型、范围、声明预算与新值 |
| relationship_effects | subject_id、target_id、relation_type、delta、个人 basis | 有向主体、知情来源与新关系值 |
| item_transfers | instance_id、明确的原归属与目标归属 | 当前实际归属、唯一归属和正式来源 |
| plan_updates | owner_id、id 或 local_plan_id、content、status、review_after_minutes、个人 basis | 正式计划 ID、版本、下次检查时间、来源归一 |
| legacy_scene | content、characters；仅无 spatial 的冻结旧世界 | 已成功或部分成功的显式换场、冻结人物名单与旧场景内容 |

有实际行动的节点由程序生成对应尝试与结果事件；尝试来自玩家原文或 NPC 的 attempt，结果保留 succeeded/failed/partial 区别。能力 effects 引用程序绑定的行动/结果 ID，不让模型猜测旧阶段 event_id。失败节点不同时获得成功才会产生的钱物效果。

progress_updates 仅列本请求选中的对象，包含 type、id、status、content、offset_minutes、basis、关联 beat_ids。content 保留评估结论或暂缓原因；offset_minutes 是实际评估时点，相对本轮世界起点计算。类型区分 external_schedule、development、personal_plan、legacy_node、generated_event。评估使用对应已有 occurred/deferred/skipped 合同；personal_plan 以 occurred/deferred 表示本次复查是否完成，计划自身 active/paused/completed/cancelled 仍由 plan_updates 表达，不合并为一套新的任务状态。

世界事项的 occurred 进度关联同一评估时点的 world_change；deferred 使用空 beat_ids，不生成已经发生的世界事实。世界变化可以没有个人接收者，projections 此时为空，正文只引用玩家实际获得的投影。结构条件由程序在首次发生节点之前判定，程序记录条件依据；同一次发生不会因自身改变了条件而被再次否定。legacy_node 的 ending 只适用于 guided 模式中已经结算的 terminal 节点。

personal_plan 的 progress_updates 仅记录此次复查是否完成及其依据，具体计划 content/status/review_after_minutes 由唯一的 plan_updates 提供。程序按 owner/id 合并一次，拒绝重复或互相矛盾的更新，不让同一计划因两处字段递增两次版本。

NPC 可以形成新计划。更新已有计划使用现有 id，新建使用响应内 local_plan_id，二者互斥；程序生成属于该 owner 的正式计划 ID。保留现有每人至多四项更新、内容至多 1200 字、来源 1—8 项、active 复查间隔 1—43200 分钟及其他状态间隔为零的合同。新计划不需要属于本轮到期清单，但必须属于本请求选定人物且有本人来源。

复查后仍 active、没有新计划内容且 NextCheck 已到期时，沿用当前程序兜底：LastCheck 更新为实际复查时间，NextCheck 为该时间加 30 分钟。显式更新已经给出未来检查时间时不再兜底，不重复增加 Version；真正 deferred 的复查不伪造已完成记录。时间值来自发生该复查的工作节点，不能一律用整轮结束时间。

development 的语义 basis 和轮转由程序计算；外部安排的已应用标记绑定正式事件。初始计划材料只初始化一次，后续使用当前 PersonalPlan。没有世界变动的复查仍可更新已评估依据，不把它编造成玩家可见事件。

event_offer 复用现有开放事件的 condition、development、after_minutes；触发位置与 kind 引用本轮已成功/部分成功节点。初始结果以当前 beats/projections 表达并关联 initial_beat_ids，不再重复另一份对白或事实。initial_beat_ids 按当前节点顺序排列，后续检查时间等于首次初始节点的世界时间加 after_minutes；本轮停止点位于该时间之前。程序校验作者节点优先、冷却、活跃上限和候选 0/1，再生成原有 GeneratedEvent 起点与后续记录。首版没有额外的开放事件导演请求；配置关闭时没有 event_offer。

## 11. 校验与正式结果构造

### 11.1 结构校验

检查完整 JSON、版本、字段类型、节点数量、唯一 local_id、合法枚举、顺序时间、输入覆盖和必需投影。未知字段、重复 JSON 键、截断响应与模型自造身份进入已有纠正机会；仍失败则没有提交。

正式 run/event/instance ID 由程序生成。`local_id` 只在本次 attempt 内使用，依次映射为当前 run 下的正式事件。重试不得沿用前次候选的未提交事实。

### 11.2 顺序工作态校验

每个节点先检查 basis 和当时行动资格，再调用现有能力校验/应用函数。移动后才能让新地点人物参与；失败后不能应用仅在成功时成立的效果。同一物品连续转移按前一节点结果检查，不能在一次事件里属于两人。

effects 应用保持同一回合的累计变化列表，状态和关系的 max_change_per_turn 按完整 Turn 累计，节点与检查点不能重置预算。Order 和当前归属来源持续传递；失败时整体丢弃这些列表。

现金变化使用声明币制的最小单位和已有状态机制；不允许负余额、未声明字段或凭空物品。固定判定使用已准备结果；关系与计划变化只能引用所有者实际获知的来源。

当前一些校验限制行动结果必须引用旧 stage 1/2 的尝试。迁移时抽取“身份、资格、来源、能力”纯规则，并让集中候选提供同等行动依据；不能仅取消阶段检查后接受任意事件。

### 11.3 来源转换与持久依赖

场景构建和节点编译共用临时 SourceLedger，复用现有来源归一与持久依赖规则，不建立新的长期记忆库或另一套来源能力。每项记录来源类别、实际提供范围、owner、原始事件及本轮个人投影。角色引用 beat:b1 时，先核对该角色收到的 b1 投影，再转换为正式依赖；不能只因为 b1 存在就允许所有角色引用。

来源键保留 owner，不使用 scene 的空 recipient 展开所有人物的个人记录或 digest。canonicalContextSources 依赖具体 recipient，必须逐 owner 调用既有归一函数，再合并正式依赖。类似的记录 ID、不同 digest 修订和多人收到的同一对白仍分别验证；归一后的事件去重不删除个人资格。

| 请求/候选来源 | 正式处理 |
| --- | --- |
| 冻结 material / definition | 保留修订标识与依据，不伪装为数据库事件外键 |
| 已提供个人记录或 digest | 使用现有归一函数展开为本人实际事件来源 |
| 旧事件 | 确认存在、有效且在本次提供范围内后绑定 |
| beat:<local_id> | 转为本轮已验证正式事件及该角色实际投影的来源 |
| fact 标签 | 核对对应冻结事实或已有证据；有事件依据时绑定，标签本身不是可提交事件外键 |

每个 local_id 映射到作者/行动结果事件与逐人投影。action_result 的正式尝试和结果保留现有 action_id 与 `:result:<序号>` 语义，规则节点绑定已准备的 ActionResolution.ActionID，不重新编号该行动。Stage、Seq、SceneVersion 和时间事件由程序按节点顺序计算，不由模型指定。

生成事件的 BasisEventIDs 和 ProjectionParentID 必须在同一最终事务内已经插入或来自有效旧事件。禁止写入 beat:、digest: 等临时标识、未来节点和不存在的父事件。状态、位置、物品、关系和计划的来源及 Before 来源均一并校验，使纠正和依赖失效能沿真实事件追踪。

当前关系更新依赖已提交个人经历与 NPC 提案。集中场景拟允许本人刚收到的、已经验证但尚未提交的节点投影成为关系依据；该提案由对应主体的 SceneDraft 字段表达。程序检查主体、来源、重复和整轮预算，不通过伪造旧 NPCDecision 绕过原校验。新合同在切换时更新，原路径在 P1 仍保留已提交经历语义。

### 11.4 投影、记忆和场景视图

按节点当时的听众和位置形成个人投影，保留作者事件与个人内容的对应。角色可从前一公开发言形成本轮后续反应，晚到者不获得此前内容。第三人只见到私聊迹象时，该迹象与私聊正文分开。

由已验证投影生成个人经历和记忆来源，继续使用现有 memory 记录。首版不要求模型再输出每人一份冗长 memory，也不从玩家正文反向抽取其他人物知识。现有长期摘要按需要维护，摘要的失败与正文回合失败按既有依赖区分。

公开/私下对白沿用 speech 的程序派生逻辑，行动/观察/外部结果沿用显式个人投影合同。两类输入经同一来源与记忆提交路径保存，不新增第二套投影实现。

SceneView 只接收该人物的投影与已有获准来源。作者结果不能直接写为所有人的场景摘要，关系面板不能展示 NPC 隐藏动机。

### 11.5 能保证什么

| 可由程序检查 | 主要依赖模型质量和体验验证 |
| --- | --- |
| 引用存在、输入片段对应、来源范围和时序 | 对玩家意图的完整理解 |
| 位置连接、听众资格、数值范围、物品唯一归属 | 新线索和人物反应在语义上是否合理 |
| 日期计算、版本、取消和一次提交 | 未知秘密是否通过措辞或选择影响其他 NPC |
| 正文引用的节点是否对玩家开放 | 正文是否准确表达节点且没有未标记的新事实 |
| 个人记忆只写入本人投影 | 个性鲜明、节奏合适、内容有趣 |

不固定加入另一个模型逐轮审核正文。规则禁止的结构结果必须拒绝；轻微表现偏差沿用产品容错和纠正机制。实际评估发现持续的重大语义不一致时，先缩减输出复杂度、改进材料或调整场景跨度，再评估是否确实需要额外调用。

## 12. 错误、取消与恢复

| 情况 | 行为 |
| --- | --- |
| 超时、连接失败、模型暂停 | 失败原因使用已有错误映射，原文保留，世界没有本次后果 |
| JSON、身份、来源或能力校验失败 | 同一依据下一次完整纠正；仍失败则整轮失败 |
| 中间节点不合法 | 隔离工作态整体丢弃，不提交合法前半段 |
| 正文为空或响应截断 | 候选不完整，不仅提交状态变化 |
| 用户取消/切换世界 | 取消传播至调用，最终事务再次核对运行资格 |
| 版本冲突 | 拒绝陈旧候选，不把旧响应套到新状态 |
| 提交结果暂时未知 | 沿用 run 查询与恢复，先查状态再决定重试 |
| 已提交运行重复查询/提交 | 返回既有结果，不重复扣钱、转移或推进时间 |

整份候选纠正包含同一快照、相关材料与精简本地错误，不把上一响应的全部私密内容写入玩家提示或日志。单轮扩大后，一次失败可能丢弃更多生成内容；重试成本必须计入实测，而不是只统计第一次成功请求。

进程重启沿用现有未完成 run 标 interrupted 与安全重试，不承诺从任意未提交节点恢复自动续跑。提交结果未知先查现有 run/请求依据；已准备固定判定可按第 3.3 节复用。模型输出截断时整个候选拒绝，不能截取可解析前半段执行。

首版继续提交成功后展示正式正文。若已有界面展示生成进度，其含义是生成中；不把流式候选当作已经发生。实时正文流与局部提交不属于本阶段。

## 13. Prompt 组织

提示属于执行场景调用的 turn 职责文件。沿用设置转换函数，按下列次序组合：核心创作任务、人物与事实分区、玩家控制、世界机制、表达设置、字段合同。通用提示使用角色 ID 与材料，不出现具体剧本名。

既有 NPC、coordination、narration 三项自定义行为策略在一个请求中仍按“人物表现、行动与情境、正文表达”三个分区使用，并形成可追踪修订。它们不再指向三个必定发生的模型请求，也不覆盖世界真值、原文与输出合同。已有设置字段保持可读取，避免旧存档偏好丢失。

### 13.1 核心创作提示草案

```text
你负责生成玩家此次意图在当前世界中形成的一段完整经历。
统一安排相关人物的对白、行为、场景变化和正文，让回应自然承接。
完成玩家已经选择的方向中的普通必要步骤，在新的重要选择前停下。

世界控制资料描述真实状态与作者事实；人物资料包分别描述各人的知识、
动机、误解和计划。主持能读到的资料不等于每个人物都知道。
人物可以拒绝、隐瞒、误判、协商、主动发起互动或保持沉默。
人物的后续反应依据本人资料和此前实际获得的投影。

保留固定事实，依据已提供的发展材料创造合理的新处境与机会。
表现细节可以自由组织；影响后续交互的发现、承诺、行动和变化写入节点。
普通阶段可以平静结束，不强制增加危险、谜团或全员发言。

玩家保有尚未表达的重要选择。按照本存档的人称、篇幅、描写密度、
主角补写和人物主动性组织正文。补写设置不授予额外钱物或世界权限。

资料足够时只返回声明的 SceneDraft 字段，正文和节点描述同一份经历。
资料不足时只返回 needs_material 及目录中的材料 ID，不混入部分正文或效果。
后段固定判定需要前段工作态时返回声明的 needs_resolution 检查点；
随后使用程序提供的固定结果完成同一段经历，保持已验证前段不变。
判定结果使用已准备的规则结果；日期和最终资产由程序计算。
来源不够时请求获准材料，或在确实未知的地方保持不确定。
```

### 13.2 场景节奏提示草案

```text
围绕本次意图安排必要观察、行动与交谈，给实际信息变化留出篇幅。
无需把拿起物品、翻页、走到门口等普通步骤分别留到下一轮。
一旦遇到新承诺、新支出、重大风险或新的调查方向，就明确呈现处境。

对白体现各自利益和说话方式。相关人物可以彼此回应，不按名单轮流发言。
环境只在帮助观察、行动或情绪时展开，避免反复描写相同雾气和姿势。
换说话人或动作重点时自然分段，结尾落在本轮实际完成的事情或新选择上。
```

草案属于待实施合同参考，不是已部署提示，也不要求输出隐藏推理、长篇计划或审稿过程。

## 14. 行动建议与阅读界面

正文、日期地点、自然语言输入及现有资料入口保留 A 方案。玩家不选择 NPC/主 Agent 模式，也不看到内部节点和校验清单。

三项建议继续纵向展示，生成内容包含具体对象、做法和目的，区分当前可行的参与方式；没有固定保守/激进/推进三个槽位。建议不提前确认别人同意，不暴露未获知秘密。点击继续填入可编辑草稿。

首版保留现有提交后建议用途，避免把建议内容与主回合一起失败。建议依据新的玩家投影和 scene_version，迟到结果按现有 basis 校验丢弃。计量同时报告正文完成时间和建议就绪时间。

角色、背包、地图、人物资料使用已提交服务端数据，不从 SceneDraft 或正文解析。查看资料不耗游戏时间，草稿、滚动位置和交谈对象沿用已有机制。

## 15. 剧本材料与可复用性

首版沿用 Story Pack v4 JSON/Markdown/ZIP 数据合同。世界、人物、初始状态、地点、材料索引、发展条件与计划继续由作者声明。集中创作不要求把剧本转换为一份巨大提示。

作者材料应明确：固定事实、当前处境、人物利益与表达方式、已知/误解、允许发展的压力与机会、可接触地点和资源。以上是内容组织建议，能由现有 profile/knowledge/background/facts/developments 文件表达，不默认增加必填字段。

知情范围仍按材料索引与个人记录管理。导入提示只能作为题材材料或风格偏好，不能替换场景系统职责。PNG/CCv3、外部脚本和宏不在当前导入能力内；本阶段不建设兼容解释器或普通玩家创作页面。

非诡秘验证使用中性城镇的交易/调查最小 fixture，覆盖两位立场不同的人物、有限地点、可选钱物和一项发展条件。它是机制验证资料，不新增正式发行剧本；已有历史兼容资料保持原样。

## 16. 兼容与迁移

### 16.1 旧存档

旧世界继续使用自己的冻结定义、ID、位置、状态、币制、事件、感知、计划和叙事设置。新代码改变生成组织，不覆盖这些内容。v1/v2 的相对时间、v3/v4 的空间能力和能力缺项按已有版本合同读取，不猜测新日期和不存在的现金。

原则上不新增持久 schema；确需记录协议版本或来源字段时，先审查能否使用现有事件元数据。新增字段必须给出精确迁移、缺省读取与存档复制测试。协议修订优先记录在已有请求诊断与事件类型中，不通过用户级运行模式保留两条引擎。

个人摘要保留原来源；旧 NPC 原文事件不要求批量重写。受限纠正、依赖失效、另存与重启通过原有逻辑继续生效。

现行纠正不支持任意结构状态回滚：会失效当前位置来源，或命中受保护的状态、关系、物品、历史已结算变化、固定判定与当前计划来源时，程序拒绝纠正。普通未被结构状态消费的文本仍可按既有路径纠正和重建个人摘要。Phase13 保持这一边界，不将来源可追踪宣称为钱物/位置自动重建；增加结构重建需另行设计与授权。

### 16.2 迁移顺序

| 单元 | 可交付结果 | 切换条件 |
| --- | --- | --- |
| P0 基线与合同 | 现有样本、结构假设、可复现请求记录 | 基线冻结，行为不变 |
| P1 纯规则解耦 | 校验从旧阶段形状解耦，结果和错误语义保持 | 现有全仓与相关 race 通过 |
| P2 上下文与候选合同 | SceneFrame、SceneDraft、来源和预算的测试实现 | 仅在测试中调用，不进入正式链路 |
| P3 首次链路切换 | 集中生成、人物互动、节点应用、正文与 Output | 机制矩阵、旧档与来源回归、创作质量预检通过后，在同一发布边界替换旧调用 |
| P4 世界与兼容收口 | 到期安排、个人计划、旧节点、开放事件、旧存档 | 能力和版本矩阵通过，无双引擎 |
| P5 真实质量验证 | 同模型同材料的连续体验对照 | 授权恢复真实模型后执行，独立记录结论 |

P2 的测试函数属于同一 turn 实现，不创建一个可以长期选择的第二引擎。P3 与 P4 如果无法在单次切换中保持既有能力，就作为一个不可拆开的发布单元；不能让正式运行先失去世界推进或兼容能力。旧调用与测试中已过时的阶段次数断言在切换提交中直接替换。

P2 后设置创作质量预检：真实模型获准时，先用 E01—E04 的完整候选验证集中输出是否仍能写出自然互动，再投入正式切换。暂停期间继续纯规则与候选机制开发，但不把测试替身成功解释为质量预检通过。结构任务挤占创作时，优先减少重复字段和场景跨度，不增加审稿调用凑结论。

P0/P1 可以按本方案直接进入工程准备与规则解耦，P2 可开发最小集中候选。P3/P4 正式切换要求机制矩阵、旧档与来源回归通过，并完成获准的创作质量预检；暂停期间保留候选测试和机制开发，正式默认链路继续现行实现。P5 验证切换后的连续质量，不替代此前的开关门槛。

### 16.3 回滚

实施在独立本地提交中推进，通过 Git 保存旧实现。工程阶段遇到失败，修复当前单元或回到切换前提交，不保留长期运行开关。基准对照在分别启动的历史修订和新修订中使用独立 fixture 数据目录，不共用用户世界库。

未执行不可逆存储迁移时，可以切换代码继续读取旧格式数据。新旧版本续玩兼容须由重启与存档测试确认，不能仅凭“数据库结构没改”推断。没有通过兼容测试的新版本只操作测试世界。

## 17. 质量验收

真实模型暂停继续有效。未恢复授权时只交付机制与待验证项，不以人工示例、测试替身或静态截图替代真实质量结论。

| 维度 | 观察内容 |
| --- | --- |
| 连贯性 | 回应承接前文，较晚反应不引用尚未发生的结果 |
| 意图完成度 | 完成已授权的普通步骤，明确未执行部分 |
| 人物区别 | 两人目标和态度可辨认，拒绝不被改成配合 |
| 开放性 | 能产生有依据的新处境，不强制走固定路线 |
| 节奏 | 有效变化与表达匹配，重复描述减少 |
| 玩家控制 | 没有擅自重要承诺、花费或风险选择 |
| 世界一致性 | 下一轮、重启和另存承接时间、位置、钱物、计划 |
| 信息边界 | 私人内容没有直接进入第三人记录或玩家旁白 |
| 恢复质量 | 失败没有半轮后果，重试不重复执行 |

对照使用相同模型、参数、冻结内容、设置与创作自由度。旧版得到等价正向创作提示后再比较，避免用受限旧链路和开放新链路证明架构优劣。不能公平对应的差异单独列出。

指标以样本的具体成立/部分成立/不成立及文本、事件证据表达。等待记录包含所有串行请求和纠正；输入/输出记录区分估计与 Provider 实测。token 与费用作为诊断，不凌驾于故事质量。

具体场景、评分与收口条件见[实施与验收计划](plans/集中创作迁移-实施与验收计划.md)。

## 18. 风险与范围

| 风险 | 首版处理 | 何时重新评估 |
| --- | --- | --- |
| 人物为剧情服务、同质化 | 核心动机与冲突材料，拒绝和互相回应样本 | 连续对照仍缺乏差异 |
| 共享秘密影响不知情者 | 个人来源、投影、正文视角与真实场景评估 | 泄漏频繁影响玩法，需缩小主持资料范围 |
| 一次输出任务过多 | 无全量末态、无冗长逐人记忆，普通场景预算 | 结构正确但故事质量持续下降 |
| 正文与状态矛盾 | 节点关联、能力校验、钱物与场景证据 | 重大矛盾频繁，先改合同再考虑额外验证 |
| 关键材料漏选 | 完整因果组、约定检索、一次补充读取 | 长历史反复丢失关键依据 |
| 世界安排被忽略 | 时间窗口、候选资格、强制边界和进度校验 | 长等待跨事件无法保持顺序 |
| 旧合同与新设计混淆 | 当前架构和拟调整分别标明，切换时同步事实源 | 代码已经变更而文档仍宣称独立人物调用 |

本阶段聚焦集中场景创作及其必要上下文、校验和兼容。全城后台模拟、长期双引擎、动态重要人物、普通玩家创作页面、PNG 卡片运行、完整经济模拟、新地图和 UI 重做均不进入首次迁移。产品入门是否更容易另以实际玩家流程评估，模块更多不作为质量证明。

## 19. 运行机制取舍

WIA 的区别体现在完整行动承接、角色经历的来源、权威世界状态和可靠续玩。SillyTavern、pi、DeepSeek Harness 与 Hermes 的实际能力及边界见[资料评估](reference/Agent运行机制-资料评估.md)；这些区别不等同于已证明的剧情质量优势。

| 参考机制 | WIA 落点 | 首次迁移范围 |
| --- | --- | --- |
| 应用材料到模型消息的明确转换 | 第 6 节分区、owner、授权与统一预算 | 调整现有 ContextComposer |
| 同一 Agent 按需补材料再继续 | 第 3 节的读取、判定与一次纠正 | 有界场景循环，常规一次核心创作 |
| 近期原文、来源摘要与原事件保留 | 第 6.5/11 节的个人视图 | 复用现有 memory 与 archive |
| 重点记忆与可定位的旧原文 | 第 6.5.1/6.5.2 节的分层与完整因果组 | 深化既有召回合同，长历史索引后置评估 |
| 已完成事项与仍有效承诺分别表达 | 第 6.5.3 节的摘要与世界时间 | 调整现有摘要职责，不增加状态种类 |
| 有界整理与安全发布 | 第 6.5.4 节的完整候选与版本校验 | 复用摘要维护和重建调度 |
| 稳定职责、动态状态与可观察请求 | 第 6.8/7 节的选择报告与计量 | 复用诊断，不建设全文审计或持久上下文服务 |
| 未开始、已失败、结果未知分别处理 | 第 12 节与现有 run 恢复 | 保留原子提交与安全重试 |

开放式工具循环、Cordis 插件运行时、编码工具、自修改、默认多 Agent、JSONL 会话树替换存档均不采用。语义召回、实际 usage 自适应预算和运行中 steering 需要新的体验证据再单独评估，不作为本阶段开工依赖。
