# Story Pack v3 与基础世界能力技术方案

状态：**阶段 A、B、C 已通过工程 CR；真实模型连续游玩与默认内容切换仍待验收。**

核对日期：2026-10-01。代码基线：`4008a8b`。

本文定义 Story Pack v3 的剧本接入合同、数据设计、实施顺序和验收要求。加载器与运行时现已支持阶段 A、B、C 交付的 v3 能力；真实模型体验与默认内容切换状态以[开发状态](开发状态.md)为准。

现行架构与依赖约束以 [ARCHITECTURE](../ARCHITECTURE.md) 为准，产品范围以[产品说明](产品说明.md)为准，已交付能力以[开发状态](开发状态.md)为准。本文获得确认后，实施时同步对应事实源；本草案不将拟议能力记为已交付。

## 1. 交付目标与范围

新剧本作者能够通过固定格式提供世界、地图、人物及开局材料，选择 WIA 已支持的状态和规则能力，经过校验后创建独立存档。同类剧本接入主要修改数据；需要新机制时，先实现通用能力，再允许剧本声明使用。

《雾都余烬》是首个完整接入样本。正式游玩内容向这个有限场景收敛：少量相连地点、作者预设的重要 NPC、一宗失踪案、一件异常物品。具体地点和人物名单在阶段 A 定稿，文稿中的 8～12 个地点、全部成长设想不自动进入首版。

本轮边界：

- 地点与重要 NPC 由剧本预设，游玩时不生成新的持久地点或重要 NPC；路人不能升级为 NPC。
- 预设 NPC 保留自主决定能力。背景人群可以有情境反应，临时称谓不创建独立 Agent、状态或个人记忆账户；关键证人、物品持有人等需要跨轮追踪的身份必须预先定义。
- 世界通过玩家行动、等待与游戏内时间推进；浏览、刷新、重启和现实离线时间不推进世界。
- 首版不包含全城模拟、完整职业经济、完整超凡晋升、复杂战斗、任意插件、脚本或公式语言，也不建设面向普通玩家的创作界面。
- 地图、状态、关系和判定均为通用能力。产品代码和通用提示词不根据剧本 ID、人物名或银镜名称分支。

## 2. 当前基础与设计裁定

| 项目 | 基线事实 | 本方案裁定 |
| --- | --- | --- |
| 外部包与运行定义 | `content.StoryPack` 与 `story.Definition` 已分离 | 保持作者合同与运行结构分离，不直接把 JSON 类型传入回合引擎 |
| 包格式 | 支持 v1/v2，严格字段与引用校验，修订摘要登记 | 新结构采用 v3；按已实现能力逐步开放，不一次承诺全部玩法 |
| 地点 | 已有地点连接、初始位置和 `scene_location`；运行人物仍使用 `in_scene`，部分地点从场景文字匹配 | 阶段 A 建立位置权威，同场从位置派生；正文不承担位置更新 |
| 状态 | 已有资料、经历和记忆，尚无通用数值状态及状态变化记录 | 阶段 B 建立定义、初始值、运行值和可见投影 |
| 事件 | 已有 `plot` 条件节点、生成事件和受刺激的场外人物响应 | 沿用同一套事件推进，逐步接入位置与状态条件 |
| 回合可靠性 | 模型在事务外，提交前检查版本；场景校验有一次纠错及字段诊断 | 新能力进入同一回合工作区和最终提交，不另建提交链路 |
| 存档 | 定义与资源冻结，每世界独立数据库，支持另存与恢复 | 新状态、位置及判定事实必须进入相同存档边界 |

代码核对入口：[外部包字段与加载](../../backend/internal/content/packs.go)、[运行定义与地点匹配](../../backend/internal/story/types.go)、[人物运行状态](../../backend/internal/world/world.go)、[场景协调](../../backend/internal/turn/coordinate.go)、[最终提交](../../backend/internal/app/store.go)。

需要特别约束的设计选择：

1. **声明状态不等于实现机制。** 定义 `pollution` 只能建立一种状态；污染来源、累积、抵抗和后果需要另有受支持的规则。
2. **合法数值不等于合法变化。** “在范围内且有事件 ID”不足以授权扣款、移动或修改 NPC 态度。
3. **关系有方向。** `艾琳 → 玩家 → trust` 与 `艾琳 → 亚瑟 → trust` 独立保存；第一版只实现人物之间的关系，不预建组织系统。
4. **v3 不等于全模块同时交付。** 基础字段固定，可选模块按能力声明加载；没有实现的模块必须拒绝，不能静默忽略。
5. **空间和基础状态先于复杂玩法。** 银镜、交易和检定在这些事实能够可靠持久化后接入。

## 3. 四层数据合同

| 层 | 保存什么 | 谁产生和使用 |
| --- | --- | --- |
| Author Pack | 元信息、作者设定、定义、初始值、能力要求及参数 | 作者填写，`content` 加载、校验和归一化 |
| Runtime Definition | 已校验的地点图、固定人物、状态定义、规则参数与事件定义 | `story` 表达，创建世界时冻结，运行期只读 |
| World State | 实际位置、状态值、物品归属、关系、事件进度及变化记录 | 回合产生候选结果，程序校验，世界事务提交 |
| Engine Capability | 程序已实现的移动、状态更新、物品转移、判定等行为 | 产品代码提供固定能力和版本，不能由包注入实现 |

例如 `fatigue` 的定义为整数 0～100，某人物初始值为 25，当前存档值为 63。运行时更新 63，不修改作者文件中的 25；更换包修订不影响已有存档。

能力名称与版本是编译进程序的有限清单，不做动态模块装载。未满足的能力要求应在创建世界前报告，并定位到包字段。

### 3.1 实体引用合同

运行事实使用统一的 `EntityRef` 语义，沿用现有稳定 ID。引用在当前世界内解析；跨世界记录以 `world_id + entity_id` 区分，不能仅凭相同字符串引用另一个世界的人物。

| 引用 | 存在依据 | 阶段 A 位置 | 阶段 B 属性状态 |
| --- | --- | --- | --- |
| `player` | 每个世界唯一的玩家身份 | 支持 | 支持 |
| `npc:<id>` | 当前世界冻结定义中的重要人物 | 支持 | 支持 |
| `bystander:<id>` | 当前世界冻结定义中的稳定背景实体 | 支持 | 首版不支持 |

统一校验同时检查格式、实体实际存在、世界归属与能力适用范围。合法前缀不代表实体存在；`definition_id` 标识初始模板，不替代运行实体 ID。临时称谓不产生实体引用。事件中的 `world` 等系统来源不是物理实体，不能成为人物位置、属性状态或物品持有人的引用。

位置、属性、后续关系和物品持有人共享身份解析，各能力另行限定允许的实体类别。实体引用不自动授予事件接收或个人记忆资格。身份合同与纯校验沿用现有领域模块，不要求增加实体总表或新 package。

## 4. 作者接入合同

### 4.1 包内容

首版继续采用 `story.json`、`npcs/*.json` 与可选 `assets/`。先固定逻辑结构，不为每个概念另造文件协议。

| 区块 | 内容 | 必填与边界 |
| --- | --- | --- |
| 身份与介绍 | `schema_version`、`game_id`、`revision`、`title`、`description`、`gameplay`、`mode`、可选 `genre` | 基础身份与介绍必填；本轮正式样本为 `open`；题材标签不决定程序分支 |
| 世界材料 | `background`、`rules`、`author_facts` | 公开背景、设定规则、作者秘密分别保存；文字规则不替代程序约束 |
| 开局 | `opening`、`clock`、`initial_location`、`player` | 沿用游戏日与时分；顶层 `initial_location` 是玩家初始地点的唯一来源 |
| 地图 | `locations` | 至少一个可进入的 place；区域只组织地点，不作为人物位置 |
| 人物 | `npcs` 引用、`bystanders` | 重要人物均预定义；有持续作用的背景实体必须具有稳定 ID |
| 状态 | `state_definitions`，玩家和 NPC 的 `initial_state` | 可选；声明即要求状态能力；未提供的初始值使用合法默认值 |
| 能力要求 | `requires` | 能力名到正整数合同版本的映射；加载器核对区块实际需求，拒绝漏报、重复键与未知能力；执行版本见第 9.1 节 |
| 事件与表达 | 已有 `plot`、`event_generation`、`defaults` | 均按当前能力校验；开放型可以有条件事件，不要求结局 |
| 后续玩法 | 关系、物品、判定的定义与初始值 | 关系与物品在阶段 B、判定在阶段 C 交付后才能在正式包中声明 |

`schema_version` 是文件格式版本，`revision` 是内容修订，能力版本是规则合同版本，三者分开。相同内容修订不能被悄悄替换；影响结算语义的规则更新也不能通过重启无声改变旧世界。

人物文件保留现有身份、公开外观、私有资料、已知信息、初始关切与说话示例，增加能力需要的初始状态。秘密身份不得写入公开 `role` 或目录介绍。长期目标和性格先用现有私有资料表达，暂不为每一种心理概念建立数值。

### 4.2 地图与状态的拟议字段示例

以下是局部示例，不是可直接加载的完整包：

```json
{
  "schema_version": 3,
  "game_id": "mist-embers",
  "revision": "mist-embers.pack.v1",
  "title": "雾都余烬",
  "mode": "open",
  "genre": ["都市", "神秘调查"],
  "requires": {"spatial": 1, "state": 1},
  "initial_location": "office",
  "locations": [
    {"id": "district", "kind": "region", "name": "调查区域"},
    {"id": "office", "kind": "place", "parent": "district", "name": "事务所", "connections": ["street"]},
    {"id": "street", "kind": "place", "parent": "district", "name": "街道", "connections": ["office"]}
  ],
  "state_definitions": [
    {
      "id": "fatigue",
      "name": "疲劳",
      "type": "integer",
      "min": 0,
      "max": 100,
      "default": 0,
      "scope": ["player", "npc"],
      "projection": "self",
      "knowledge": "owner",
      "update_policy": {"kind": "bounded_proposal", "max_change_per_turn": 10},
      "description": "当前疲劳程度"
    }
  ],
  "player": {"name": "调查员", "editable": true, "initial_state": {"fatigue": 18}}
}
```

示例中的地点、初始值和变化上限仅演示格式，不是《雾都余烬》的内容定稿。`bounded_proposal` 是明确授权的有限模型提案策略；默认更新策略为只读，见第 6 节。

### 4.3 接入流程与错误

1. 复制最小模板，填写稳定 ID、介绍、公开设定及作者事实。
2. 配置地图、固定人物、开局位置和各人的初始知识。
3. 选择已支持能力，填写定义、初始值和规则参数。
4. 配置条件事件和受限生成范围；没有新事件生成需求时省略该区块。
5. 执行现有加载校验链：格式、资源、跨文件引用、能力、初始值与运行定义一致性。
6. 创建新测试存档，验证启动、移动、私聊、状态变化及另存重启。
7. 发布不可变修订，目录仅公开介绍与获准资源。

错误应包含文件、字段路径、稳定错误码和预期约束，例如 `npcs/reporter.json: initial_state.fatigue: state_out_of_range`。坏包不进入新建目录，其他包和已存在存档的读取不受影响。沿用现有开发者校验入口，本阶段不另建编辑器或迁移工具。

## 5. 空间状态（阶段 A）

### 5.1 地点与位置

- `region` 和 `place` 两级；place 可没有 region，region 不嵌套 region。
- 连接是 place 到 place 的显式有向边；双向通行声明两个方向。
- 首版不增加坐标、自由寻路或通用交通规则。玩家可直接表达目的地，模型提出路线，程序逐段验证连接。
- 玩家、重要 NPC、预定义稳定背景实体按第 3.1 节统一引用，各有一个当前位置。新 v3 世界创建时要求全部指向合法 place；位置表是唯一运行权威，场景文字仅作投影。存量缺失位置按第 9.2 节处理。
- `in_scene` 可以作为接口派生字段保留，计算为双方具有明确位置且处于同一 place；空值或未知位置不参与相等判断，不再独立接受模型生成的在场名单。
- 首版不配置另一套移动计时引擎，耗时沿用有界游戏时间协调；固定路程耗时规则作为后续能力，不假设连接本身已经定义时间。

### 5.2 回合中的移动

移动候选至少包含实体、起点、实际到达点、所经路线及已确认行动来源。程序验证实体存在、起点匹配本轮阶段快照、目标为合法地点、路线连通、行动归属与结果成立。

玩家移动必须来自已表达的意图；NPC 移动必须来自本人决定或已定义的外部事实，不能因玩家说“他跟着我”就视为该人物同意。失败留在原地、途中停在已定义地点，均是可提交的游戏结果。

各阶段根据当时位置授予感知，后续移动不回填此前对白。传话、电话等远程获知仍依赖独立事件来源。同场只表示获得感知的资格，不自动授权私聊、秘密或所有行动结果。

空间状态随事件、感知、正文和时间一起提交。停止从 `scene` 文本推断当前地点，初始位置只用于创建世界。前端提供当前位置和允许展示的相邻地点，隐藏地点不通过完整地图数据泄露。

## 6. 通用状态（阶段 B）

### 6.1 定义与投影

首版类型限定为整数、布尔与枚举。数值需要小数时使用明确最小单位，例如货币内部保存整数便士；单位和显示名称属于定义，不根据剧本名称硬编码。

状态定义包括 ID、显示名、类型、范围或枚举、默认值、适用对象、玩家投影权限 `projection`、角色访问权限 `knowledge`、更新策略和简短说明。两个权限字段均显式填写并分别校验。首版只支持玩家和重要 NPC 的属性状态；全世界变量与关系分别在后续单元接入，不先做任意键值容器。

`projection` 决定玩家 API 与界面能否展示原值：

| 值 | 玩家投影 |
| --- | --- |
| `self` | 仅允许展示玩家自身的值；不返回 NPC 的值 |
| `public` | 允许展示玩家与 NPC 的值，但仍要求实体与该状态已获准在当前玩家视图中展示 |
| `hidden` | 不向玩家 API 或界面返回原值 |

`knowledge` 决定原值进入角色材料的资格：

| 值 | 角色访问 |
| --- | --- |
| `owner` | 状态所属人物可以读取；其他人物只能根据获准来源形成自己的认识，不能直接读取其当前原值 |
| `public` | 允许作为可观察信息提供，仍按接收者、发生时位置、感知来源与调用用途筛选；不全世界广播 |
| `host_only` | 原值不进入角色认知材料；只有执行相关规则所必需的协调用途可读取 |

所有状态的规则执行材料均遵循用途最小化，`host_only` 不要求每次主持调用都注入该值。玩家界面展示本身不产生人物感知事件，人物的观察、转述和症状认识也不自动开放玩家 API 的精确值。

| 状态示例 | `projection` | `knowledge` | 含义 |
| --- | --- | --- | --- |
| 疲劳 | `self` | `owner` | 玩家看到自身数值；NPC 可使用自身数值作决定 |
| 自知但界面隐藏的状态 | `hidden` | `owner` | 界面不显示，所属角色材料可以使用 |
| 本人也不知精确程度的污染 | `hidden` | `host_only` | 规则读取原值；人物只获知有来源的症状 |

这里的“自身”指世界中的实体，不是账户所有者。用户拥有世界，不代表能读取所有 NPC 私有状态。可见症状、人物行为和原始数值分别投影；人物获知一次旧值，也不因此永久获得实时读取权限。

状态栏只展示服务端已过滤的定义与当前值，不下载完整 NPC 状态后用前端隐藏。阶段 B 不增加玩家任意改值入口或 NPC 全量状态面板。

### 6.2 变化权限

状态更新合同见[模型主导的可选能力模块](stages/模型主导的可选能力模块.md)。`model` 支持模型决定整数、布尔、枚举变化；`bounded_proposal` 保留作者明确声明的整数预算；`rule_only` 由固定规则更新；`readonly` 保持初始值。程序保存来源、校验类型和定义范围，并在最终事务中提交。

普通行动的因果关系由模型判断。人物有向关系由主体本人依据获准经历提出，协调器采用本人提案。物品实例保持唯一归属，模型决定交付、拾取等结果，程序按变化顺序应用。

## 7. 关系、物品与规则能力（阶段 B、C）

| 能力 | 首次交付要求 | 当前不扩展到 |
| --- | --- | --- |
| 有向关系 | `subject + target + relation_type` 唯一；有范围、来源、主体决策权限和私有投影 | 图数据库、组织关系模拟、自动人格重写 |
| 物品 | 定义与实例分离；关键实例只有一个当前位置或持有人；转移校验归属和授权并原子完成 | 装备词缀、复杂合成、全套经济系统 |
| 风险判定 | 固定一套受支持规则；模型提议行动，程序验证参数、产生随机结果并记录，正文消费确定结果 | 任意公式、模型自报骰点、完整战斗流程 |
| 世界计划 | 沿用 `plot`，到期后根据实际位置、物品、状态及人物决定评估；条件不成立可推迟或取消 | 独立事件引擎、离线全世界模拟 |

阶段 C 使用的判定规则必须明确骰型、阈值、修正来源、失败后果、行动身份与重试范围，作为阶段 B 交付时的下一阶段输入集中确认。稳定输入 ID 已有基础，但仅绑定 `run_id` 或模型临时生成的 `action_id` 不足以防重试换结果。

同一输入下同一已确认行动需具有程序确定的判定身份；取消、修复、网络重试不能重新随机或重复扣费。判定准备记录与已发生世界事实必须区分，世界后果仍只在最终事务成功后成立。具体随机复用与恢复策略在阶段 C 内先确定再实现，随完整模块一并审查，不把“未来补幂等”作为可玩版本交付。

计划不等于事件；配置允许某人物接收事件，也不证明他实际获知。沿用事件投影与个人感知机制授予知识。生成事件只能引用已定义地点和人物，保留现有活跃数、冷却及单轮推进上限。

## 8. 运行、持久化与纠正

### 8.1 接入现有主流程

实现落点遵循现有架构：`content` 扩展包校验和归一化，`story` 扩展冻结定义，领域记录与纯校验进入 `world`，回合材料与执行进入 `turn`，事件规则沿用 `plot`，数据库变更进入 `storage`，最终提交沿用 `app.commitTurn`。不新增并行的回合流程，也不把每个模块都包装为 Service。

回合开始时，从已提交世界快照构造独立的回合工作态（Turn Working State）。既有事件与感知暂存机制、位置、属性和后续物品关系变化使用同一阶段接受边界；不另建并行执行流程，也不要求创建通用工作态框架。

1. 每个阶段基于当前已接受工作态生成候选结果。候选中的依赖效果按确定顺序在隔离副本中计算，整组校验通过后一次性应用。
2. 阶段被拒绝或进入纠错时，候选修改全部丢弃；纠错从相同的阶段输入重新生成，不保留先成功的部分效果。
3. 后续阶段的位置、状态值、同场候选、场景投影与上下文材料读取更新后的工作态，不回读数据库旧值或始终使用回合初值。
4. 已发生事件保留发生时的阶段位置、接收者资格与来源快照；后续移动不回算历史感知。工作态是世界事实，模型材料仍按用途与接收者过滤。
5. 正文只表达已校验、拟提交的玩家可见结果。最终由 `app.commitTurn` 在短事务内校验运行状态、`context_epoch`、`scene_version` 等版本，并原子提交确定性增量及其事件来源。

所有模型调用在事务外。工作态不直接持久化；叙述失败、取消或最终版本冲突时，丢弃整轮候选世界变化。既有运行诊断、模型用量记录及第 7 节的判定准备记录不等于已提交世界后果，按各自保存合同处理。

阶段 A、B 新增的逻辑记录如下，物理表与具体索引在对应模块实现时收敛：

| 记录 | 最小内容 |
| --- | --- |
| 实体位置 | 实体 ID、地点 ID、确认来源、版本 |
| 当前状态 | 实体 ID、状态 ID、类型化值、版本 |
| 状态变化 | 唯一变化 ID、实体与状态、前后值、来源事件、回合和顺序 |

变化记录有程序控制的唯一键，避免一次纠错后追加两份效果。同一回合多次变化按确定阶段顺序折叠，校验读取对应阶段值；不能全部拿回合开头的数值重复结算。

### 8.2 另存、重启与纠正

- 新字段、初始基线、变化记录、能力版本及后续判定记录都属于世界存档；另存复制完整状态，后续写入互相隔离。
- 包文件不是存档；读取与重启不得重新套用作者初始值。
- 现有记忆纠正不等于世界状态回滚。描述性纠正继续按其原有范围生效。
- 对会使位置、状态或判定依据失效的纠正，必须先识别依赖；在相应重建能力完成前，原子拒绝该项影响世界事实的纠正，明确说明限制，不能先失效来源却保留已失去依据的数值。
- 本轮不以事件溯源方式重写全部存储。未来若支持这类重建，需从保存的基线及有效变化重算，禁止靠摘要或正文猜测余额、位置和骰点。

上述纠正限制是新增结构化事实的兼容边界，需要在阶段 A、B 验收中覆盖，并在玩家提示中说明；不把现有全部记忆纠正功能关闭。

## 9. 版本、旧包与旧存档

### 9.1 格式与能力演进

v1/v2 包保持可解析，外部格式差异归一化在 `content`，正常 Turn 不按包版本分支。既有平面地点可以归一为 place；旧包未声明的状态不会被补造。格式转换不证明旧存档具备了运行位置。

既有合同将旧版连接定义为提示语义，不能通过格式归一化直接赋予 v3 的强制路线约束。旧包可解析、旧档可读取与可按新空间合同继续推进分别验收；启用新约束必须有明确的规则迁移。未确认迁移前，不自动为旧世界填入 `spatial: 1`。

v3 加载支持与每个能力一同交付。未知字段、未知能力、声明但未支持的模块，以及不满足依赖的组合均拒绝。可选模块可以省略；一旦填写，必须具备实际执行语义。规范与实现支持清单同步更新。

**能力版本是行为合同版本，不是程序构建版本。** Author Pack 的 `requires` 指定确切合同版本；加载器验证声明、模块使用及内置依赖的一致性，创建世界时冻结实际采用的能力清单（resolved capability manifest）。清单包含所需依赖及其确切版本，随世界另存、导出与恢复，不在每次启动时按最新包重算。

| 运行程序与存档合同的关系 | 行为 |
| --- | --- |
| 支持已冻结合同 | 按该合同运行；实现优化和缺陷修复仍须符合合同 |
| 需要改用新合同，且具有明确迁移 | 显式迁移数据与规则，验证成功后原子更新状态及能力清单 |
| 不支持已冻结合同，且无适用迁移 | 保留原档，报告不支持的能力与版本，拒绝开始新回合；历史读取与导出按各自格式兼容性处理 |

迁移失败保留原合同和原状态；任何规则升级均不得仅修改清单而跳过数据与行为检查。首版只交付实际实现的合同及必要迁移，不预建多版本执行框架。既有世界缺少能力清单时，通过识别其原有语义的迁移处理，不能把缺项解释为采用最新版本。

### 9.2 存量位置迁移

旧档只有 `in_scene` 和部分场景资料，无法据此确定每个场外人物现在的位置。初始位置和正文关键词不能作为已推进世界的静默回填依据。

现行[总体技术方案第 4.2.1 节](总体技术方案.md#421-位置与同场)规定旧档无法确认的位置保留未知；产品说明与开发指南也包含“未知位置不视为同场”的要求。这些合同在新决策确认前保持有效。`unknown` 表示缺少位置事实，不是地点，两个未知位置不会因此同场。

本方案要求新建 v3 世界具有完整位置。对于有缺项的旧档，以下处理仍待确认：

| 策略 | 对续玩与实现的影响 |
| --- | --- |
| 延续现行未知位置合同 | 旧档保留未知；所有依赖位置的移动、感知与事件须明确处理缺项，不能猜测路线或同场 |
| 进入新空间合同前明确补全位置 | 需要可核对的补全流程；未完成时不得报告已具备新空间合同，须明确升级期间的续玩安排 |
| 保留历史读取与导出，另开新世界 | 改变旧档续玩承诺，必须由用户明确选择并确认读取、导出可用 |

**建议先在独立数据根完成 v3 新世界开发与验收。默认环境升级前，提交位置缺项、旧连接语义和对应迁移策略清单供 CR。** 选择替代现行未知位置合同的策略时，同步修订总体技术方案、产品说明与开发指南中的相关约定；历史验证记录保持原样。更换正式剧本不构成删除旧档或放弃旧档续玩的授权。

迁移先备份，识别有可靠依据的位置，按确认后的合同完成一致性检查，再在事务中发布迁移版本。缺失依据如实列出，不把格式转换完成当成全部运行约束已满足。迁移失败保留原库；成功迁移与另存、重启、纠正的交互必须有回归。

不以长期保留两个位置引擎解决迁移问题。迁移归存储边界，运行时只保留一套位置语义。

### 9.3 两份旧示例的处置

目标是将新游戏目录和默认安装内容收敛到《雾都余烬》。需要同时检查内置示例、本机已安装包、公开文档与测试引用。

新样本验收通过后再执行内容切换。原样本中的有效机制测试保留或转换为最小测试夹具，不继续维护两个正式内容包。用户目录中的已安装包、已有世界和导出文件不随源码包删除；实际处置清单单独确认。

## 10. 实施计划与 review 节点

### 10.1 三个模块阶段

实施按 A → B → C 顺序进行，每个阶段交付一个完整模块，由用户 CR 通过后进入下一阶段。本文的合同设计是开工依据，不另设文档阶段；剧本准备、数据设计、后端、必要前端、回归和自查均纳入所属模块。

| 阶段 | 完整模块 | 完成后可实际验证的结果 | 用户 CR 重点 |
| --- | --- | --- | --- |
| A | 剧本接入与空间世界 | 新 v3 样本可以创建世界、交流、移动、离开与返回，人物位置和感知正确，另存重启保持一致 | 作者格式、地图与固定人物、位置权威、阶段工作态、旧档兼容边界 |
| B | 人物与物品状态 | 玩家和 NPC 有持久状态，有向关系影响本人决策，物品可按权限持有与转移，玩家看到获准状态及物品信息 | 状态授权、两类权限、关系方向、物品唯一归属、原子结算与恢复 |
| C | 规则与世界推进 | 风险行动由程序判定，事件按游戏时间与实际条件发展，《雾都余烬》完成连续游玩与恢复验收 | 判定幂等、失败后果、事件因果、NPC 知情、真实体验和默认内容切换 |

阶段是交付与人工审查边界，不等于一次巨大提交。开发 AI 可以内部拆任务并按仓库授权保存小步提交，持续运行匹配测试和内部 CR；不为每个字段、文件、接口或前后端子任务另设用户验收点。模块内修复完成后统一交付，用户 CR 的问题修复仍归本阶段。

### 10.2 阶段 A：剧本接入与空间世界

完整交付范围：

- 将《雾都余烬》的有限场景整理为地图、固定人物、开局、核心事实与知情表；银镜规则及不介入时间线形成内容设计，标明其后续能力依赖。
- 落实 v3 基础作者合同、最小模板、加载校验、运行定义归一化、实体引用与能力清单。样本只声明当前可执行能力，未来玩法留在设计材料，不用无效字段或虚假效果占位。
- 实现空间状态、结构化移动、同场派生、阶段感知及回合工作态，覆盖主流程和已有事件、场外人物响应路径。
- 完成存储、提交、另存重启、相关纠正边界与最小位置展示；世界创建后直接进入现有游玩流程。
- 在独立数据根验证，提交旧档位置缺项、连接语义和迁移策略清单；未经确认不升级用户默认数据根。

完成判据：第 11 节的接入、实体、空间、阶段工作态及对应存档回归通过；用实际界面完成新建、交流、移动、返回和重启。位置不再由正文解析或模型在场名单决定。此阶段样本用于验证接入和空间，不声明完整调查玩法已经交付。

交付后进行 **CR-A**。同时集中确认影响后续范围的内容缺项和旧档策略，未决旧档策略阻塞默认环境升级，不阻塞独立数据根中的阶段 B。

### 10.3 阶段 B：人物与物品状态

完整交付范围：

- 一次完成属性状态的定义、初始化、当前值、变化权限、结构化来源、整轮预算、记录与恢复。
- 完成玩家投影和角色认知权限、上下文裁剪，以及玩家状态栏和获准的 NPC 状态表达；数值实际参与后续决策。
- 实现人物之间的有向关系；关系变化依据主体的获准经历，进入其后续决策材料，不提供全量秘密关系面板。
- 实现样本所需的物品定义、实例、唯一归属和授权转移；银镜使用通用物品机制表达持有，其异常效果由阶段 C 的规则结算。
- 将属性、关系、物品统一接入已有回合工作态和最终事务，覆盖失败、重试、另存与纠正依赖。提供必要的玩家可见物品信息，不扩展复杂背包或装备系统。

完成判据：使用同一套机制改变玩家与 NPC 状态，验证状态对后续行动材料的影响；通过一次有来源的关系变化与物品转移，检查私有值、归属、失败保持原值和重启一致性。相应作者字段、运行实现与界面共同交付。

交付后进行 **CR-B**。将阶段 C 所需的固定判定规则、阈值与修正来源、资源消耗和银镜后果作为同次 CR 的输入确认；实现细节由开发 AI 在该合同内完成。

### 10.4 阶段 C：规则与世界推进

完整交付范围：

- 实现已确认的一套风险判定规则，程序决定结果，保存稳定行动身份和可恢复的判定准备记录，技术重试不换结果或重复扣费。
- 将已确认的银镜及其他必要规则接入通用效果结算；规则由程序实现，参数由剧本声明，代码不根据剧本或物品名称分支。
- 扩展现有 `plot` 条件与推进，读取位置、状态、关系和物品事实，支持参与、拒绝、等待及条件被提前破坏后的结果。
- 衔接有限场外计划、NPC 本人决定与获准感知；计划、意图、实际结果分别处理。
- 完成样本所有本轮范围内的内容配置、必要的判定结果展示、连续游玩、另存恢复和直接受影响的回归。
- 准备默认内容切换、已确认策略下的旧档迁移与回退方案，在隔离数据上验证，供用户审阅后执行。

完成判据：第 11 节适用项目全部覆盖，真实模型连续游玩记录单独提供；缺少真实验证时明确待验证，不能仅凭测试替身宣布体验验收通过。

交付后进行 **CR-C**，合并工程与体验审查。通过后，在已授权范围内执行内容切换及迁移，不增加独立开发阶段；涉及用户数据且未授权的操作保留待执行状态。完成后停止本轮范围扩展。

### 10.5 开发 AI 的执行与交付合同

每次只委派一个完整模块，上一模块 CR 通过后再委派下一模块。开始时读取仓库 `AGENTS.md`、本方案、现行架构与开发状态，核对实际 HEAD 和工作树；本文代码基线用于识别设计依据，不能用于回退后续已验收成果。

模块内部先处理数据与执行依赖，再完成界面和验证，保持连续推进。常规实现选择由开发 AI 决定；只有改变产品范围、玩法合同、旧档续玩承诺或涉及未授权用户数据操作时集中提出问题。可独立完成的工作继续进行，不将内部拆解转为逐项人工审批。

每次 CR 交付必须包含：

1. 可运行的完整模块、启动方式及一条从入口走到结果的复现路径。
2. 实际变更范围、测试结果、内部自查结论；独立审查与真实模型验证如实注明是否执行。
3. 数据与格式兼容影响、迁移验证结果、已知限制和待确认项。
4. 对应公开事实源更新及适用的验收记录；未实现能力保持规划状态。

给执行 AI 的阶段 A 委派文本：

> 请按仓库 AGENTS.md 和 docs/phase12/Story-Pack-v3-技术方案.md 第 10.2 节，完整交付阶段 A「剧本接入与空间世界」。先核对实际代码与工作树，读取用户提供的《WIA_开放型剧本产品设想与诡秘之主测试剧本设计材料_v1.0.md》，在独立数据根中完成样本内容准备、v3 基础接入、空间运行、必要界面、存档及相关验证。按第 10.5 节提交完整 CR 材料。内部自行拆解与连续实现，模块完成后停止等待用户 CR，不提前开发阶段 B、C。缺少内容原件时先索取或定位原件，不臆造已确认设定。不得修改用户默认数据根或自行 push。

## 11. 验收矩阵

| 领域 | 必须覆盖的场景 |
| --- | --- |
| 作者接入 | 最小合法包；缺字段、重复 ID、未知能力、错误版本、非法初始值、跨文件错误引用；错误能定位 |
| 实体引用 | 玩家唯一；合法前缀但实体不存在、跨世界误用、系统来源充当人物、路人写属性均拒绝；位置与状态使用相同身份校验 |
| 阶段工作态 | 接受移动后下一阶段读取新位置；多次变化按顺序结算；阶段内一项非法则整组不生效；纠错从原阶段输入开始；最终失败不提交候选变化 |
| 通用性 | 使用另一份最小测试夹具替换世界名称、地图、人物和状态定义，无需修改产品代码；不增加第二份完整正式剧本 |
| 空间 | 移动成功、拒绝跟随、停在中途地点、非法路线；人物离开后不再接收后续私聊，返回不补收历史 |
| 状态 | 初始值与当前值分离；整轮变化上限；无权限更新、无来源或无效来源拒绝；模型自报作用范围不构成授权；旁观身份不授权改值；重试与重复来源不重复结算 |
| 私有信息 | 覆盖 `hidden + owner`、`hidden + host_only`、`self + owner` 和 public 的来源限制；API 展示不授予人物知识；历史感知不随最新位置变化；错误与普通日志不暴露私有值 |
| 版本兼容 | 能力清单冻结并随另存恢复；缺失清单不采用最新规则；不支持版本时不推进；迁移失败保留原档；旧版提示连接不自动变为强制路线约束 |
| 关系与物品 | 主体和目标区分；关系变化有本人感知依据；银镜唯一归属；转移失败保持原持有关系 |
| 判定 | 不确定行动才判定；重试不换骰；失败结果可以正常提交；取消和重启不重复扣资源 |
| 计划与事件 | 参与、拒绝、等待、提前破坏条件；计划不记为事实；到期事件只向实际获知者投影 |
| 存档与纠正 | 另存、退出重启、切换世界、提交冲突、纠错失败；新状态与来源保持一致；受影响的纠正不会留下半成品 |
| 真实体验 | 包含调查、普通交流、移动、一次风险、状态变化、拒绝事件、返回与重启的一段连续游玩 |

自动检查沿用项目要求：相关回归、全仓 `go test ./... -count=1`、相关包 race、`go vet`；涉及前端时执行类型检查、机制测试与正式构建。新增能力必须有端到端存档测试，不能只测 JSON 解析或界面渲染。

阶段 C 建议以至少 30 个已提交回合作为首轮持续性样本，记录人物/物品位置矛盾、状态回退、知情泄露、重复行动、模型调用数、修复次数与等待时间。次数是建议的验收规模，不代表达到该次数即可证明稳定。确定性边界必须通过；语义错误和延迟如实记录，由用户体验 review 决定是否可接受。

本轮完成后停止扩展模板市场、公式系统、完整地图编辑器等外围能力，后续新增机制以实际剧本需求为依据。

## 12. 当前需要确认的事项

| 事项 | 建议 |
| --- | --- |
| 首版模块范围 | 按接入与空间、人物与物品状态、规则与世界推进三个完整模块交付，各模块完成后由用户 CR；不把全部长期设想列为 v3 首次发布要求 |
| 模型修改状态的权限 | 采用 model、bounded_proposal、rule_only、readonly 策略；普通变化由模型判断，程序保证存档一致性，关系仍由主体本人提出 |
| 旧档策略 | 独立数据根开发；新 v3 开局位置完整；旧档未知位置沿用现行合同直至替代方案确认，默认环境升级前审阅位置与连接语义迁移清单 |
| 内容边界 | 阶段 A 定稿少量地点、固定重要 NPC、失踪案和银镜的内容材料；保持路人升级关闭，玩法按所属模块交付 |

通过本方案 review 只确认设计方向与上述范围。后续开发授权按用户下一步指令执行；当前交付不包含代码实现、旧内容删除或用户数据迁移。
