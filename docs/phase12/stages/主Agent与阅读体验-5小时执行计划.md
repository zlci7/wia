# 主 Agent 与阅读体验 5 小时执行计划

日期：2026-10-06。状态：待执行。范围依据[改进建议](主Agent创作与叙事体验-改进建议.md)；代码基线以执行开始时的 HEAD 为准。本轮规划与独立 UI 样稿准备不代表游戏运行逻辑已经修改。

## 1. 交付目标

在约 300 分钟预算内完成一组可验证的改进：检查独立 NPC 之间的互动衔接，增强已有主持的世界创作职责，改善已确认结果的正文表现，提高三项行动建议的细节与区分度，并提供三套本地静态 UI 供选择。

32 项评估作为参考，实际改动集中在下表。WIA 的产品与架构范围继续以[产品说明](../产品说明.md)、[架构方案](../../ARCHITECTURE.md)和[总体技术方案](../总体技术方案.md)为准。

| 工作项 | 交付 | 验收依据 |
| --- | --- | --- |
| NPC 互动衔接 | 四类多人因果场景、最早问题阶段与有证据的修复 | 实际请求、个人投影、行动结果和世界状态 |
| 主持创作 | 现有持续世界提示与两种题材的发展材料 | 外部变化有材料支持，重要 NPC 本人决定，旧状态保持 |
| 正文表现 | 表达任务和表现边界一致的提示合同 | 台词含义、态度、听众、时间与后续事实保持 |
| 三项建议 | 有对象、做法、目的的三种可尝试意图 | 保留现有结构和 120 字上限，只有玩家已知信息 |
| UI 候选 | 三套离线 HTML、桌面与手机截图、比较入口 | 同内容可比较；真实阅读、建议、输入与资料交互可试 |
| 回归与交付 | 匹配范围的测试、内部 CR、证据与本地提交 | 工程、真实模型、用户选择分别记录 |

## 2. 预算与执行顺序

| 时段 | 时长 | 工作单元 | 完成条件 |
| --- | --- | --- | --- |
| 0—30 分钟 | 30 分钟 | U0：工作区与因果基线 | 检查 HEAD、未提交变更、AGENTS；记录四类互动经过哪些阶段 |
| 30—105 分钟 | 75 分钟 | U1：NPC 衔接与世界主持 | 修复有证据的遗漏，明确主持创作任务，验证个人刺激与本人决定 |
| 105—140 分钟 | 35 分钟 | U2：正文合同与表达 | 收敛重复要求，保持本人态度，改善段落和结果呈现 |
| 140—165 分钟 | 25 分钟 | U3：行动建议 | 三项有合理细节与差异，权限、结构和版本回归通过 |
| 165—220 分钟 | 55 分钟 | U4：三套 UI 静态方案 | 保存比较页、单独 HTML 与六张基础截图，检查窄屏和资料交互 |
| 220—280 分钟 | 60 分钟 | U5：全量回归与 CR | 必需检查完成，证据和事实文档一致，完整单元可本地提交 |
| 280—300 分钟 | 20 分钟 | 收口缓冲 | 修复直接失败项，整理提交、实际结果与未验证范围 |

最后 80 分钟保留给验证与收口。第 220 分钟停止新增范围。工作单元在相关验证通过后即可本地提交，不必全部等到最后；不执行 push。

已准备好的 UI 样稿直接复用。U4 用于比较、适配用户反馈及补充缺少的验证，不重复生成同一批页面。没有新的 UI 反馈时，剩余时间优先用于 NPC 连续性和已有失败路径的验证；无需把预算全部消耗完。

## 3. U0：确认真实问题阶段

先查看当前输入、NPC 请求与决定、场景裁定、世界刺激、个人感知和正文。优先使用既有报告和受控测试，避免只根据最终文字推断缺陷。

四类必须检查的场景：

1. **甲拒绝乙。** 乙是否收到拒绝，是否在既有合适阶段作下一次决定；没有发生的回应不由正文补出。
2. **两人争夺同一物品。** 提案可以冲突，结果和归属必须成立；不能两人都成功持有同一个实例。
3. **NPC 行动失败。** 本人是否获得失败经历；后续计划可以改变，但计划不当作执行结果。
4. **两人私聊、第三人在场。** 第三人只获知实际公开内容与可见迹象，不自动理解私密内容。

记录“收到刺激但无反应”“没有收到刺激”“决定被错误裁定”“正文遗漏或改义”“本轮按边界合理结束”分别属于哪个阶段。当前第二阶段承接对白，不能据此假定所有行动结果都获得了下一次决策机会。

机制基线用受控响应证明材料、顺序和结算。真实模型暂停期间，人物为什么沉默、内容是否有趣等质量结论继续待验证。

## 4. U1：独立人物与主 Agent 的分工

### 4.1 优先完成的范围

- 在已有路径中修复刺激遗漏、旧状态覆盖、结果整合或范围检查的真实错误。
- 世界主持明确依据已提供的发展材料形成具体的新情境，允许发生、暂缓和跳过。
- 作者材料区分固定事实、当前压力、合理发展和信息传播条件。
- NPC 有当下可行动的关切，使用已有主动性与个人计划，不要求全员发言。
- 《雾都余烬》和非诡秘维修站共享通用机制，各自使用自己的材料。

### 4.2 因果衔接的实施边界

先充分使用既有增量回应、外部刺激和行动协调。如果问题属于已经应该执行却遗漏的路径，直接完成根因修复。

如果需要新增结果后的反应阶段，先明确一个具体场景的触发、实际接收者、最大次数、停止条件、共享时间预算及费用影响。不能用正文代作决定，也不能把本轮扩成可任意循环的对话引擎。此类新增行为纳入主计划确认的具体范围后实施；边界无法在预算内验证时，完成可独立交付的其他单元并记录缺项。

新增外部变化也不自动触发所有 NPC。只有实际获知且与事件相关的人适合进入对应决定请求。重要人物可以拒绝、沉默、继续原计划或提出新的尝试。

## 5. U2：正文表现

正文以已确认结果为依据，充分表现动作过程、关键对白和可见变化，合并重复信息，保持实际先后与公开／私密范围。

有性格、态度或情绪含义的语气、犹豫和表情由 NPC 本人输出支持；正文保留其原意，不能将拒绝写成动心，将失败写成成功，将沉默写成默认接受。表现性补写不能成为后续钱物、地点、知识或关系变化的依据。

保持现有三种篇幅、主角补写和 NPC 主动性设置。简单互动可以短，完整小场景是质量目标；新的重要选择、真实等待和合理阶段停点都可以结束本轮。

本单元对应修改 `composeNarration`、`DetailInstruction` 及必要的产品合同。只改自定义策略不能覆盖当前固定职责。

## 6. U3：三项行动建议

沿用一次辅助调用、`items` 三项字符串、程序单项 120 字上限、已有版本依据和失败状态。中文建议通常一至两句、约 35—70 字，作为软目标。

各项写清对象、做法与目的。参考观察核实、交谈试探和行动改变处境等参与方式，根据情境选择，不设固定保守／激进／推进槽位。差异来自实际参与方式，不给同一个问题换词。

建议保持第一人称意图，不预写 NPC 同意、任务结果或秘密答案。纵向布局沿用，点选进入可修改草稿，已有草稿不被覆盖。不给建议质量增加固定评分模型调用。

## 7. U4：UI 多方案探索

### 7.1 三套方案

| 方案 | 排版与视觉 | 适合比较的体验 |
| --- | --- | --- |
| A 蓝白书页 | 居中阅读列、宋体正文、冷白与蓝色；顶部紧凑资料入口 | 与现有品牌衔接、长文阅读、信息层级 |
| B 深色阅读 | 非对称阅读区域、等线正文、深墨与青色；底部常驻输入区 | 夜间阅读、操作可达性、正文可用高度 |
| C 暖色纸感 | 窄导航带、雅黑正文、米色与橄榄色；平静轻边界布局 | 长时间阅读、文字入口辨识度、窄屏重排 |

每套使用同一份演示故事、日期、建议和资料，区分字体、色彩和布局。演示内容明确标注为静态样稿，不读取用户存档，不冒充真实结算结果。

三项建议纵向排列；角色、背包、地图与人物按需打开；日期直接为世界年月日和时分；交谈对象与表达范围清楚；正文保持高对比底色。选择后才评估正式前端接入，本单元不改变当前游戏 UI。

### 7.2 设计研究依据

资料读取日期为 2026-10-06，以下是有公开依据的产品设计方向，不是流行度排名。

- Apple 2025 年的软件设计强调内容与操作层的关系、辅助工具按需出现。WIA 借鉴内容优先和轻薄工具层；正文使用稳定底色，保证可读性。[Apple 官方介绍](https://www.apple.com/newsroom/2025/06/apple-introduces-a-delightful-and-elegant-new-software-design/)
- Material 3 Expressive 强调借助颜色、形状与大小引导关键行动，同时保留熟悉交互和清楚标签。WIA 适合让行动入口易辨认，较克制地使用表达性视觉。[Google Design 研究](https://design.google/library/expressive-material-design-google-research)
- Linear 的 2024 年改版讨论减少视觉噪声、层级、对比与多环境压力测试，作为成熟产品的布局参考。[Linear 改版记录](https://linear.app/now/how-we-redesigned-the-linear-ui)
- Reader 的公开产品展示关注低干扰阅读与跨设备使用。WIA 保持正文中心，资料按需打开。[Readwise Reader](https://readwise.io/reader)

### 7.3 样稿验证

检查 1440×960 桌面、390×844 手机模拟，必要时增加短屏。每套保存一张桌面主界面和一张手机主界面截图；资料打开状态另外保留至少一张示例。

检查正文空间、字号和行长，三项建议换行、过长建议的滚动，输入与资料不重叠，关闭资料保留草稿及阅读位置。键盘焦点可见，关闭资料可用 Escape；触控入口足够清晰。静态样稿的交互检查不是正式应用或真机软键盘验收。

样稿为离线 HTML，使用本地或系统字体，避免远程依赖；用户直接打开比较页或各方案页面即可。文件按用户正常账户可读的父目录权限创建，不改变 ACL。

## 8. 与主线相关的附加工作

以下是预算有余时的建议，优先顺序固定。它们以已有能力的验证或材料改善为主，不扩大产品范围。

| 顺位 | 内容 | 价值 | 范围 |
| --- | --- | --- | --- |
| 1 | 两种题材的连续因果场景组 | 观察拒绝、失败、等待和返回后是否连续 | 复用已有测试世界与事件机制 |
| 2 | 人物表达辨识度校准 | 两个 NPC 面对同一刺激有不同关切和措辞 | 修改已有角色材料与必要提示，保留决定归属 |
| 3 | 整轮费用与等待基线 | 评估更完整互动的实际代价 | 使用已有用量与阶段数据，不新增玩家后台面板 |
| 4 | 资料、草稿与失败恢复检查 | 确认查看资料、建议失败、迟到结果不会干扰行动 | 回归已有行为和静态样稿，不增加新流程 |
| 5 | 提示的重复要求整理 | 提高职责清晰度，减少无用上下文 | 限于本轮受影响职责，保持来源和必要规则 |

真实模型未恢复时，附加连续场景与表达校准只形成机制证据及候选材料，不能标记叙事质量通过。费用与延迟使用既有记录或估计时，明确其样本与性质。

复杂地图、技能树、路人升级、额外日历、关系图、语音、多人联机和新导演模型属于其他产品范围，本计划不纳入。

## 9. 测试与费用边界

叙事链路改动执行 `go test ./... -count=1`、相关包 `go test -race`、`go vet` 与构建。涉及正式前端时执行类型检查、机制测试与正式构建；纯静态样稿检查页面脚本、浏览器行为、响应式截图与本地资源。文档检查链接和 `git diff --check`。

真实模型暂停及原费用限制保持有效，通用开工确认不自动等于恢复付费调用。恢复授权后，在隔离世界中对相同起点与输入进行改前改后比较，覆盖普通互动、多人冲突、私聊、拒绝、等待及存读档往返，并记录请求、重试、输入输出、耗时和实际费用。

确定性测试证明执行、权限和事务；浏览器样稿证明布局与示例交互；真实连续游玩才支持叙事质量结论。三类证据分别交付。

## 10. 收敛与最终交付

到第 220 分钟，冻结新增范围。先缩减附加材料数量、额外 UI 状态和视觉修饰，保留三个可比较的完整候选及核心机制检查。必要回归未通过的单元继续修复或明确不交付，不降低来源校验和权限边界。

最终交付包含：

1. 实际完成的代码、提示和材料，以及对应本地提交列表。
2. NPC 因果场景与两种题材回归结果，注明真实模型是否运行。
3. 三套本地 UI、比较页、截图与待选状态；正式前端保持用户选定后的范围。
4. 费用与等待证据的性质、实际样本和未验证范围。
5. 内部 CR、必要检查结果及未完成项。

旧存档、密钥、本机配置和用户改动保持；仅提交该工作单元相关文件。实际进度写入[开发状态](../开发状态.md)，验证证据写入对应验收记录，不把计划或设计样稿写成已交付的游戏能力。
