# Phase12 M1 核心游玩与可靠存档技术方案

状态：已形成可运行内测基线。实际验证与限制见 [M1 验收记录](../records/M1-验收记录.md) 和 [开发状态](../开发状态.md)。

依据：[产品说明](../产品说明.md)、[总体技术方案](../总体技术方案.md)、[开发指南](../开发指南.md)。

## 1. 阶段目标

M1 建立一次输入可以可靠完成、失败后可以恢复、存档之间不会串数据的核心游玩闭环：

1. 玩家从首页选择剧本或继续存档，确认主角后进入故事。
2. 输入经过意图识别、重要 NPC 独立决策、场景协调和正文生成。
3. 不同人物只获得自己有权知道的信息，正文只使用玩家可见投影。
4. 完整回合一次提交；失败、取消和迟到结果不留下半份剧情。
5. 当前进度自动保存，支持继续、另存、切换和删除。
6. 长对话、故事设置、模型连接和错误反馈在正式网页中可用。

M1 不实现长期摘要与检索、条件化世界剧情、内容编辑器、导入导出、桌面安装包或服务器账户。

## 2. 运行结构

```text
浏览器
  │ 输入、设置、存档操作
  ▼
storyapi
  │ 会话、Origin、参数、owner、版本检查
  ▼
storyapp.App
  ├─ 用户活动世界协调
  ├─ 世界单写者与 run 生命周期
  ├─ ContextComposer
  ├─ 模型执行与格式校验
  └─ 另存、激活、删除和恢复
        │
        ├─ app.db：世界目录、活动世界、幂等操作、模型配置
        └─ worlds/<world_id>/world.db：该世界的剧情与人物状态
```

`storyapi` 不决定故事，不直接拼 Prompt。`storyapp` 负责业务与事务。模型只产生候选内容，程序决定来源是否合法、对象是否存在、版本是否仍有效以及结果是否能够提交。

## 3. 一次回合

### 3.1 冻结输入

提交包含 `request_key`、玩家原文、可选交谈对象、活动世界版本及世界 heads/epoch。服务端先处理同键重放，再验证当前世界和版本。run 创建后冻结：

- owner、game、world 和运行 generation；
- 玩家原文及明确对象；
- definition、人物与场景版本；
- 故事设置与模型配置修订；
- 当前可见来源水位。

后续页面切换不会改变该 run 的写入目标。

### 3.2 阶段链路

```text
玩家输入
  → 意图识别：行为、交谈对象、公开/私密范围、等待意图
  → 第一阶段 NPC：处理玩家直接刺激
  → 场景协调：裁定行动、冲突、结果和接收范围
  → 后续 NPC：只处理本阶段真正新增的刺激
  → 最终协调：收敛剩余计划与结果
  → 正文：使用玩家可见投影组织第二人称故事
  → 原子提交：事件、感知、场景、正文和 run 终态一起保存
```

重要 NPC 的承诺、拒绝、隐瞒和主动行动由本人决策。场景协调负责执行条件、冲突和结果，不替人物重新决定立场。正文负责表达，不新增会影响后续的事实或人物决定。

### 3.3 沉默与主动性

NPC 可以说话、行动、说话并行动，或者保持沉默。人物主动性来自 definition 中的身份、知识、初始关切和世界经历；通用提示词只描述如何根据这些材料决策，不写具体人物目标。

玩家允许自然共创：正文可以补充与本轮意图一致的简短台词、日常动作和即时反应，但不能替玩家接受任务、改变立场、建立重要关系或选择新目标。

## 4. ContextComposer

四类模型请求统一由 `ContextComposer` 构建：意图、NPC、协调和正文。输入按用途与接收者选择，不共享一份全知 Prompt。

| 分区 | 规则 |
| --- | --- |
| 身份与职责 | 必需；描述本次调用能决定什么 |
| definition | 按用途提供公开背景、作者事实或人物私有资料 |
| 已提交经历 | 只使用有效来源；失败输入不进入 |
| 当前刺激 | 玩家原文、本人决定或本阶段新结果 |
| 场景视图 | 按接收者组合获准片段，不广播完整协调文本 |
| 文学历史 | 只作表达参考，不升级为世界事实 |

玩家私聊原文提供给玩家正文和实际接收者；旁观人物只获得交谈迹象。NPC 的公开回复继续按已确认合同传播。来源 ID 只用于追踪，不自动授予原事件全文读取权。

输入预算对最终完整请求检查。身份、核心规则、本轮原文和必须处理的结果属于必需内容；可选历史近期优先并按完整因果组移除。必需内容超限时明确失败，不静默截断后继续生成。

## 5. 世界、事件与人物数据

每个世界使用独立 SQLite 数据库，核心记录包括：

- `meta`：world、game、revision、epoch、heads、scene 和 definition 快照；
- `characters`：世界内人物实例及冻结 definition；
- `messages`：玩家输入、故事正文和运行关联；
- `events`：行动、对白、结果及来源；
- `perceptions`：某接收者获准看到或听到的投影；
- `memories`：M1 的近期人物记忆记录；
- `runs`：请求、attempt、阶段、状态和错误。

世界事实、人物感知、人物判断和玩家正文分别保存。正文出现一句话不等于所有人物都知道这句话；人物的推测也不自动成为世界事实。

## 6. 回合一致性与失败恢复

- 模型调用期间不持有数据库写事务。
- 每个阶段发布前重新检查 world、generation、epoch、run 和 attempt。
- 格式错误最多进行一次同阶段有限修复，修复内容也计入预算。
- 任一必需阶段失败时，run 进入明确失败状态；输入保留用于重试，世界不提交半轮结果。
- 取消关闭后续发布权，不删除已经完整提交的历史。
- 进程启动把上一进程未终结 run 标为 interrupted，不自动重放可能已经计费的外部调用。

前端保留原请求身份。响应不确定时先查询原 run，必要时以同键同载荷重发；明确完成或失败前不能把新输入混入旧请求。

## 7. 存档语义

### 7.1 新建与继续

新建世界从已确认的 `game_id + revision` 建立 definition 和资源快照。继续存档只读取自己的快照与运行状态，不读取新版模板补写旧世界。

### 7.2 激活

一个用户只有一个活动世界。列表和阅读不改变活动世界；显式激活携带 request_key 和 expected active revision。切换时先阻止旧世界的新生成，结束或取消旧任务，再发布新活动状态。

### 7.3 另存

另存复制当前完整稳定状态并产生新的 world ID，完成后仍停留在源世界。前端固定源世界、名称、请求键和活动版本；响应丢失后继续确认原 operation，不能生成第二份副本。

数据库使用一致性备份机制，目标 ready 前不可游玩。目标世界具有独立 generation 和后台任务执行权；删除源世界不影响副本。

### 7.4 删除

活动 run、另存或其他必需写操作期间拒绝删除。删除当前世界会清空活动选择并返回所属剧本详情，不自动激活其他存档。迟到任务不能复活已删除世界。

## 8. 玩家界面

- 应用启动默认进入首页，主入口为“继续故事”和“选择剧本”。
- 剧本详情负责新开局、继续、选择和删除该剧本的存档。
- 游玩页固定顶部导航、正文滚动区和底部输入区。
- 正文按游标读取最新 100 条，可向上加载；上翻时新消息不强制滚到底部。
- 输入使用 Ctrl+Enter 发送，中文输入法组合期间不触发。
- 桌面显示场景与人物侧栏，窄屏使用侧面面板。
- 人物可作为明确交谈对象；离场或切换世界后自动失效。

故事设置按世界保存，包含叙事视角、篇幅、描写密度、主角补写、NPC 主动性和行为策略。设置编辑会话固定打开时的 world 与 epoch；切换世界或版本冲突时保留草稿并拒绝错误写入。

## 9. 主要接口

| 接口 | 作用 |
| --- | --- |
| `GET /api/v1/games` | 公开剧本目录 |
| `POST /api/v1/worlds` | 幂等创建世界 |
| `GET /api/v1/worlds` | 当前用户的存档摘要 |
| `POST /api/v1/worlds/{world}/activate` | 显式切换活动世界 |
| `POST /api/v1/worlds/{world}/save-as` | 另存当前稳定进度 |
| `DELETE /api/v1/worlds/{world}` | 删除指定世界 |
| `GET /api/v1/worlds/{world}/messages` | 游标分页读取正文 |
| `POST /api/v1/worlds/{world}/runs` | 提交玩家输入 |
| `GET /api/v1/worlds/{world}/runs/{run}` | 读取 run 状态 |
| `PUT /api/v1/worlds/{world}/agent-settings` | 按 epoch 更新故事设置 |
| `PUT /api/v1/model-config` | 保存并验证模型连接 |

所有世界接口从已授权 world 解析 game，不信任客户端任意组合。写接口使用 request key 或 expected revision；普通错误返回稳定错误码和可恢复说明，不返回秘密 Prompt 或服务器路径。

## 10. 验证与完成边界

确定性测试覆盖：多人场景、私聊、迟到者、失败输入、格式修复、上下文预算、并行 NPC、原子提交、重试取消、新建激活、另存恢复、删除、世界隔离、设置冲突和历史分页。

工程检查包括相关 Go 测试与 race/vet、前端机制测试、类型检查、正式构建、浏览器桌面/平板/手机视口和差异检查。真实模型验证单独记录叙事质量、等待时间和失败；程序正确性不以模型偶然成功代替。

M1 的完成含义是“核心游玩与可靠存档可以用于本地内测”，不代表长期记忆、完整剧情、内容创作或发布产品已经完成。
