# 模型主导的可选能力模块

## 交付单元

本次以一个完整模块交付：模型主导的行动与状态更新。实现与回归完成后统一进行用户 CR。实际进度记录在[开发状态](../开发状态.md)，模块归属与依赖规则见[架构方案](../../summary/ARCHITECTURE.md)。

本方案调整 Story Pack v3 的行动裁定合同：普通行动、委托接受与拒绝、物品转移和日常状态变化由模型理解；明确声明的固定判定仍由程序执行。现有阶段 A、B、C 验收记录保留其当时的合同和验证结论。

## 主流程接入

```text
读取快照 → 理解意图 → 可选判定 → NPC 决策 → 协调结果 → 世界推进 → 叙述
                                      │             │
                                      └─ 能力上下文与状态变化 ─┘
                                                       ↓
                                              应用层原子提交
                                                       ↓
                                         玩家状态栏／人物状态栏
```

能力使用已有冻结 capability manifest 启用。未启用的能力提供空材料、接受空变化；模型输出未启用能力的变化时拒绝该候选。场内、场外协调使用同一份能力字段合同与材料装配。能力不新增模型调用，也不自行提交世界事实。

## 状态模块

输入为剧本状态定义、当前值与模型提出的变化；输出为新值及带来源的变化记录。状态标识、名称、单位、类型和范围由剧本声明。

`update_policy.kind` 支持：

| 策略 | 更新合同 |
| --- | --- |
| `model` | 模型判断整数变化量，或明确提供整数、布尔、枚举的新值；程序检查类型、定义范围与有效来源 |
| `bounded_proposal` | 作者明确限定的整数变化，保留整轮累计预算 |
| `rule_only` | 明确规则提供变化，模型不能直接修改 |
| `readonly` | 初始固定值 |

模型变化使用 `state_effects`，每项包含 `entity_id`、`state_id`、`action_id`，以及整数 `delta` 或带类型的 `value`，两者择一。失败的行动也可以产生疲劳等后果；未执行的行动不产生状态变化。程序检查目标是否为本世界已定义实体，模型判断行动与目标之间的因果关系。

状态栏接收服务端已裁剪的公开状态，通过独立展示组件渲染名称、值和单位。组件不解析正文、不判定行动、不计算世界状态，不依赖投掷模块。

## 物品与关系模块

物品实例只保存一份当前位置：一个持有人或一个地点。模型基于材料决定拾取、交付、夺取等结果，使用 `item_transfers` 给出实例、原归属、新归属与行动来源。程序验证实例、归属连续性、合法实体或地点及有效结果；行动者、显式目标和结束位置不充当物品转移的通用语义判定器。数组顺序表示同一阶段内的转移顺序，后续阶段继续使用工作态。

人物行动可以通过可选 `action_target_id` 明确目标；未明确目标时为空。人物公开物品按同场与个人知情来源提供，玩家界面和 NPC 上下文使用一致的物品可见性规则。

关系仍由关系主体本人提出，协调器采用本人提案。经历来源需要属于本人，关系对象由模型判断，允许依据一段经历改变对该段经历中其他人物的态度。`max_change_per_turn=0` 表示未声明单轮数值预算；正值保留作者明确设定的预算。数值保持在声明范围内。

## 投掷与固定判定模块

输入为选中的规则、相关快照和稳定输入标识；输出为规则标识、骰点、目标、修正、结果及可选声明效果。普通行动使用空规则标识，自然进入模型协调。判定准备使用现有短事务；模型调用在事务外；世界效果只在最终提交生效。

同一输入重试复用完整已保存的判定参数，包含骰点、目标和修正。投掷模块提供固定结果，状态模块接收规则声明的状态效果。没有状态效果的骰子规则可以独立工作；没有骰子规则的状态模块也可以独立工作。

新修订《雾都余烬》将接受、拒绝委托和银镜使用交给模型；普通调查与镜像状态由模型更新。保留潜入检定作为可选百分骰示例，后果由模型结合固定成功或失败结果判断。委托的后续推进依据经历与自然语言条件，不要求额外的成功标记。

## 一致性与已有存档

每轮只有一个工作态和一个最终提交点。能力应用先在隔离候选中进行，任何无效变化都不泄漏部分更新。变化记录具有独立顺序标识，同一来源引发同一状态的多次合法变化能够完整保存。整轮重试继续沿用既有输入与提交幂等机制。

旧世界继续使用冻结定义，保留已声明的固定规则和预算；新内容使用新的 revision，已有世界不转换剧本内容。状态变化与物品转移的唯一索引包含 `effect_order`；打开旧库时在既有 schema 事务中替换相应索引，保留全部记录与当前值。涉及当前结构化事实或已结算固定规则的纠正，在支持事实重建前保持明确拒绝；普通委托经历沿用记忆纠正流程。内容加载检查所有保留规则的引用，包括规则清单为空的情况。

## 实施与验收

实现顺序是：明确模块入口与合同、调整状态和行动应用、接通场外上下文与界面组件、更新示例修订、完成回归。以上属于同一交付单元，不设置逐步骤人工审批。

确定性验收覆盖：

- 无能力、仅状态、仅投掷及组合能力的接入；拒绝未启用能力的变化。
- 整数、布尔、枚举的模型更新，作者明确预算与只读规则保留。
- NPC 向其他 NPC 交付、模型确认的非持有人转移、拾取后离开、同轮连续转移。
- 人物已知的他人物品可见，未获知的私密资料仍不进入模型材料。
- 场外协调拿到当前地点、状态、物品、本人关系提案与完整字段合同。
- 判定重试复用参数，重复来源效果正常保存，无效候选整组回退，存档重启保持一致。
- 新示例不以接受委托的规则记录驱动叙事；旧冻结规则仍能加载。

工程检查包括全量 Go 测试、受影响包 race、go vet、前端类型检查、机制测试、正式构建、文档链接与 diff 检查。真实模型验收使用独立新存档，连续体验接受或拒绝委托、拾取后离开、人物交付、状态变化和风险行动；自动化替身不代表真实模型验收通过。
