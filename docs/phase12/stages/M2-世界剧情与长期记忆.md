# Phase12 M2 世界剧情与长期记忆技术方案

状态：M2 工程构建可交付，真实模型收口仍受 Provider 余额限制。实现与验证进度见[开发状态](../开发状态.md)和[M2 验收记录](../records/M2-验收记录.md)。本文件已合并剧本配置、多剧本、开放事件和本地剧本包说明，是 M2 的唯一技术入口。

依据：[产品说明](../../产品说明.md)、[总体技术方案](../../summary/总体技术方案.md)、[开发指南](../开发指南.md)。

## 1. 阶段目标

流程型旧渡口和独立开放型示例分别定义玩法与结束规则，类型由作者决定。玩家参与、干预、拒绝或等待，都能产生有依据的发展；人物能够在长期对话、离场重返及存读档后接续关键经历。玩家能够查看回顾及来源，纠正错误后继续故事。本地剧本包、完整流程收束、开放多事件与有界 AI 事件生成已经接入。

M1 作为本地可玩基线保留。NPC 独立决策、ContextComposer、分接收者场景、有限格式修复、原子回合和当前存档语义保持有效。人物具体动机、剧情条件和秘密属于世界采用的 definition；通用提示词只描述职责及处理规则。

本轮不实现 M3 的三个行动建议、内容编辑器、导入导出和基础外观设置，也不实现 M4 的 Electron、真实账户或部署系统。正文生成不承担事实抽取，不增加逐句裁判、任意动作 DSL 或全世界周期轮询。

## 2. 工作单元与交付顺序

| 单元 | 交付 | 验证门槛 |
| --- | --- | --- |
| U0 另存恢复 | 前端冻结另存请求身份，恢复丢失响应及轮询 | 接受后丢响应、轮询中断、改名与切换、终态失败；同请求只有一个副本 |
| U1 世界剧情 | 版本化剧情定义、条件节点、时间推进、两种模式及场外信息传播 | 顺序、幂等、失败回滚、玩家选择边界、秘密隔离、重启与复制 |
| U2 长期记忆 | 连续个人回顾、结构化主观状态、近期尾部、受限检索 | 覆盖连续性、权限、旧承诺召回、失败来源排除、预算与迟到发布 |
| U3 纠正与恢复 | 来源查看、有效修订、失效与可恢复重建、最小回顾纠正入口 | 各对象范围、并发版本、重启恢复、另存竞争、秘密不广播 |
| U4 阶段集成 | 可运行构建、连续游玩与存读档验证、验收记录 | 全仓回归、相关 race/vet、前端检查、浏览器及真实模型证据 |

各单元通过相关测试与差异检查后本地提交，不推送远端。确定性测试、真实模型质量、浏览器验证和用户验收分别记录。

## 3. 另存未知结果恢复

当前页面会话保存 `request_key / source_world_id / name / expected_active_revision / operation_id`。第一次点击冻结载荷；未取得任务 ID 时使用同键同载荷恢复请求，取得任务 ID 后只查询该任务。

网络异常或等待超时保留未确认操作；再次打开原存档的另存弹窗仍显示原名称与恢复提示，不把编辑后的名称提交到旧键。明确 ready 或 failed 后结束该操作，下一次另存才分配新键。结果归属源存档，不关闭其他弹窗、不覆盖其他世界的反馈。响应确认前禁止同源发起第二个另存；不同源各自保存页面状态。

刷新后以服务端已有存档和任务为准，本轮不增加跨刷新草稿存储。后端现有幂等查找先于活动版本验证，沿用该合同。

## 4. 世界剧情与时间

### 4.1 数据

在现有 `storyapp` 增加剧情组件，继续由 `worldStore` 持有事务，不迁移到新的通用框架。

| 数据 | 内容与作用域 |
| --- | --- |
| PlotDefinition | revision、固定事实、节点 ID、依赖、最早游戏时间、自然语言条件、人物计划、干预分支、结束约束 |
| PlotProgress | 各节点状态、已发布事件 ID、评估依据、进度版本、流程结束状态 |
| WorldClock | 游戏内绝对分钟数及展示文本；推进关联本轮来源 |
| PlotEvent | 节点、发生时间、实际结果、证据引用、接收者投影；区别未来计划与已发生事实 |

新世界复制完整 definition 与初始进度。旧世界缺少剧情定义时保留原有经历，不从新版模板自动注入未来节点；允许继续游玩、使用记忆和纠正，新剧情体验从新存档开始。缺字段与损坏数据区分处理，损坏不得静默当空。

### 4.2 推进

1. 从冻结世界快照和本轮有效行动中确定新增耗时及待处理结果。
2. 普通代码检查节点依赖、时间和终态，按最早候选时间选取有界批次。
3. 协调模型在授权作者资料及有效事件范围内评估自然语言条件，输出结果与依据；程序验证引用、版本、候选节点和接收范围。
4. 需要重要 NPC 新决定时，将获准刺激交给本人；仅有例行背景变化时不唤醒无关人物。
5. 先处理早事件的结果，再评估后事件。遇到需要玩家关键选择或工作量上限时停在已处理时点，剩余等待留给下一次输入。
6. 正文只读取玩家实际获知的变化。时间、剧情进度、事件、感知、场景与正文在原回合事务内提交。

失败、取消和旧 generation 均不推进时间或节点；重复请求只返回原结果。闲置、现实模型等待、刷新、读档和重启不推进游戏时间。

玩家明确等待时，通常推进至请求时长或下一节点边界。缩短等待需要引用本轮事件或提供的已提交事件；尚未解除的既有危险可以成为依据，未知来源及未来剧情定义不能充当已经发生的中止事件。是否仍有即时危险属于模型的情境判断，来源存在性由程序保证。

等待上限为玩家请求分钟数、下一剧情边界和单轮 120 分钟上限三者的最小值。没有 PlotDefinition 的剧本同样解析和校验等待；超出上限时整轮失败，时间和故事记录均不提交。

开放型单条剧情结束后仍可行动，不强制接受任务；流程型仅在已满足结束条件且有来源时收束。结果可以是成功、失去机会或离开，不伪造玩家承诺。

### 4.3 示例内容

沿用暮灯镇、旧渡口、沈岚与铁杉。definition 明确小范围地点、调查风险、时间窗口、信使去向和可改变的计划。每个节点给出不干预的发展及可干预条件；未来真相不进入公开开场或 NPC 未获知材料。

旧渡口配置化为流程型；开放型另设至少两条独立事件及少量地点，允许有界 AI 事件生成。模板加载、公开投影、快照和生成事件生命周期均使用本文件后续合同及验收要求。

场外事件保存事实和获准投影。玩家只能经目击、声音、迹象或有来源的转述获知；来源 ID 本身不是读取原文的权限。

玩家非对白行动进入协调候选，以带状态和来源的 player_action_result 作为干预依据；玩家声称已完成不等于实际成功。剧情投影可携带该接收者的事件后场景，程序绑定对应人物与投影来源。后续 NPC 行动结果继续按接收范围更新场景，正文使用最终视图；作者层剧情全文不能作为玩家场景来源。

玩家行动裁定适用于所有剧本，与是否提供剧情节点无关。剧情后续协调的 outcome 可携带 `actor_in_scene` 布尔值，仅描述该行动成功或部分成功造成的行动者进出场；失败、未执行、未知行动及同一人物重复位置变更均拒绝。最终名单供正文、原子提交及下一回合调度共同使用。入场结果可由目的场景人物获知，入场前的场外对白和私有经历保持原接收范围。

推理模型的内部推理预留与可见回答额度分开：现有正文及结构化输出上限保持不变，模型总输出窗口同时容纳两者，输入预算扣除总输出预留。默认诊断只保存预算、实际用量和错误分类；详见[总体技术方案](../../summary/总体技术方案.md#8-上下文与可见范围)。

## 5. 长期记忆

### 5.1 原始来源与派生资料

保留不可变原始事件、个人感知和玩家正文。新增按 scope 保存的回顾修订与人物状态修订，均带 epoch、连续覆盖起止水位、来源和发布状态。人物状态区分信念、关系判断、关切及约定，保留主观性质，不直接升级为事实。

玩家回顾仅使用玩家可见的成功提交内容；NPC 整理仅使用本人感知与原有有效状态。失败、取消及待执行输入不进入任何回顾、检索和条件证据。

### 5.2 整理与上下文

默认在历史达到阈值时自动整理连续前缀，保留近期完整因果组作尾部。辅助模型使用既有执行器与 Composer 的独立 purpose、预算及期限，整理不调用 NPC 决策或重演历史。

实现采用世界库中的 `memory_sources` 个人连续序列与 `memory_digests` 修订。回合开始时整理已成功提交的历史；超过八个经历组，或超过四组且尾部估算超过 6,000 tokens 时触发，保留最新四组，每次选择约 6,500 tokens 的完整前缀，每人每轮最多三次整理。回顾与近期完整经历组是必需上下文：通常纳入最近四组，进入请求前按字符预算预选，完整请求仍超限时按从旧到新移除窗口内较早的完整组，至少保留最近一个完整组；仍无法容纳时明确失败，不在组内截断。人物本轮前阶段的获准暂存经历单独保留，不与长期历史混为一谈。协调阶段另从世界事件按本轮输入及剧情条件检索完整因果组，不使用玩家文学回顾作为事实。

模型调用期间不持有数据库写事务。发布前核对世界存在、epoch、来源水位、活动 generation 和前版摘要，迟到结果不能替换新版本。可选整理失败仍保留原始尾部与真实覆盖水位；未覆盖尾部在投影时按近期窗口有界选入，较早的未整理记录留给检索，不假装已被摘要覆盖。必需基础材料与最小近期完整组仍无法容纳时有界降级，仍失败则给出明确错误，不丢弃材料继续生成。

检索先限定世界及接收者，再做文本相关性排序。默认自动查询近期刺激；NPC 可追加最多两次、每次最多 256 字符的只读查询，每次最多五条结果。结果包含合法投影、来源及时间，按 ID 去重，与摘要覆盖区分；无命中不制造经历。首版无需向量服务。

每次最多五条检索命中扩展为所属已提交回合的完整因果组。排重依据本次请求实际纳入的记录：近期窗口内的记录不重复添加，摘要水位之后但未进入窗口的未整理记录仍可被取回。检索组属于可选材料，低相关组优先因预算退出，保留当前刺激与近期窗口。构建报告记录检索纳入和排除数量，请求明确区分“未命中”和“因预算未提供”，不将未提供解释为事情没有发生。

增量摘要保留完整覆盖水位和来源元数据；实际模型请求的合法来源目录仅含上一版保留状态所需记录 ID 与本次新增记录 ID。输出状态按本次目录验证。历史覆盖 ID 不随每次请求重复展开，原记录仍可检索，纠正仍可追踪覆盖范围。

## 6. 统一纠正与重建

纠正目标覆盖事件、人物设定、个人感知、人物主观状态和派生摘要。请求携带目标 ID、适用 scope、替代文本、请求键和预期 epoch。模型内容不能指定数据库路径、扩大接收范围或执行写操作。

纠正由世界单写者提交：保存原文与新修订，递增 epoch，使依赖旧解释的派生资料失效。改信念不改事件，改摘要不改来源，改事件只更新有合法依赖的个人投影。已提交历史保留，不重写旧正文，不自动撤销或重演后续行动。

事件原文与个人投影完全一致时，有效投影采用纠正文本；局部投影撤回旧解释，不自动获得完整作者真相。需要补充局部信息时，通过该人的感知纠正明确指定。受影响的旧文学正文只保留作阅读，不进入后续回顾依据；关联旧场景说明标记待重新确认，不移动人物。角色设定、感知和主观状态均按自己的 scope 生效。

`event_dependencies(child_id, parent_id)` 在剧情事件与投影的原子提交中保存依赖。根事件纠正沿依赖展开到有效事件、个人感知、检索资料、场景来源及已覆盖回顾。旧档首次读取时，仅对同一 run、stage、scene_version 且符合旧编号合同的剧情投影补建关系；原事件和正文保持不变。依赖表随世界另存和重启恢复，关系本身不授予父事件读取权。

个人感知、主观状态和获准事件投影的纠正同时形成该范围内的近期纠正记录。它覆盖对同一内容的旧解释，不抹去历史对白，也不作为故事中新发生的交谈。其他范围的纠正不会覆盖已经手动编辑且来源仍有效的个人回顾。摘要状态只引用明确列出的个人记录ID，来源事件ID仍是溯源元数据。

重建使用 `memory_jobs` 保存 epoch、scope 列表、已完成数量、状态和安全错误码。模型调用前关闭数据库并释放世界锁，发布时重新验证世界存在、epoch、源头水位及摘要修订。删除不会被迟到结果复活；重启恢复 queued/running 任务，失败任务由界面显式重试。纠正追加期间旧任务失去发布权，各个人范围按各自有效来源重建。普通整理与纠正重建都不在模型调用期间持有写事务。

重建以已发布个人回顾的 epoch 为编辑水位，累积处理到当前任务 epoch 的已接受纠正。其他范围的新纠正可替换旧任务，但不能丢弃旧任务尚未发布的人工回顾编辑。后续相关来源纠正仍使该人工回顾失效；已应用或已被相关纠正废止的编辑不重新恢复。

重建任务保存目标 epoch、scope、进度和错误；从原始来源加有效纠正恢复，发布前再次检查版本。进程中断可恢复，新纠正使旧任务失去发布权。未来节点条件重新评估，已发生节点保持历史。

必需重建未完成时新生成返回 `memory_rebuilding`，已有正文仍可阅读。另存在冻结前及取得预约后检查重建状态，返回明确失败并释放预约，不持有重建需要的锁等待。

## 7. API 与最小界面

沿用用户/剧本/世界授权、Origin 和就绪检查。新增接口实际字段以同单元类型与测试为准：

| 接口 | 合同 |
| --- | --- |
| GET worlds/{world}/memory | 玩家回顾、覆盖水位、获准来源、整理状态；有界分页 |
| GET worlds/{world}/author-memory | 明确创作/剧透视图，受同所有者检查；人物记录与可纠正引用 |
| POST worlds/{world}/corrections | 幂等提交目标、scope、替代文本与预期 epoch，返回修订与重建状态 |
| GET worlds/{world}/corrections | 当前修订、重建进度及可恢复错误，不输出模型原始诊断 |
| POST worlds/{world}/memory/rebuild | 携带 expected_context_epoch，重试本世界失败的必需重建 |

回顾读取默认 `scope=player`，普通接口拒绝人物及作者 scope；作者接口可选人物 ID 或 `author`。`before_seq` 为排他边界，每页最多 100 条，返回 `has_more/next_before_seq`，个人范围使用个人水位，作者事件使用事件序号。纠正请求的 kind 为 event/character/perception/subjective/digest；人物设定目标为 profile/knowledge/initial_concerns，其余使用读取接口返回的 target_id。

游玩入口增加“回顾与纠正”，普通视图只展示玩家回顾与来源；人物私有记录通过明确剧透提示进入。错误就地呈现，写入中保护弹窗，编辑绑定世界与版本，切换后旧响应无效。完整人物/剧情编辑器仍属于 M3。

## 8. 存储和兼容

世界库采用幂等、增量建表或 meta 扩展；不删除既有消息、事件和记忆。定义与派生状态随世界一致性备份复制，新世界有独立 generation；复制不携带原世界后台任务执行权。重启恢复任务先检查来源、版本及世界所有权。

私密内容不进入普通 API、默认日志或共享缓存。诊断沿用 purpose、world、run、epoch、来源数量、预算和错误分类，不打印完整 Prompt。

## 9. 验收

### 开放事件运行合同

开放型剧本可配置 `event_generation`：作者限定 `scope`、既有 `locations`、重要人物 `participants`、`max_active`（1–3）和 `cooldown_turns`（2–20个成功回合）。远星样例采用同时两件、间隔三轮。配置随 definition 快照冻结；缺失表示不启用，流程型不接受此项。

场景协调在已确认抵达或显著变化时返回可选 `event_opportunity(kind, location, action_id)`。程序要求地点在授权范围、引用对应本轮成功或部分成功结果。没有机会、冷却未到、活动数已满时不调用生成。每轮优先处理到期作者节点，其次到期活动事件，最后新机会；同轮最多一个世界事件协调轮次。生成可以返回空候选。

候选只描述本次外部起点、后续条件与可能发展、1–120分钟后的检查边界和分接收者投影。重要人物通过已有第5阶段作新决定，第6阶段处理其行动。背景人物交谈进入主 Agent 的已裁定互动结果，不获得独立 Agent；明确面向重要NPC的交谈仍由其本人决定。`scene_characters` 只表示与玩家同一现场的重要人物，场外人物的个人场景继续保存。

`generated_events` 世界元数据保存有界活动集合、最近生成机会回合和结算数；事件起点与 `generated_event_plan` 原始记录随回合保存。事件身份绑定稳定 `input_id`，格式失败、取消和重试均复用原子回合与版本校验。完成事件退出活动集合，历史仍可溯源。作者计划不作为已发生事实，不进入普通人物感知或公共目录。另存、重启与只读访问不产生新事件。

依赖方向为触发结果→事件起点→个人投影/作者计划/收束结果。纠正触发或起点时，未发生的派生发展退出有效活动集合；旧正文和原记录保留。来源 ID 不授予原文读取权。剧情协调接受已提供场景及节点结果中、经当前世界元数据验证的来源引用，来源落到历史窗口外不等于不存在；未知引用仍拒绝。

### 示例内容

《暮灯镇的失踪信使》v2：客栈、码头、仓棚三处相连地点，19:05催渡、19:30追索窗口、20:00结算。帮助、拒绝、受阻、保全部分成果或错过机会均可收束，依据已确认结果而非固定动作顺序。

《远星维修站》v2：检修提醒及结算、货运通知及结算两条独立依赖链。流程条件不互相锁定，活动事件按最早检查时间调度；单件结束不结束世界。允许地点内的日常补充事件，不扩展地图或重要人物名单。

### 验收范围

确定性测试覆盖时间边界与前后依赖、干预和忽略、节点重复、场外隔离、离线不推进、失败事务、两种结束语义、连续摘要覆盖、尾部及检索去重、超过窗口的旧约定、真正缺失来源、纠正作用域、重建中断与迟到、重建和另存竞争、复制独立性。

工程检查包括全仓 Go 回归、受影响包 race/vet、前端机制测试、类型检查、正式构建与差异检查。浏览器使用独立数据根验证回顾、纠正、切换、错误和另存恢复；不修改用户现有存档。

同一真实模型分别验证开放与流程模式：参与、干预、等待、不参与、旧承诺、离场重返、纠正后继续、另存和重启接续。记录完成数、耗时、失败及典型语义偏差。机制通过不等同于真实模型质量通过；用户体验验收由用户完成。

M2 完成条件是上述能力进入实际游玩链路并有验证证据，不以新增类型、空页面或单独示例代替。M3/M4 的状态由[开发状态](../开发状态.md)单独记录。

## 10. 本地剧本包参考

### 10.1 文件与启动

v1/v2 剧本包是一个目录，包含 `story.json`、被引用的 `npcs/*.json` 和可选 `assets/` 图片。兼容性测试资料位于：

- [暮灯镇的失踪信使](../../../backend/internal/content/testdata/legacy-packs/lantern-dusk/story.json)
- [远星维修站](../../../backend/internal/content/testdata/legacy-packs/orbital-repair/story.json)

独立 Runtime 的默认目录是 `%LOCALAPPDATA%\WorldIsAgent\story-app\story-packs`。目录首次不存在时安装内置《雾都余烬》；已有目录由作者维护。源码启动器默认读取仓库初始包，修改文件后重启生效。验证 v1/v2 兼容性时可显式使用测试资料：

```powershell
.\scripts\start-phase12.ps1 -StoryPacks .\backend\internal\content\testdata\legacy-packs
```

也可以使用 `-story-packs <directory>` 或 `WIA_STORY_PACKS`。配置根目录包含多个包目录，不是单个 `story.json`。坏包从新游戏目录隔离，其他包和已有存档继续可用。

### 10.2 Story definition

加载时执行 [story schema](../../../backend/internal/content/schemas/story.schema.json)、重复键、未知字段、空值、跨文件身份和引用校验。

| 字段 | 含义 |
| --- | --- |
| `schema_version` | 配置格式版本，当前为 `1` |
| `game_id`, `revision` | 稳定剧本身份与不可变内容修订 |
| `mode` | 作者确定的 `guided` 或 `open`，玩家不能覆盖 |
| `title`, `description`, `gameplay`, `background` | 公开目录和介绍 |
| `rules` | 协调、正文与 NPC 共用的世界规则，不放秘密 |
| `author_facts` | 仅作者和获准协调阶段使用的固定资料 |
| `player` | 默认姓名、简介、公开要求和 `editable` |
| `opening`, `initial_location`, `clock` | 开场、地点 ID 和游戏内时间 |
| `locations` | 地点 ID、公开描述和连接；不是确定性导航引擎 |
| `npcs` | NPC definition 的相对路径 |
| `bystanders` | 背景人物，不拥有独立 NPC Agent |
| `cover`, `cover_alt` | `assets/` 下本地封面及替代文本 |
| `plot` | 条件剧情 revision、事实和节点 |
| `event_generation` | 开放型事件范围、地点、人物、活跃数和冷却 |
| `defaults` | 部分故事设置和共用行为策略 |

节点包含 `id`、`after`、可选 `at_minute`、`condition`、`development`、`audience` 和可选 `terminal`。依赖只引用前序节点；独立事件线使用独立依赖。

开放型可以声明 `event_generation.scope`、现有地点、重要人物、`max_active`（1–3）和 `cooldown_turns`（2–20）。省略表示禁用；流程型不接受该配置。事件候选是未来计划，不是已发生事实。

限制为 32 个地点、16 个重要 NPC、40 个路人和 32 个剧情节点。`story.json` 最大 256 KiB，每个 NPC 文件最大 64 KiB。封面仅支持 PNG/JPEG，最大 4 MiB、4096×4096。相对引用必须留在包目录内，拒绝远程 URL、路径穿越和外部链接。

### 10.3 NPC definition

[NPC schema](../../../backend/internal/content/schemas/npc.schema.json)包含 `definition_id`、`revision`、`entity_id`、`name`、`role`、`appearance`、`profile`、`knowledge`、`initial_concerns` 和 `initial_location`。

`entity_id` 以 `npc:` 开头，标识世界内人物；definition ID 与 revision 标识冻结模板。姓名、身份和外观公开，profile、knowledge 和 concerns 是私有角色资料。初始关切是起点动机，不是永久任务；运行中的感知、决策、记忆和纠正保存在世界内。

### 10.4 版本与存档

内容或引用资源变化时必须更新 `revision`。Runtime 持久绑定 `(game_id, revision)` 与规范化 digest；同一 revision 对应不同内容时拒绝加载，JSON 排版和对象键顺序不影响 digest。

新世界固定页面确认的 revision；版本冲突保留表单并要求刷新确认。世界拥有 definition 与资源快照，继续、另存和删除源世界均不依赖当前包目录。旧存档不从新版包注入人物动机或未来事件。

### 10.5 公开接口

| 接口 | 合同 |
| --- | --- |
| `GET /api/v1/games` | 公开目录与字段化加载问题 |
| `GET /api/v1/games/{game}` | 公开详情与实际 revision |
| `GET /api/v1/games/{game}/cover?revision=...` | 精确 revision 的受控图片 |
| `GET /api/v1/worlds/{world}/game` | 存档自己的公开剧本资料 |
| `GET /api/v1/worlds/{world}/cover` | 世界资源快照中的封面 |
| `POST /api/v1/worlds` | `game_id`、`expected_revision`、request key 和主角资料 |

创建成功返回 201；同 owner、同键、同载荷返回原结果；载荷变化返回幂等冲突；旧 revision 返回 409；不可用剧本返回 404。重放先按幂等记录解析，再读取当前目录。
