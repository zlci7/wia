# Phase12 M3 完整玩家工作台技术方案

状态：范围已收窄，实施范围见下表。本文是 M3 的开发合同，不代表功能已经完成。实现进度与验证结论只更新到[开发状态](../开发状态.md)和后续 M3 验收记录。

## 0. 范围变更说明（本次修订）

M3 原方案把"普通玩家不编写 JSON 即可创建、导入、发布剧本"和"游玩中把路人提升为重要人物"作为交付前提。产品定位现已收窄为：**由开发者准备世界和人物，让玩家直接进入、自由行动的开放型 AI 角色扮演产品**。本方案据此调整，不改写已交付的能力，也不删除已有代码。

| 原交付项 | 现定位 |
| --- | --- |
| 行动建议、自由输入、回顾与纠正 | **保留**，属于玩家侧能力 |
| 当前世界主角资料的版本化修改 | **保留** |
| 剧本自带默认主角，开局只改姓名与简介 | **保留并简化**；跨剧本模板库后置 |
| 内容项目、草稿、双视图预览、不可变修订发布 | **降为开发者工具**；其中发布幂等、重复请求与中断恢复仍需可靠 |
| TXT / Markdown / WIA 包 / CCV2 导入与导出往返 | **降为开发者工具或后置** |
| 路人在游玩中提升为重要人物 | **移出本轮**；玩家侧入口移除；开发者需要重要人物时直接在剧本包中定义 |
| 流程型主线、节点与结局编辑 | **移出本轮**；已有 Plot 代码保留并继续测试，不作为本轮交付门槛 |
| 地点层级、人物位置、由位置推导同场 | **本轮新增**，合同见[总体技术方案 §4.2.1](../总体技术方案.md#421-位置与同场) |

**功能后置不等于缺陷自动修复**：仍然被开发者使用的发布与加载路径，其发布准入、重复请求、恢复和版本冻结问题继续按既有验收要求修复；共享的记忆容量、位置、感知与存档问题不随创作功能一起后置。

依据：[产品说明](../产品说明.md)、[总体技术方案](../总体技术方案.md)、[开发指南](../开发指南.md)和 [M2 技术方案](M2-世界剧情与长期记忆.md)。

## 1. 阶段目标

M3 将现有可运行的故事内核交付为可长期游玩的开放型角色扮演产品。玩家可以：

1. 在正文下方使用三个行动建议，或者继续自由输入。
2. 使用剧本自带的默认主角并修改姓名与简介；编辑当前世界主角资料时有明确的世界版本边界。
3. 在开发者准备好的世界里自由交谈、行动、探索和等待，不沿预设主线节点走。
4. 人物依自己的位置参与或退出当前场景；玩家前往另一个地点后，原处的人群不被带走。

开发者可以：

5. 用本地剧本包定义世界、区域与地点、重要人物、默认主角与开放型世界计划。
6. 通过内容工作台编辑、校验、预览和发布不可变内容修订。
7. 导入 TXT、Markdown、WIA 内容包和 Character Card V2 JSON，先查看映射报告，再决定是否保存。
8. 导出已发布修订，并完成导出后重新导入的往返验证。

M1/M2 的人物独立决策、ContextComposer、来源权限、剧情时间、长期记忆、纠正重建、世界分库、幂等、原子提交和存档快照继续作为基础合同。M3 不改变 Agent 架构，不增加逐个路人 Agent，也不允许导入内容覆盖系统职责或执行程序指令。

## 2. 范围边界

### 2.1 本阶段包含

- 默认三个行动建议、关闭开关、自由输入和建议用量记录。
- 剧本自带的默认主角，以及当前世界主角公开资料的版本化修改。
- **地点层级（区域与具体地点）、连接语义、人物与稳定背景实体的当前位置，以及由位置推导同场。**
- **位置变更由主 Agent 提议、程序校验并随世界回合提交；移动受阻与程序执行失败分开处理。**
- 开发者工具：剧本、地点、重要 NPC、路人和本地图片资源的编辑与草稿管理。
- 开发者工具：草稿校验、玩家视图预览、作者视图预览和不可变内容修订发布。
- 开发者工具：TXT、Markdown、WIA ZIP 内容包和 CCV2 JSON 文本子集导入，以及 WIA ZIP 导出。
- 封面、人物头像、阅读字号和现有响应式布局的基础外观支持。
- 开放型内容与连续游玩路径验证。

### 2.2 本阶段不包含

- 面向普通玩家的可视化剧本编辑器、跨剧本主角模板库、游玩中提升路人。这些不属于当前产品定位。
- 流程型主线、强制节点与结局验收。已有 Plot 实现保留，不作为本轮交付门槛。
- Electron/Windows 安装包、Linux 多用户部署、真实账户和跨设备授权。这些属于 M4。
- 世界存档跨服务器迁移、离线双向同步和存档合并。M3 导入导出针对内容模板，不是世界进度备份。
- 在线内容市场、共享角色库、远程图片下载和云端素材管理。
- PNG 角色卡、CharX、任意插件、脚本、宏执行和第三方扩展运行时。
- 生成图片、动态立绘、完整主题系统、自定义 CSS 和语音。
- 自动把任意长篇文本转换成可发布剧本。模型可以生成草稿建议，但发布前必须由作者确认所有结构化结果。
- 对已经开始的世界静默套用新版剧本。历史世界继续使用自己的 definition 与资源快照。
- 坐标、逐分钟移动模拟、专门路径规划系统和棋盘式位置划分。


## 3. 已有基线与实现原则

当前正式基线已经具备：严格 story/NPC JSON schema、本地资源限制、不可变 `(game_id, revision, digest)`、新世界 definition 快照、公开剧本目录、世界级长期记忆与纠正、玩家和作者视图隔离、模型调用计量。

### 3.1 直接复用的现有能力

| 子问题 | 现有实现 | M3 处理 |
| --- | --- | --- |
| 剧本解析与校验 | `loadPack`、严格 JSON、引用和资源校验 | 提取为内存包和目录包共用的纯校验入口，不复制第二套规则 |
| 内容身份 | `game_id + revision + digest` 与 `pack_revisions` | 用户内容沿用同一不可变身份，增加 owner、草稿和发布状态 |
| 世界隔离 | 新世界保存 definition 快照，继续与另存不读取新版模板 | 发布只更新未来开局目录，不提供旧世界隐式升级 |
| 模型执行 | 统一文本执行器、ContextComposer、期限和用量账本 | 建议及显式模型辅助继续走现有入口，不由 HTTP handler 直接调用模型 |
| 世界写入 | 世界单写者、epoch、幂等和恢复操作 | 当前世界主角修改与路人提升接入同一边界 |
| 前端异步保护 | 页面会话、世界/版本核对、就地错误和迟到响应丢弃 | 草稿、导入和提升复用同一原则，各自维护编辑会话 |

### 3.2 组件边界

M3 在这些边界上增加普通代码组件，不建设通用插件框架：

```text
浏览器工作台
  ├─ Play：正文、行动建议、回顾与人物
  ├─ Creator：草稿、人物、地点、剧情、资源和预览
  └─ Import/Export：映射、确认、发布和内容包下载
             │
             ▼
storyapi：认证、大小限制、版本与幂等入口
             │
             ▼
storyapp
  ├─ suggestion 组件：玩家可见投影 → 三个建议
  ├─ content 组件：草稿、导入、校验、发布、导出
  ├─ persona 组件：主角资料模板与世界主角资料
  ├─ promotion 组件：路人经历 → 重要人物草稿 → 原子确认
  └─ 现有 WorldStore/Memory/Plot/ContextComposer
```

这些名称表示 `storyapp` 内的职责和文件分组，不是新进程、通用 Service 框架或四套独立运行时。优先给现有 `App` 增加窄方法和小型纯函数；只有共享事务或状态机确实需要时才引入内部类型。

HTTP handler 不直接调用模型，不直接拼装文件路径，也不拥有发布任务。所有模型辅助功能继续通过统一文本执行器、ContextComposer 和用量账本；所有内容写入继续经过 owner、版本、大小与引用校验。

M3 继续使用当前 `App.userID` 作为 owner。新增应用表从第一天保存 `user_id`，但本阶段不把 Runtime 改造成多账户服务；M4 接入真实会话时复用这些 owner 字段。磁盘路径只由服务端生成的 project、draft、operation 和 revision ID 组成，不直接使用用户输入名称或原始 `user_id`。

现有官方包保持只读，由启动目录加载。用户发布内容写入独立的 `content/` 根目录并登记到应用库。`App` 增加内容目录读写锁：列表读取不可变快照，发布在完成文件发布和应用库提交后一次替换目录项。用户项目不能覆盖官方 `game_id`；普通 `/games` 只合并官方包和当前 owner 的 ready 修订。

## 4. 工作单元与交付顺序

| 单元 | 交付 | 完成门槛 |
| --- | --- | --- |
| U0 基线收口 | 复核现有未提交工作和已存在的行动建议实现，修复整理滞后时的有界记忆投影，保持 M2 回归通过，建立 M3 验收记录 | 工作树归属清楚；已存在代码经测试与界面检查后才计入完成，不重复实现；整理滞后的世界在必需材料可容纳时仍能生成，原始记录与摘要水位不变 |
| U1 行动建议 | 收口三个异步建议、开关、过期保护、自由输入和用量记录 | A12、A20、A21、A65；浏览器完成选择、编辑、关闭和失败路径 |
| U2 主角与内容草稿 | 主角模板、内容项目、草稿版本、编辑器与双视图预览 | 草稿不影响世界；秘密不进入玩家预览；并发编辑返回冲突 |
| U3 发布与资源 | 严格校验、不可变修订、封面/头像、当前目录更新 | 发布崩溃恢复；旧世界不变；新世界冻结新修订 |
| U4 导入导出 | TXT/MD、WIA ZIP、CCV2 映射和 WIA ZIP 往返 | A34、A35、A39；恶意路径、未知字段、超限与附件测试 |
| U5 路人提升 | 稳定身份、来源选择、补充背景、原子提升和个人记忆起点 | 只继承可归属经历；迟到响应、另存、重启和世界隔离通过 |
| U6 整合验收 | 第三个题材、完整响应式工作台、全量回归与体验路径 | 三个内容、导入到开局、建议、提升、纠正、导出往返可完成 |

每个单元通过针对性测试和差异检查后独立本地提交，不推送远端。LLM 不可用时完成确定性、受控模型和浏览器验证；真实模型质量单独标记待补，不把外部余额问题记为工程失败。

## 5. 行动建议

### 5.1 生成与材料

建议在一段正文成功提交后异步生成，返回恰好三条。材料只包含：

- 当前世界的公开背景、主角公开资料、游戏内时间和玩家场景。
- 玩家可见的有效回顾、近期正文和纠正后的有效来源。
- 当前在场人物的公开投影。

材料不得包含作者事实、NPC 私人 profile/knowledge/concerns、其他人物个人记忆、未来剧情节点、模型推理或失败输入。建议只表达下一步可尝试的说话或行动，不预先宣布结果，不替玩家接受任务、建立关系或作出重大承诺。

### 5.2 Basis 与状态

每组建议绑定：

```text
world_id + message_head + event_head + context_epoch + definition_revision
```

状态为 `empty / generating / ready / failed / interrupted / disabled / ended / waiting`。同一 basis 最多启动一个生成任务；格式错误最多进行一次同阶段修复。失败后不对同一 basis 自动反复调用模型，玩家仍可自由输入。建议调用使用独立 `purpose=suggestions`，20 秒总期限，输出上限 1,024 tokens，并进入模型用量页。

世界切换、新回合提交、删除、设置或纠正改变 epoch、关闭建议时取消旧任务。发布前重新核对 world、basis、活动版本和世界状态；迟到结果不得覆盖新世界或新输入。

### 5.3 前端行为

- 建议默认开启，开关按世界保存；开关不改变故事 epoch。
- GET 只读取状态，不产生模型调用。生成使用显式、幂等的 POST。
- 点击建议只填入输入框，不自动发送；已有草稿时不覆盖。
- 用户可以修改建议。只要仍标记为建议来源，提交前再次核对 basis。
- basis 已过期时保留文字，提示用户检查后切换为自由输入，不偷偷替换基线。
- 未选择的建议、生成失败和关闭状态不进入消息、事件、记忆、检索或剧情条件。

世界库可以只保存最新 `suggestion_set` 与 `suggestions_enabled`；采用 meta 或专用表均可，但必须满足同一 basis 去重、重启后识别中断和另存继承偏好的合同。

## 6. 主角资料管理

### 6.1 主角模板

应用库新增 owner 作用域的 `personas`：

| 字段 | 合同 |
| --- | --- |
| `persona_id` | 稳定 ID，不由名称推导 |
| `name` | 1–80 字符 |
| `profile` | 最多 2,000 字符 |
| `version` | 乐观并发整数 |
| `created_at / updated_at` | UTC 时间 |

新建故事可以选择模板，选择结果复制进新世界；之后修改模板不改变已有世界。删除模板不影响已经创建的世界。

### 6.2 当前世界主角资料

当前世界可以修改主角姓名和公开简介，但必须携带 `expected_context_epoch`，活动 run、另存或记忆重建期间拒绝修改。保存后递增 epoch，使建议和依赖旧资料的可选派生内容失效；历史正文和已发生事件不重写。剧本声明 `player.editable=false` 时拒绝修改。

## 7. 内容项目、草稿与发布

### 7.1 内容项目

一个内容项目对应稳定 `game_id`，可以产生多个不可变 revision。作者不需要手工填写 ID：创建项目时生成稳定 ID，发布时生成 `r-<UTC>-<digest-prefix>` 修订；高级视图可以显示但不能通过改名重建身份。

应用库增加：

```text
content_projects(
  user_id, project_id, game_id, title,
  current_revision, version, deleted_at, created_at, updated_at
)

content_drafts(
  user_id, draft_id, project_id, base_revision,
  version, status, payload_json, source_json,
  created_at, updated_at
)

content_draft_assets(
  user_id, draft_id, asset_id, relative_name,
  media_type, byte_size, width, height, digest,
  staged_path, created_at,
  PRIMARY KEY(user_id, draft_id, asset_id)
)

content_revisions(
  user_id, game_id, revision, digest, path,
  status, created_at,
  PRIMARY KEY(user_id, game_id, revision)
)

content_operations(
  user_id, request_key, request_hash, operation_id,
  kind, target_id, stage, status, result_json, safe_error,
  created_at, updated_at
)
```

草稿状态为 `editing / import_preview / published / deleted`。导入预览直接使用 `status=import_preview` 的草稿，不再建设第二套临时导入对象；确认后在同一 `draft_id` 上转为 `editing`。原始导入文件作为该草稿的受限来源附件保存，删除草稿时按引用关系清理。

`payload_json` 与 `source_json` 分别限制为 2 MiB，列表接口只读取摘要，不扫描完整 JSON。草稿 JSON 使用现有 `StoryPack`、`PackNPC`、`PlotDefinition` 和资源引用作为发布目标，另保存字段级来源信息。来源至少区分 `manual / text_import / ccv2 / wia_pack / promoted`。来源标签用于映射报告和作者视图，不自动授予故事人物知识。

### 7.2 编辑范围

编辑器分为：

- 基本信息：标题、简介、玩法、类型、主角默认资料、开场和时间。
- 世界设定：公开背景、世界规则、作者事实。
- 地点：稳定 ID、名称、描述和连接。
- 人物：身份、公开外观、头像、profile、knowledge、initial concerns、初始地点和说话示例。
- 路人：稳定 ID、公开描述和初始地点。
- 剧情：流程节点、依赖、时间、条件、发展、受众和终态；开放型事件生成边界。
- 资源：封面、人物头像和不执行的来源附件。
- 默认故事设置：沿用现有 NarrativeSettings 与行为策略限制。

类型由作者在项目首次发布前确定。已有 revision 发布后改变 `guided/open` 需要“另存为新项目”，避免同一 `game_id` 的玩法语义改变。

### 7.3 双视图预览

玩家预览只显示普通 `/games` 与公开人物投影会返回的内容。作者预览在明确“包含剧透”入口下读取作者事实、人物私有资料、剧情条件和来源。隐藏字段不得先随普通页面下发再用 CSS 隐藏。

预览不创建世界、不生成记忆、不推进时间，也不调用模型。可选的“整理剧情草稿”必须由用户显式点击，并显示其单独模型用量。

### 7.4 发布

发布请求携带 `request_key`、`draft_id`、`expected_draft_version` 和 `expected_project_version`。同一项目的发布由内容写协调器串行处理，其他项目和只读目录不被长时间阻塞。

SQLite 与文件系统之间不存在跨介质原子事务，因此发布采用可恢复状态机，而不是宣称一次事务同时提交两者：

```text
prepared
   │ 校验并冻结草稿/资源
   ▼
files_written ── 临时目录完整写入、逐文件关闭并校验 digest
   │
   ▼
renamed ─────── 同一内容根目录内原子 rename 到最终 revision 目录
   │
   ▼
ready ───────── 应用库登记 revision、更新 current_revision、替换目录快照
```

发布流程：

1. 冻结草稿和资源清单。
2. 使用现有 JSON schema、重复键、字段长度和跨文件引用规则校验。
3. 验证剧情依赖、受众、地点、人物、资源 MIME、尺寸和路径。
4. 计算规范化内容 digest，生成不可变 revision。
5. 先在应用库登记 `prepared` operation，再在内容根目录的专属临时目录写入完整包；文件与目录继承父目录的正常权限。
6. 校验临时目录与 digest，在同一内容根目录内原子重命名为 revision 目录，将 operation 记为 `renamed`。
7. 在一个应用库事务中插入 ready revision、按 `expected_project_version` 更新项目 current revision，并将 operation 记为成功。
8. 提交后以不可变 `loadedPack` 一次替换当前 owner 的目录快照；目录刷新失败不撤销已发布 revision，读取路径可从应用库重建快照。

启动恢复只处理本应用登记的未终结 operation：目标目录存在且 digest 一致时补交应用库；只有临时目录存在且内容完整时继续 rename；内容不完整时删除该 operation 的专属临时目录并标记失败。恢复不扫描或删除未知目录，不覆盖已存在的不同 digest。未 ready 的修订不能出现在目录或用于开局。同一 request_key/载荷返回原结果，不同载荷冲突。

编辑模板只影响未来新世界。已有世界继续使用自己的 definition 与资源快照；对历史事实的修正使用现有纠正入口，故事表达设置使用故事设置，路人提升使用世界专用接口。M3 不提供任意“把新版模板覆盖到旧存档”的操作。

## 8. 资源与基础外观

StoryPack 增加可选 NPC `avatar` 资源引用；路人可选公开头像。资源只允许包内 `assets/` 相对路径。包加载时把封面、头像和来源附件解析为受控资源清单，业务结构只保存相对资源 ID，不保存客户端路径。

| 类型 | 限制 |
| --- | --- |
| 封面/头像 | PNG 或 JPEG；单文件最多 4 MiB；最大 4096×4096 |
| 普通文本导入 | 单文件最多 1 MiB；UTF-8 |
| CCV2 JSON | 最多 1 MiB；严格 JSON |
| WIA ZIP | 压缩包最多 8 MiB；解压后最多 16 MiB、128 个文件、嵌套不超过 8 层 |

禁止绝对路径、反斜线、盘符、`..`、符号链接、硬链接、设备文件、重复规范化路径和远程 URL。图片按内容解码，不信任扩展名或请求 MIME。浏览器只能通过受授权的 asset ID 读取资源，不能提交服务器文件路径。

创建世界时，将该 revision 实际引用的封面和头像复制到世界资源快照并保存 digest；另存沿用现有一致性复制机制复制这些资源。以后项目被删除、目录被清理或发布新 revision，已有世界的头像和封面仍可读取。普通世界资源接口只允许读取 definition 快照已经引用的 asset ID。

前端保持现有暖纸色视觉，只增加 `小 / 标准 / 大` 三档阅读字号并保存在浏览器本地。封面与头像来自受控资源，缺失时继续使用统一占位。M3 不开发主题市场、自定义 CSS 或动态立绘。

## 9. 导入与映射

### 9.1 两阶段合同

所有导入先创建 `status=import_preview` 的 content draft，返回其 `draft_id`、版本和：

- 检测到的格式与版本。
- 字段到 WIA 草稿的映射。
- 公开、人物私有、作者私密的建议范围。
- 未支持、被忽略、截断风险和需要确认的项目。
- 预览草稿版本和来源附件。

预览不发布内容、不修改世界、不写人物记忆。用户修改映射并确认后，同一草稿转为 `editing`；导入确认携带 request_key 和 preview version，重复确认幂等，过期预览返回冲突。没有单独的 import 临时表或第二份草稿身份。

### 9.2 TXT 与 Markdown

TXT/Markdown 内容默认映射为“公开背景候选”，作者可以改为世界规则、作者事实、开场、地点描述、人物 profile/knowledge 或剧情草稿。Markdown 作为文本内容处理；预览使用安全渲染，不加载远程资源，不执行 HTML、脚本、链接命令或代码块。

可选“整理剧情草稿”调用模型提取固定事实、人物计划、关键节点、条件、干预路径和结束约束。模型只产生 content draft，不能发布；输出必须经过严格结构校验和作者逐项确认。模型不可用时手动编辑完整可用。

### 9.3 WIA 内容包

WIA 内容包文件名建议为 `.wia-story.zip`，根目录包含：

```text
story.json
npcs/*.json
assets/*
attachments/*    # 可选，只作为不执行的来源附件
```

导入使用与运行时相同的 schema 和引用验证。若 `game_id` 与当前 owner 已有项目冲突，用户选择“作为新修订”或“复制为新项目”；默认复制为新项目并重映射内部稳定引用。不能覆盖官方包或其他 owner 的项目。

### 9.4 Character Card V2 JSON

只接受 `spec="chara_card_v2"`、`spec_version="2.0"` 的 JSON 文本卡。映射如下：

| CCV2 字段 | WIA 草稿候选 |
| --- | --- |
| `data.name` | NPC name |
| `description` + `personality` | NPC profile，保留字段来源 |
| `scenario` | 世界背景、人物 knowledge 或开场情境候选，必须确认 |
| `first_mes` | 开场或说话示例候选，必须确认 |
| `mes_example` | NPC speaking examples |
| `creator_notes` | 作者备注，不进入模型上下文 |
| `alternate_greetings` | 可选开场候选，不自动发布 |
| `tags / creator / character_version` | 项目来源元数据，不参与提示词 |
| `system_prompt / post_history_instructions` | 不执行，报告为不支持行为指令 |
| `character_book` | 保留在来源附件，M3 不自动转换为世界知识 |
| `extensions` | 原样保留在来源附件，不执行、不解释 |

只对文本字段中的精确 `{{char}}` 和 `{{user}}` 提供可预览的名称替换；其他宏保持原文并列为未支持。原 JSON 在大小限制内作为不执行附件保存，导出时可以选择包含。未知 `extensions` 的保留仅保证 WIA 来源附件不丢失；M3 不提供 CCV2 再导出，因此不声称可以无损往返第三方卡片。CCV2 卡缺少人物知情范围，系统不得声称已经准确还原秘密边界。

### 9.5 导出

只有 owner 可以导出自己的已发布 revision。导出重新生成规范 WIA ZIP，不直接打包任意目录。导出包含 story、NPC、引用资源和用户选择保留的来源附件；不包含世界存档、模型凭据、服务会话、绝对路径、运行日志、用量记录或其他 owner 内容。

导出后重新导入必须得到等价的公开内容、作者内容、人物定义、剧情、资源 digest 和内部引用；新项目使用新的 owner 作用域身份，不复用世界 ID。

## 10. 路人提升为重要人物

### 10.1 稳定路人身份

M3 在包加载边界把路人规范化为带稳定 ID 的内部定义：

```json
{
  "bystander_id": "bystander:boatman",
  "name": "船夫",
  "description": "门边条凳上打瞌睡的船夫",
  "initial_location": "old-ferry-inn",
  "avatar": "assets/boatman.png"
}
```

包 schema v1 的字符串数组继续可读；新编辑器发布 schema v2 的对象数组。加载器只在一个归一化函数中兼容两种输入，运行时、世界快照和新导出一律使用对象格式，避免两套行为长期并存。legacy ID 按 `definition revision + 数组序号 + 规范化文本摘要` 生成；已冻结的旧世界在一次幂等迁移事务中保存规范化对象，不根据新版模板补人物，也不改变已有 scene 或 event head。

世界库增加有界的 `bystander_experiences`，每条记录引用有效 `source_event_id`、`bystander_id`、接收方式和内容投影。协调候选涉及已定义路人时必须引用 `bystander_id`；只有明确以该路人为 actor、target 或合法接收者的已提交来源才能进入经历。同处一室、出现在正文或玩家知道某事，都不等于该路人知道全部现场信息。旧正文中的文学描写不自动反推经历。

### 10.2 预览与确认

玩家在“场景与人物”中选择路人并打开提升流程。预览包含：

- 路人的公开名称、描述、头像和当前地点。
- 明确归属于此人的已有经历及来源。
- 待填写的 role、appearance、profile、knowledge、initial concerns。
- 每项内容的来源标签：已有来源或作者补充。

模型可以在用户显式点击后根据获准材料生成草稿；失败不影响世界，也不自动重试。没有模型时所有字段可以手工填写。

确认请求携带 request_key、expected_context_epoch、bystander_id、选中的 source IDs 和完整草稿。程序验证来源属于当前世界、该路人且仍有效。确认在世界单写事务中：

1. 生成稳定且唯一的 `entity_id` 与 world-local definition revision。
2. 插入重要人物及 `character_origins` 来源记录。
3. 仅把确认且可归属的经历投影为该人物的个人 perception/memory source，并登记后续个人回顾工作；不把模型草稿本身当作已经发生的经历。
4. 从活动路人列表移除同一 bystander，保持其物理位置不变。
5. 更新场景人物、scene version 和 context epoch。
6. 使旧建议和相关派生上下文失效。

活动回合、另存、必需记忆重建或另一提升操作期间返回 busy。重复 request_key 返回同一人物；不同载荷冲突。另存和重启保留人物及来源；删除世界后迟到草稿不得复活数据。

路人仍不拥有独立 NPC 决策调用。只有提升事务提交后，新人物才从下一轮开始进入重要 NPC 候选；当前进行中的回合不会中途增加 Agent。

## 11. API 合同

所有接口沿用本地会话、Origin、owner 和 ready 检查。写接口使用 request_key 或 expected version；错误不返回完整导入原文、作者秘密或服务器路径。

### 11.1 行动建议与主角

| API | 合同 |
| --- | --- |
| `GET /api/v1/worlds/{world}/suggestions` | 读取当前 basis、状态与三条建议；无副作用 |
| `POST /api/v1/worlds/{world}/suggestions` | 对当前 basis 幂等启动生成 |
| `PUT /api/v1/worlds/{world}/suggestions` | 保存当前世界 enabled 开关并取消不再需要的任务 |
| `GET/POST /api/v1/personas` | 列出或创建 owner 的主角模板 |
| `GET/PUT/DELETE /api/v1/personas/{persona}` | 按 version 读取、修改或删除模板 |
| `PUT /api/v1/worlds/{world}/player-profile` | 以 expected_context_epoch 修改当前世界主角资料 |

### 11.2 内容工作台

| API | 合同 |
| --- | --- |
| `GET/POST /api/v1/content/projects` | 列出或创建 owner 的内容项目 |
| `GET /api/v1/content/projects/{project}` | 项目、修订与草稿摘要 |
| `POST /api/v1/content/projects/{project}/drafts` | 从空白或已有 revision 创建草稿 |
| `GET/PUT/DELETE /api/v1/content/drafts/{draft}` | 作者视图读取、按 version 保存或删除未发布草稿 |
| `POST /api/v1/content/drafts/{draft}/validate` | 无副作用校验，返回字段和引用问题 |
| `GET /api/v1/content/drafts/{draft}/preview` | `view=player|author`；作者视图要求显式入口 |
| `POST /api/v1/content/drafts/{draft}/assets` | 上传受限本地资源，返回 asset ID |
| `POST /api/v1/content/drafts/{draft}/publish` | 幂等发布不可变 revision |
| `POST /api/v1/content/imports/preview` | 上传并创建 `import_preview` 草稿，返回 draft ID/version |
| `POST /api/v1/content/imports/{draft}/confirm` | 幂等确认映射，将原预览草稿转为 editing |
| `GET /api/v1/content/revisions/{game}/{revision}/export` | owner 下载规范 WIA ZIP |
| `GET /api/v1/content/operations/{operation}` | 读取显式模型辅助任务的状态与安全错误 |

### 11.3 人物与路人

| API | 合同 |
| --- | --- |
| `GET /api/v1/worlds/{world}/entities` | 玩家可见的重要人物和稳定路人投影 |
| `POST /api/v1/worlds/{world}/character-promotions/preview` | 读取获准来源或显式生成提升草稿，不修改世界 |
| `POST /api/v1/worlds/{world}/character-promotions` | 以 request_key/epoch 原子确认提升 |
| `GET /api/v1/games/{game}/definitions` | owner 的模板作者视图；普通游戏页面不调用 |

纯校验、手动导入确认、发布和提升确认在短事务/文件期限内同步完成，网络结果不确定时以原 request_key 重放确认，不为这些操作再建队列。只有“整理剧情草稿”和“生成提升草稿”等显式模型辅助使用后台 operation；它们必须提供 owner 作用域的轮询接口和 `queued / running / succeeded / failed / cancelled / interrupted` 终态。同键恢复不能新建第二份内容或人物。

统一错误码至少包括 `content_not_found`、`draft_version_conflict`、`project_version_conflict`、`content_busy`、`content_invalid`、`import_unsupported`、`import_limit_exceeded`、`asset_invalid`、`publication_failed`、`suggestion_stale` 和既有 owner/world 错误。界面按当前操作就地展示安全说明；响应不包含服务端路径、原始附件或作者秘密。

## 12. 前端信息架构

顶部导航增加“创作”，模型用量继续作为独立入口。首页保持选择剧本和继续故事，不把创作表单堆在普通玩家首屏。

```text
首页
  ├─ 故事详情 → 新开局/选择存档
  └─ 创作
       ├─ 我的剧本
       ├─ 新建/导入
       ├─ 故事编辑
       ├─ 人物与路人
       ├─ 地点与剧情
       ├─ 资源
       └─ 玩家预览/作者预览/发布/导出

游玩页
  ├─ 正文与行动建议
  ├─ 输入与交谈对象
  ├─ 场景与人物 → 路人提升
  └─ 回顾与纠正/故事设置/用量
```

编辑器采用分区表单，不直接暴露原始 JSON 作为默认操作。高级用户可以查看只读 JSON 预览和字段错误路径。草稿自动保存固定采用 750ms 防抖、expected version 和独立编辑会话；版本冲突保留本地草稿并提供重新载入/复制为新草稿，不自动覆盖远端。

不为 M3 引入新的前端状态框架或路由依赖。沿用现有页面状态机，但把创作目录、草稿编辑、导入映射、资源管理和预览拆成独立组件与 composable；`App.vue` 只负责顶层导航和主弹窗编排，API 调用及编辑会话不直接散落在模板事件中。

导入、发布、提升、人物编辑和故事设置各自维护错误区域。异步响应核对项目、草稿、世界、版本和页面会话；切换后迟到响应不能关闭新弹窗或覆盖新内容。所有主弹窗沿用焦点圈定、Esc、背景滚动锁定和写入中关闭保护。

窄屏创作页改为单列步骤导航，游玩页保持持久顶栏、正文滚动和底部输入。表格在容器内横向滚动，不扩大文档宽度。真实手机软键盘验证仍需实机，视口模拟不能替代。

## 13. 安全、权限与日志

- 普通游戏目录和游玩 API 只返回玩家公开投影。
- 作者事实、NPC 私有定义、剧情答案、导入原件和扩展只从 owner 作者入口读取。
- 查看作者页不修改人物知识，不生成记忆，不触发建议或剧情。
- 导入内容一律视为数据。脚本、HTML、SQL、命令、宏、system prompt 和 post-history 指令均不执行。
- Markdown 使用安全渲染；默认可以直接按纯文本显示。
- 内容文件与资源采用允许列表、大小限制、解压限制和路径归一化。
- 日志只记录 owner 的不透明 ID、格式、大小、版本、问题数量、operation 状态和安全错误码，不记录完整正文、作者秘密、卡片原文、Prompt 或模型推理。
- 模型辅助整理、建议和提升草稿全部计量；用量页按 purpose 区分，不估算金额。
- M3 不修改工作区或数据目录 ACL；新文件继承父目录的正常权限，普通用户必须可读取自己的内容。

## 14. 存储、兼容与删除

应用库和世界库使用增量、幂等建表，不删除或重写既有消息、事件、记忆和 definition 快照。旧字符串路人采用读取后规范化迁移；无法解析的数据返回明确错误，不静默当空。

删除草稿只删除未发布草稿及其独占暂存资源。删除内容项目时：

- 已发布 revision 和被世界快照引用的资源默认保留。
- 项目从创作列表隐藏，不破坏已有世界。
- 真正清理未引用 revision 属于后续显式维护操作，不随普通删除执行。

发布 revision 不可原地改写。相同 `(game_id, revision)` 与不同 digest 冲突；已有世界、另存副本和导出引用保持稳定。官方包和用户包在目录中标明来源，用户内容不能覆盖官方身份。

## 15. 性能与资源边界

- `/games`、项目列表、草稿列表和修订列表只读取摘要列；打开编辑器时才读取完整 `payload_json`，避免目录页出现大字段 N+1。
- 官方包与 ready 用户修订在内存中保存不可变 `loadedPack`；发布只加载并替换一个新 revision，不全量重扫所有图片和内容目录。
- ZIP 上传通过有上限的 reader 逐项读取，先验证条目数量、声明尺寸和规范化路径，再解压到专属暂存目录；任何路径都不能绕过解压后总量检查。
- 图片只在上传和发布校验时解码尺寸，列表与正文读取使用已保存元数据，不重复解码。
- 草稿自动保存只发送发生变化的完整草稿一次，不并行积压；保存进行中产生的新修改合并到下一次版本化保存。
- 行动建议继续使用低优先级模型额度。内容列表、导入映射、手动编辑、预览、校验、发布、导出和手动提升不得依赖模型。
- 本阶段以单机、小型内容包为容量目标：单 owner 最多 200 个可见项目、每项目最多 100 个 revision、单草稿 JSON 最多 2 MiB。超过上限返回明确错误，不通过无限分页或后台全量扫描维持表面可用。
- 验收记录发布、导入、导出、建议生成和创作页初次打开的耗时与峰值文件大小。确定性本地操作以 5 秒为保护期限，不把该上限宣传为体验目标。

## 16. 验证方案

### 16.1 后端确定性测试

- 建议：恰好三条、同 basis 去重、失败最多一次修复、关闭、过期、迟到、删除、另存、重启、失败输入排除、隐藏信息排除、用量计数。
- 记忆整理滞后：无摘要的多组历史仍能构建材料、组数与容量双重约束、最小近期组不可容纳时明确失败、移出窗口的较早组可被默认与追加召回取回、跨接收者隔离、覆盖水位与原始记录不变。
- 主角：模板 CRUD、复制入世界、不可编辑约束、活动 run、epoch 冲突、删除模板不影响世界。
- 草稿：owner 隔离、版本冲突、非法枚举、重复 ID、未知字段、引用错误、秘密双视图、草稿不进入世界。
- 发布：同键恢复、不同载荷冲突、digest、revision 不可变、崩溃恢复、目录刷新、旧世界快照不变。
- 资源：MIME 欺骗、超限、尺寸、远程 URL、路径穿越、符号链接、重复路径、ZIP bomb 和损坏图片。
- 导入：TXT/MD、WIA 往返、CCV2 全部支持字段、缺字段、未知 spec、system prompt/宏不执行、extensions 保留、知识范围待确认。
- 路人提升：只继承合法来源、作者补充标签、重复确认、并发提升、世界切换、删除、另存、重启和迟到模型结果。
- A12、A20、A21、A30、A34、A35、A39、A41、A65、A67 的相关组合回归。

### 16.2 前端机制与浏览器验证

- 建议到达时不覆盖正在输入的文字；选择后可修改；旧 basis 不能沿用新 head。
- 创建项目、手动编辑、玩家/作者预览、发布、新开局完整走通。
- 四类导入均显示映射和未支持项；确认前目录和世界不变化。
- WIA 内容包导出后重新导入，关键字段和图片一致。
- 路人提升预览、手动补充、确认、后续对话和人物信息可见。
- 两个标签页并发编辑、切换项目、迟到保存、发布响应丢失和操作恢复。
- 桌面 1280×800、平板 768×1024、手机 390×844；手机软键盘另列实机项。
- 所有主流程键盘可达，焦点恢复、错误位置、上传进度和写入中保护正确。

### 16.4 内容与体验验证

仓库至少提供三个不同题材的测试内容。现有《暮灯镇的失踪信使》和《远星维修站》继续使用，新增第三个小型题材，至少包含一名主角、两名重要 NPC、稳定路人、封面/头像和可完成的三轮以上互动。

M3 阶段必须实际完成：

1. 使用空白表单创建第三个内容并开局。
2. 使用 TXT/Markdown 创建背景草稿并人工确认。
3. 导入 CCV2 文本卡，检查人物、情境、开场、示例和未支持字段。
4. 导出 WIA 内容包并重新导入为新项目。
5. 在故事中使用、编辑和关闭建议。
6. 提升一个路人，验证其只继承合法经历，重启和另存后继续存在。
7. 查看作者秘密和玩家预览，确认普通接口未收到隐藏字段。

真实模型质量采用可用时的现有模型记录，不要求用户承担程序回归。单次成功不证明长期稳定；等待时间、调用数、输入/输出 token 和缓存命中率写入 M3 验收记录。

### 16.5 关键失败模式

| 路径 | 生产失败 | 程序处理 | 必须验证的用户结果 |
| --- | --- | --- | --- |
| 建议生成 | 超时、格式错误或旧 basis 迟到 | 一次格式修复；basis 不同即丢弃 | 正文和草稿仍可用，原地显示失败或过期 |
| 草稿保存 | 双标签页版本冲突 | 409，保留本地编辑会话 | 可重新载入或复制，不静默覆盖 |
| 资源上传 | MIME 欺骗、损坏图、超限 | 流式限额、内容解码、删除专属暂存文件 | 对应资源区显示安全错误 |
| 发布 | rename 前后进程退出 | operation 分阶段恢复，ready 前不进目录 | 重试同键得到同一 revision 或明确失败 |
| 目录刷新 | 文件已发布但内存替换失败 | 应用库保持 ready，读取时重建目录快照 | 不产生第二个 revision，重启后可见 |
| ZIP 导入 | 路径穿越、压缩炸弹、重复路径 | 解压前后双重限额并拒绝整个预览 | 项目和世界不变化，可换文件重试 |
| 模型整理 | Provider 不可用或输出非法 | operation 失败，保留原预览草稿 | 手工编辑仍完整可用 |
| 记忆整理滞后 | 摘要长期未推进、未覆盖尾部膨胀 | 近期窗口有界选入，较早未整理记录留给检索，不改写覆盖水位 | 正文、NPC 与建议仍可生成；未提供的旧事不会被当成没发生 |
| 路人提升 | epoch 过期、来源被纠正或世界删除 | 事务前重验；不发布迟到草稿 | 人物不重复、不带入无效经历 |
| 世界开局 | 项目已删除或资源被清理 | 只从 ready revision 建快照；世界资源独立 | 新开局明确失败，已有世界仍可继续 |

上述每条都必须同时具有确定性测试、明确错误处理和可见恢复路径；任何“无测试、无处理、用户无提示”的组合都阻止 M3 工程完成。

```text

  ├─ 发布状态机 → ready revision → 新世界快照                   [崩溃恢复 + 集成]
  ├─ TXT/MD/CCV2/WIA → import_preview → editing                 [fixture + 安全回归]
```

## 17. 完成定义

M3 只有同时满足以下条件才可以标记工程完成：

- 行动建议、剧本自带默认主角与当前世界主角资料的版本化修改、基础外观进入玩家正式界面，不是空页面或仅后端类型。
- **地点层级、人物与稳定背景实体的当前位置、由位置推导同场进入运行合同，并且位置变更随世界回合原子提交。**
- **旧存档升级后不把人物重置到初始地点、不伪造无法确认的位置；读取不偷偷修改历史，可靠迁移不推进游戏时间。**
- **开发者的发布与加载路径可靠**：发布准入、重复请求与中断恢复有回归；剧本包加载校验、内容版本与旧存档快照正确。
- 草稿、已发布修订和已开始世界的语义清楚，模板更新不改写旧世界。
- 玩家视图、人物私有资料和作者事实经过程序隔离，不依赖提示词保密。
- 摘要整理滞后时请求材料仍然有界：不把全部未整理历史强制纳入，不伪造摘要覆盖水位，移出近期窗口的经历仍可检索且不跨接收者，必须生效的纠正不因降级失效。
- 所有写操作具备 owner、版本、幂等或明确单写边界；迟到结果不能跨世界、草稿或编辑会话发布。
- 导入内容不执行，附件和 ZIP 经过安全限制，导出不携带凭据与运行数据。
- 开放型连续路线、完整浏览器路径、全仓回归、race/vet、前端检查和正式构建有记录。
- 真实模型不可用时如实标记质量待补；不得把受控模型结果写成真实 Provider 验收。

M3 玩家体验验收只要求：从首页发现并开始一个开发者准备好的故事；使用默认主角或修改姓名与简介；自由输入或使用建议；经历一次人物自行离开与玩家自行前往；另存、重启后继续。创作、导入与导出属于开发者工具，不进入玩家验收路径。M4 在 M3 工程收口后再处理桌面安装、服务器账户、部署、跨设备和备份恢复。

## 18. AI 开发执行合同

接手开发的 AI 应先读取 `AGENTS.md`、本文、产品说明、总体技术方案、开发执行指南和开发状态，然后检查工作树与现有 M3 相关代码。已有代码只有在实现、测试和界面均符合本文时才能计入完成；不得为了套用方案还原用户或其他开发会话的改动。

按 U0–U6 顺序持续实现、验证和修复。不要停在类型、路由、页面框架或测试桩；每个单元形成可运行的纵向功能，并按独立工作单元本地提交。不得执行 `git push`。不得调用收费模型进行常规程序验证；真实模型不可用时继续所有不依赖它的开发，并把质量验证明确留待环境恢复。

交付时更新开发状态并创建 `records/M3-验收记录.md`，分别列出确定性测试、浏览器验证、真实模型验证与用户体验验收，不用一种证据替代另一种。

### 18.1 实现任务与依赖

| 任务 | 主要模块 | 依赖 | 验证出口 |
| --- | --- | --- | --- |
| T0 收口现有建议代码、记忆投影与空间状态 | `storyapp`、`storyapi`、游玩页 | 无 | U1 全部测试与浏览器路径；整理滞后、窗口降级、召回去重与真实覆盖水位回归；位置模型、同场推导与旧档兼容回归 |
| T1 主角资料（剧本默认 + 当前世界修改） | 应用库、`storyapp` | T0 基线稳定 | owner/version、固定主角拒绝 |
| T2 草稿编辑与双视图（开发者工具） | 内容组件、API、创作页 | T1 | 隐藏字段正反向测试、并发编辑 |
| T3 发布目录与资源快照 | 包加载、内容根、世界创建/另存 | T2 | 崩溃点恢复、旧世界资源、发布幂等与请求身份 |
| T4 导入与导出（开发者工具） | 内容组件、ZIP/JSON 适配、创作页 | T2、T3 | 恶意 fixture、WIA 往返 |
| T5 整合体验与开放型连续路径 | 前端、示例包、验收文档 | T3、T4、T0 的空间状态 | 完整浏览器路径、连续路线、全量回归 |

本阶段以顺序实现为默认，原因是 T1–T5 都会修改 `storyapp` 数据结构、应用库迁移或同一前端顶层状态。不要在多个工作树同时修改这些共享边界。schema 与 API 冻结后，示例内容和浏览器用例可以与后端收口并行；合并前必须重新运行 schema fixture 与正式前端构建。

T0 的空间状态先于其他内容任务：同场判定会改变感知分发与场景投影，越晚接入，后续任务的回归越难定位。位置模型与"由位置推导同场"必须一起交付，不发布"有位置字段但在场仍由模型名单决定"的中间版本。

U0 的记忆投影修复先于 U1 收口：行动建议与正文、NPC 共用 `withLongMemory` 投影，整理滞后时同一缺陷会同时影响三者。该修复只调整请求材料的选入与降级，不改变 `memory_digests` 覆盖水位、不新增 schema、不新增 Agent；合同见[总体技术方案](../总体技术方案.md#91-原始经历与主观整理)与 [M2 技术方案](M2-世界剧情与长期记忆.md#52-整理与上下文)。建议调用不依赖主回合先行整理成功，投影层自身即可降级。

每项任务先交付纵向可运行路径，再进入下一项。禁止先批量建立所有表、路由和空页面后集中补行为；这会让版本、权限和恢复问题在阶段末同时爆发。
