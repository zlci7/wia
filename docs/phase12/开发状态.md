### 续接要点

- 基线：一次前台完整运行 `go test ./... -count=1 -v`；权威判据为源码测试函数数（当前 **1432** = 1423 基线 + 9 个依赖守卫；2026-09-29 复核）。**不要用后台任务跑基线**，R0 曾因此丢掉 11 个包的输出。
- 阅读入口：一轮故事的主流程在 `backend/internal/storyapp/run.go` 的 `executeTurn`；它是一个按顺序调用的阶段流水线。
- 下一步（**M3 第二部分：切换 `InTx`**）：`storage.WorldTx` 与 `WorldStore.InTx` 已就位，`publishDigest` 已改用 CAS，`memory_jobs` 的写入已具名化。**剩余工作是把 `MetaGetTx`/`MetaSetTx` 的 30 余处调用点与承载它们的 7 个函数签名（`initializeWorld`/`commitTurn`/`cloneWorld`/`updatePlayerProfile`/`promoteBystander`/`updateNarrativeSettings` 等）改成 `InTx` + `WorldTx` 形参**——这些函数的 `tx` 参数必须与 11 处 `BeginTx`/`commit`/`rollback` 结构**同时**改造，调用方共 50 余处，因此单独一个工作单元。完成后才有 `tx.SetMeta`/`tx.GetMeta` 的全面采用。之后：`worldSnapshot` → `turn.TurnSnapshot` → `executeTurn`。
- **storage 的事务端口（M3 落地）**：`storage.WorldTx` 只提供**具名持久化操作**（`GetMeta`/`SetMeta`/`InsertCorrection`/`UpdateMemoryJob`/`SupersedeOpenMemoryJobs`/`InsertMemoryJob`/`AppendMemorySourceIfAbsent`/`CountMissingEventSources`），**不暴露 `Exec`/`Query`/`QueryRow`**。`WorldStore.InTx(ctx, fn)` 负责 begin/commit/rollback，fn 返回非 nil 即回滚并原样返回该错误。
- **边界判据（M3 由评审定下，选项 C）**：**领域名词可以进 storage（表示"存了什么"），领域决策不能进（为什么写、何时写、哪些写必须同事务）**。检验方式：*"这个函数删掉 SQL、换成 PostgreSQL 后，名字和参数是否仍然合理？"*——`InsertCorrection`/`UpdateMemoryJob`/`CompareAndInsertMemoryDigest` 合理（持久化契约）；`RebuildMemory`/`ApplyCorrection`/`IndexMemorySources` 不合理（业务行为）。**事务范围由调用方拥有，提交由 `InTx` 保证。**
- **CAS 是 storage 原语**：`CompareAndInsertMemoryDigest` 检查 `context_epoch`、scope 当前 revision、source head 后原子插入；前置条件不成立返回 `MemoryDigestConflict` 结构体，**由调用方判断这是冲突、重试还是忽略**。选名 `CompareAndInsert` 而非 `Publish`（后者带业务语义）。
- **`memory_jobs` 的写入方式**：单语句更新用 `store.UpdateMemoryJob(ctx, storage.MemoryJobUpdate{...})`——**不要长成 `MarkRunning`/`MarkFailed`/`MarkCompleted` 一族**；带状态前置条件的用**具名条件写**（`FailMemoryJobIfOpen`/`RequeueMemoryJobIfFailed`），`WHERE status IN (...)` 属存储层前置条件、不泄漏成业务侧 SQL。
- **storage 的中性记录类型（M2 落地）**：`storage.CorrectionRecord`/`MemorySourceRecord`/`MemoryDigestRecord`/`MemoryJobRecord` 只有列名、没有领域含义；`memorymodel.Correction`/`MemorySource`/`MemoryDigest`/`MemoryJob` 与之对应。**转换放在 `storyapp/record_adapters.go`**——`storage` 不认识纠正语义、`memorymodel` 不做 I/O，中间那层必须有人同时命名两者。**不要把转换放进 `memorymodel`**（会变成懂持久化的领域包），**也不要把领域类型放进 `storage`**（守卫会失败）。
- **Pack DTO 与运行定义的分界（已落地）**：`content.PackLocation`/`PackBystander`/`GameSummary`/`PlayerDefaults` 是**外部文件格式**，只在加载/校验/导入导出/草稿回读里出现；`story.Location`/`Bystander`/`Summary` 是**归一化后的运行定义**，由 `storyapp/definition.go` 的 `storyLocations`/`storyBystanders` 产出。**不要再让运行侧引用 `content` 的类型**——`story/definition_boundary_test.go` 会因 `story` 包出现 `content.` 字样而失败，`story/boundary_test.go` 会因 import `content` 而失败。
- **`CoverURL` 不属于运行定义**：它是一条 HTTP 路由，原先被写进 `gameDefinition.Summary` 并随世界冻结。现在目录条目（`Modes`/`DefaultMode`/`CoverAlt`/`CoverURL`）放在 `loadedPack.Catalog`，`Games()`/`Game()` 返回它；`WorldGame()` 优先取已安装 pack 的 `Catalog`，pack 不在时从 `story.Summary` 兜底再覆盖为 `/api/v1/worlds/<id>/cover`。**新增目录字段时放 `Catalog`，不要加回 `story.Summary`。**
- **`bystander_refs` 的存储形状已改为 `story.Bystander`**：两者 JSON 标签相同，旧存档读得进来；写入侧写运行定义形状，使存储不再依赖 pack 格式。
- **草稿回读读 `pack.Story`（原始 pack JSON），不从运行定义反序列化**：编辑一个包不该丢掉运行时不用的字段，草稿是**包的视图**。
- **四层归属（已定，选项 A + 新包 `story`）**：`content` 拥有外部包格式（可删除）、`story` 拥有归一化后的不可变运行定义、`world` 拥有可变/已提交的世界词汇、`plot` 拥有世界推进规则；`turn` 消费 `story`+`world`+`plot`。依赖是 `content → story`、`turn → story`、`content → plot`、`story → plot`、`plot → world`。**不要放 `world`**（会形成 `world → plot`，破坏"world 只依赖标准库"），**也不要放 `content`**（会让 `turn → content`，使内容工具成为游玩内核的 runtime dependency）。包名**不用 `definition`**：`backend/internal/definition` 是 R5 待删的旧包，同名会重演 `memory` 的混淆坑。
- **⚠️ 新代码不得落进 R5 待删的旧包目录。** `backend/internal/` 下并存两代实现，包名可能相同：`backend/internal/memory` 是旧 Game Runtime 包（38 个文件，R5 删除），WIA 的 memory 类型当前在 `backend/internal/memorymodel`。**两者都是 `package memory`，编译与 `go doc` 都不报冲突**——`go doc ./backend/internal/memory` 会把新旧类型混在一起列出来。开工前必须确认目标目录是新的还是待删的，并核对类型名未被旧包占用。**R5 删掉旧 `memory` 后，`memorymodel` 应合并进 `backend/internal/memory`。** 同类检查：`agent`/`context`/`task`/`tool`/`gateway`/`httpapi` 等目录也全是旧的。
- **`plot` 与 `content` 的分工（已定，选项 B）**：`content` 负责"内容包是否合法"（JSON/schema/字段类型/文件大小/资源路径/NPC 与地点引用是否存在），`plot` 负责"剧情定义本身是否合法"（节点、依赖、时间、条件、状态枚举）。依赖是 `content → plot`、`turn → plot`；**`plot` 永不 import `content`**。运行时入口调用 `plot.Validate(def, progress)`，发布入口只调 `plot.ValidateDefinition(def)`——**不要为了校验定义而伪造一个 progress**，这正是拆分的原因。
- `plot` 返回自己的 `ErrInvalidDefinition`/`ErrInvalidProgress`，不再返回 `ErrStorageUnavailable`：同一个剧情校验失败在发布入口是"内容非法"、在运行入口是"存档不可读"、在 HTTP 层是状态码，**映射属于各入口**。
- 已建立八个底层包：`wire`、`world`（只依赖标准库）、`plot`（只依赖标准库）、`memorymodel`（只依赖标准库，R5 后并入 `memory`）、`story`（只允许 `world`/`plot`）、`storage`（只允许 `world`/`wire`；`.Database()` 计数只降不升）、`turn`（只允许 `world`/`wire`/`model`/`storage`）、`content`（允许 `world`/`plot`/`wire`，**禁止 `storyapp`/`turn`**——删掉整个内容工具后玩家仍应能游玩）。**八者各有一条依赖守卫测试。**
- 下一步：**T1 建立 `turn` 包**。storage 的 S1 收口已完成——13 个通用持久化函数变成 `WorldStore` 方法、3 个读函数的参数从 `*sql.DB` 换成 `*storage.WorldStore`、43 处 `Database().Close()` 换成 `store.Close()`。**migration debt 测量**：`storyapp` 的 `.Database()` 生产用法 **149 → 61**、测试 111 → 104，由 `storage/escape_hatch_test.go` 守住"只降不升"。剩余 61 处集中在尚未建立 owner 的模块路径（`memory_jobs` 19、`world_ops` 12、`run` 10、`corrections` 9、`suggestions` 9），**随各自模块迁移时自然下降，不要现在强行清零**——加 `Exec`/`Query`/`BeginTx` 通用代理只是伪封装，把各模块的写事务吸进 storage 则会让 storage 变成新版 `storyapp`。
- **事务边界的原则**：模块拥有事务的**业务**边界，storage 拥有**持久化实现**。所以 `MetaGetTx`/`MetaSetTx` 保持收 `*sql.Tx`；将来推荐 `store.InTx(ctx, func(tx storage.WorldTx) error { ... })` 这种 transaction port，而不是让 `memory` 直接写 `UPDATE memory_jobs`，也不是让 storage 理解"重建记忆"这个业务。
- 仍留在 `storyapp` 且依赖 turn 侧类型、**要等 `turn` 建立后才能归位**的：`loadWorldSnapshot`（一轮回合的冻结输入组装，将来叫 `TurnSnapshot`）、`initializeWorld`、`commitTurn`、`cloneWorld`。业务判定同理留在上层：`count > 0 → ErrWorldBusy`、`memoryReady` 的语义、版本冲突判定。**不因为函数里含 SQL 就归 storage**：storage 提供事实，上层决定事实意味着什么。注意这四者**最终归属可能不同**（`loadWorldSnapshot`→turn、`commitTurn`→turn 编排 + storage 原语、`initializeWorld`→world/application 创建、`cloneWorld`→world 操作 + storage 复制），不要因为历史上同在一个文件就一起搬。

- **改写 Go 源码的八条硬规矩**（每条都由一次实际事故换来）：① 不要用 `Get-Content -Raw` / `Set-Content`——它们按系统代码页解码再编码，会把所有非 ASCII 字面量写成乱码，而行数、diff 规模、字节数都看不出异常；用 Go 程序或 `edit` 工具。② 不要靠"列 0 的 `}`"判断函数体边界，按 `ast.Decl` 删除。③ 判断标识符是不是目标符号，用它绑定的 `ast.Object` 是否指向**包级**声明（函数、类型、常量都算，不只是类型）；局部同名变量必须放过。④ 判断结构体字面量的字段名要按**包**（而非按文件）收集类型名；嵌入字段名（无冒号）也要保护。⑤ 不要手工枚举"能放表达式的位置"——漏一个就静默失效（第一版漏了 `switch` 的 `case`）。⑥ **先限定引用、再删除定义**：顺序反了会产出 `wiaworld.X` 这种包里不存在的成员。⑦ 重写 import 块的工具**必须保留它不认识的导入**，否则会删掉 `embed`/`zip`/`slices`/`jsonschema`。⑧ **不要为搬运而手抄**：schema 这类长字面量要从 Git 原文按字节提取，再用字符串包含关系验证；函数用 `tools/move` 逐字搬。⑨ 正则替换要限定接收者：`\.path\b` 会误伤 `DiagnosticLog.path`，`"app.db"` 会被改成字符串里带方法调用的怪东西。
