# R3 耦合测量与抽取顺序

状态：**分析结论，未执行任何代码搬移**。本页是 R3 开工前的测量记录，回答一个具体问题：`storyapp` 的每项职责对包内私有符号的依赖有多深，因此按什么顺序抽取才不需要"为了搬而导出"。

测量工具：`tools/coupling/`（独立 module，不进入主构建），用法见第 8 节。可重新生成的数据在第 3 节与 [原始测量输出](R3-耦合测量.md)。

## 1. 测的是什么，为什么

架构方案第 8 节 R3 要求按 `context` → `agent` → `memory` → `plot` → `content` 顺序抽取。但跨包搬移在 Go 里有一条硬成本：**小写标识符包私有**。任何一段代码被搬到新包，它用到的 `App` 私有字段/方法、以及其它文件里的私有类型与函数，都必须先导出或重排归属。因此"抽哪个先"的真正判据不是模块听起来多外围，而是**跨边界要导出多少东西**。

本页对 `storyapp` 的全部非测试文件统计：

1. 每个文件直接使用了多少个 `App` 私有字段与方法（`a.X`）；
2. 每个文件引用了**其它** `storyapp` 文件的哪些私有符号（跨文件私有出/入边）；
3. 各候选模块的汇总与其中的最坏文件。

"私有"指未导出。已被 `storyapi` 使用的导出符号不计入——它们本来就能跨包引用。

## 2. 结论摘要

1. **耦合不在 `App` 上，在"共享词汇"上。** 44 个非测试文件里，`App` 私有成员使用最多的是 `publish.go`(34)、`run.go`(33)、`app.go`(30)、`world_ops.go`(27)；但真正横跨全包的是一批**自由函数与类型**：`definition.go` 被引用 **107** 次（22 个文件），`store.go` 被引用 **287** 次（31 个文件），`run.go` 被引用 **67** 次（8 个文件）。这三个文件不是"某个模块"，是 R3 的**词表层**，它们不先拆，抽任何一个模块都要顺手导出十几个符号。
2. **抽取成本 = 跨边界的私有符号数。** 只要把整个子集群**一次整体**搬走，集群内部的 `App` 方法互调就退化成普通包内调用，不需要导出。逐文件搬（先搬 `content_material.go`，再搬 `content.go`）才会把成本放大成"导出十几个 `App` 方法"。
3. **`content` 不是最软的，是依赖最多的。** 11 个文件 4073 行、`App` 私有成员 79 个（全部模块最高）。它在"看起来外围"和"测得耦合最深"之间差得最远，因此**不能开工就搬**。
4. **`promotion.go` 不是内容模块。** 它 568 行，29 次引用 `store.go`、由 `world_ops.go` 使用，是**世界变更路径**（与 `SaveAs`/`ActivateWorld` 同类），不是内容工具。按文件归属表当内容一起搬会连带拖出世界写入逻辑。
5. **`tokenestimate` 已是新旧共用，不是"待迁移算法"。** R0 保留表把 token 估算列为旧 `context` 里值得迁移的算法；实测 `tokenestimate` 包已被新 `storyapp/context_composer.go` 与旧 `context` 同时引用，**新实现侧已有覆盖**，R3 不需要再迁一遍。（详见第 6 节）
6. **`turn` 收尾前必须先动 `storage` 一小块。** `run.go` 对 `store.go` 有 43 次私有引用（`loadWorldSnapshot`、`commitTurn`、`readRun`、`metaGetTx`…）。架构方案把 `storage` 排在 R4，但 `turn/` 要成立就无法等 R4 全量收口。R3 需要提前切一块**最小存储切片**（世界库读写与运行记录），而不是把 R4 整体前移。

**只被搬移后成为跨包导出 API 的符号引用（这类引用不构成障碍，新包本来就该导出 `SceneView`、`Snapshot` 这类东西）**

```text
content_schema.go(60 行)   json.go(69 行)
```

**例外：两个"词表"文件的入向引用量级完全不同，必须先拆（见 3.4）**

```text
definition.go(入向 107)   store.go(入向 287)
```

读法：`memory_stream.go` 的 31 次入向引用、`scene_context.go` 的 36 次，都是"新模块对外提供的类型与函数"，导出它们是正常的结果；而 `definition.go` 的 107 次、`store.go` 的 287 次说明它们承载的是**全包共用的词汇**，不属于任何一个待抽模块，留在原地会让每一步都要重新决定它们的归属。

### 3.4 三个"词表"文件：它们挡住谁

**`definition.go`（59 行，无 `App` 依赖，被 22 个文件引用 107 次）**

提供 `cleanText`、`gameDefinition`、`characterByID`、`findSceneCharacter`、`sceneCharacters`。`cleanText` 一个函数被 15 个文件使用。它是纯函数与纯领域类型，**可以最先搬，且搬完立刻降低其它所有文件的跨包成本**。

**`store.go`（906 行，被 31 个文件引用 287 次）**

其中 40 次引用只是 `nowText()`（15 个文件）、`marshalJSON()`、`boolInt()` 这类纯工具；其余是 `openWorldDB`、`loadWorldSnapshot`、`commitTurn`、`metaGet/metaGetTx/metaSetTx`、运行记录读写等真正的存储访问。**把纯工具与存储访问分开，是 R3 成本最低的一刀。**

**`run.go`（1648 行，被 8 个文件引用 67 次）**

被外部引用的私有符号：

```text
类型     turnIntent, turnOutput, npcDecision, npcStageInput, hostResult, hostActionResult, narrativeEvent
函数     characterIDs, characterDisplayName, eventIDs, eventByID,
         generateJSON, generateJSONCheckedMetrics, structuredTurnOutputTokens,
         appendNPCDecisionOutput, appendHostOutcomes, validateSceneCharacters,
         coordinationDecisionContext, coordinationContinuity, publicCharacterContext,
         availableCharacterIDs, describeRecipient, formatBystanders
```

引用方：`context_material.go`(21)、`plot.go`(26)、`scene_context.go`(9)、`generated_events.go`(3)、`suggestions.go`(3)、`context_composer.go`(2)、`memory_context.go`(2)、`dialogue.go`(1)。

也就是说：`plot`、`context`、`memory`、`agent` 四个模块**都在等 `run.go` 交出它们的领域词汇**。这是 R3 的真正关键路径。

### 3.5 `content` 的耦合结构

`content` 集群的 79 个 `App` 私有成员使用里，**大部分是集群内部互调**（`publish.go` 调 `startPublish`/`runPublish`/`completePublish`/`buildPackage`/`existingRevision` 等，它们都在同一集群的文件里）。真正跨出集群的只有很小一组：

```text
App.contentRoot()           内容根路径
App.newID(prefix)           标识生成（还被 app.go、personas.go 用）
store.nowText()             时间戳
store.metaGet/openWorldDB   发布修订的元数据
definition.cleanText        文本清洗
contentSchema/usageSchema   schema 片段
App.pack/setPack/packs      已安装包目录
```

因此 `content` 的正确做法不是"等它变软再搬"，而是**整块搬 + 在边界上定义一个很窄的宿主接口**（内容根、标识生成、包目录、时间戳）。逐文件搬会把 34 个成员一次性摊到公共接口上。

但 `content` 内部有两个方向相反的依赖需要先裁定，否则整块搬过去就会形成环：

- `packs.go`（包加载/校验）依赖 `plot.go` 的 `validatePlot`、`clockMinute` 与 `generated_events.go` 的 `validateEventPolicy`——**剧本包校验要用剧情规则**；
- `promotion.go` 反向依赖 `corrections.go` 的 `memoryReady`，并大量写世界库。

前者说明"剧本包校验"要么留在剧情侧，要么把剧情校验下沉为纯函数；后者说明 `promotion.go` 应归世界变更路径。这两条必须在动 `content` 之前定，不能搬到一半再决定。

### 3.6 `memory` 的耦合结构

`memory` 是**内部分层最干净**的模块：

```text
memory_stream.go   读取来源与投影，零 App 依赖
memory_evidence.go 协调证据，零 App 依赖
memory_context.go  长期记忆与整理，只用 logger + contextGenerator
memory_jobs.go     后台重建作业，使用 14 个 App 成员（worker 生命周期）
corrections.go     纠正，只用 worldRecord/worldRuntimeFor/startMemoryRebuild
memory_api.go      对外读取
```

难度集中在 `memory_jobs.go`（`closing`、`copyCtx`、`copyWG`、`memoryWorkers`、`memoryWake`、`modelMu`、`generator` 等进程级生命周期字段）。**办法是把作业生命周期留在组合根，`memory` 只接收"给我这个世界的重建步骤"。** 这与 `content` 用窄宿主接口是同一个手法。

### 3.7 `plot` 的耦合结构

```text
plot.go ↔ run.go        26 次（appendHostOutcomes、appendNPCDecisionOutput、hostActionResult、
                              npcDecision、npcStageInput、turnOutput、generateJSON…）
generated_events.go     需要 hostResult/turnOutput 与 structuredTurnOutputTokens
event_dependencies.go   零 App 依赖
settings.go             被 6 个模块引用（叙事设置校验/指令）
behavior.go             叙事行为策略，零 App 依赖
```

`plot` 与 `turn` 之间是**双向**的（`turn` 调 `advancePlot`，`plot` 调 `turn` 的输出类型与追加函数）。这是 R3 里除 `storage` 之外第二个必须在动代码前裁定的边界：`turn` 必须把"输出累积"的所有权拿回来，`plot` 只返回自己的结果类型。

## 4. 与原定顺序的差异

> **顺序已更新**：第 1 步已执行（见第 11 节），实际切分与下表有两处不同——纯工具原来计划并入 `world`，实测后单独建立了 `wire` 包（它们不是领域概念）；`cleanText` 的引用数从原先记录的"107 次入向"（那是 `definition.go` 整个文件的口径）更正为 **70 处调用**。

| 原定 | 测量后 | 差异原因 |
| --- | --- | --- |
| `context` 第一 | `context` 的**材料组装**确实可以先搬（`App` 依赖只有 2），但它 73 次出向私有引用里 21 次指向 `run.go`，必须先拆词表 | 计划没算"跨边界要导出多少"这一项 |
| `content` 最后 | `content` 的**依赖最多**（79），但它的耦合是**集群内部**的，整块搬 + 窄宿主接口即可；不该按"从外围到内核"排最后 | "外围"不等于"低耦合" |
| `memory` 最后最难 | `memory` 内部分层最干净，真正难的只有 `memory_jobs.go` | 模块级判断掩盖了文件级差异 |
| `storage` 在 R4 | `turn` 依赖 `store.go` 43 次，R3 必须先切一块最小存储 | R3/R4 的边界需要按依赖而不是按阶段号划 |

## 5. 建议的抽取顺序

原则：**先搬没有任何私有依赖的东西，再搬只依赖已被搬走的东西的东西。** 每一步以"这一步不需要导出 `App` 成员"为达标条件。

### 第 0 步（前置，不是搬移）：冻结并复核基线

- 复核：全仓测试函数 1423（`grep -c '^func Test'`），`go test ./... -count=1` 26 包 0 失败。**本页已复核通过**（2026 年执行，见第 3.1 节）。
- 用途：此后每一步都对比"测试函数数不下降、0 失败"。

### 第 1 步：拆词表

把"恰好都在用"的东西从它当前所属的文件里拿出来，放到它们真正的归属：

| 内容 | 现位置 | 去向 | 引用规模 | 状态 |
| --- | --- | --- | --- | --- |
| `cleanText` | `definition.go` | `wire`（文本规范） | 70 处调用 | **已完成** |
| `nowText`、`marshalJSON`、`boolInt` | `store.go` | `wire`（纯工具） | 54 / 32 / 3 处调用 | **已完成** |
| `newID` | `app.go` | `wire`（标识生成） | 生产 8 处 + 测试 | **已完成** |
| `characterByID` | `definition.go` | `world`（纯规则） | 12 处 | 随领域类型一起搬 |
| `findSceneCharacter`、`sceneCharacters` | `definition.go` | `world`（纯规则） | 各 2 处 | 随领域类型一起搬 |
| `containsID` | `scene_context.go` | `wire` 或 `world` | 20 处 | 下一步 |
| 领域类型（`Character`/`Event`/`Perception`/`Memory`/`Message`/`Run`/`WorldSummary`） | `types.go` | `world` | `Run` 253 处、`Character` 231 处、`Event` 136 处、其余各 25–89 处 | 下一个工作单元 |
| `gameDefinition`、`loadedPack`、`worldSnapshot` 等**契约结构** | `definition.go`/`packs.go`/`store.go` | `world` 或 `content`（按第 3.5 节裁定） | 需要一次归属裁定 | 待裁定 |

`wire` 与 `world` 的分界：**领域概念进 `world`，命名了概念之后剩下的东西进 `wire`。** `wire` 只依赖标准库，被所有叙事包依赖；把 `cleanText` 放进 `world` 会让"只想清洗一个字符串"的包必须依赖领域类型所在的包。

领域类型是**独立的工作单元**：约 1300 处引用、约 40 个文件，属于纯机械改名，改动面广但不改语义。它与第 1 步的其余部分分开提交，避免让一次改动同时承担"新增 `wire` 包"和"全包类型改名"两件事。

`world`/`wire` 的建立与领域类型提取，对应架构方案 R2 第 2 步里"领域类型移入 `world/`"的内容，是同一件事。

### 第 2 步：最小存储切片

把 `store.go` 拆成两块：

- **纯工具**（已在第 1 步移走）；
- **世界库访问**：`openWorldDB`、`loadWorldSnapshot`、`loadEvents`、`loadCharacters`、`loadDialogue`、`metaGet/metaGetTx/metaSetTx`、`commitTurn`、`readRun/readRunByRequest/scanRun/updateRunStatus/countActiveRuns`、schema 与迁移。

后一块进入 `storage`，作为 R4 的**第一刀**，而不是等 R4 全量收口。R4 剩余部分（`app.db`、存档复制、内容 schema、迁移）届时并入同一包，不需要第二次搬家。

不做这一步，`turn/` 无法成立。

### 第 3 步：`context`（材料组装 + 预算）

搬 `context_composer.go`、`context_material.go`、`context_sources.go`（856 行，`App` 依赖仅 2 个：`logger`、`userID`）。

- 对外入口按架构方案 6.7 收敛为 `Build(BuildRequest{Purpose, Recipient, World, Stage})`，不保留 `BuildNPC()`/`BuildNarrator()` 这类函数集合。
- `scene_context.go`（场景成员、场景来源、场景更新）建议归 `world` 或 `turn`，**不归 `context`**：它是场景规则与回合投影，不是"这次调用该看到什么"。
- 边界裁定**已由实测回答**（见第 11 节）：`context_composer.go` 与 `context_sources.go` 不涉及任何 `turn` 契约类型，`ContextScope` 只用 `Purpose`/`Recipient`/`Stage int`/`Epoch` 这类扁平字段。真正碰 `turnIntent`/`npcDecision`/`npcStageInput` 的是 `context_material.go` 的 `composeCoordination`/`composeNPC`/`buildNPCPrompt` 三个**材料构造器**——它们属于 `turn`/`agent`，不属于通用 `context`。因此 `context` 不需要 `turn` 的类型，也不形成反向依赖。

### 第 4 步：`agent`（人物提示词与决策）

搬 `dialogue.go`、`behavior.go` 与 `run.go` 里的 `composeNPC`、`decideNPCs`、`narrativeEvent` 等人物决策部分，以及 `definition.go` 里的人物提示词素材。

- 架构方案要求 `agent` 不写数据库；`decideNPCs` 当前不写库，只调模型，符合。
- `agent` 需要 `turn` 传入的感知与阶段输入——即第 3 步同一类边界裁定。
- 只有 98 行独立文件，其余逻辑仍在 `run.go` 里；这一步的实际工作是**从 `run.go` 里切出人物决策**，不是搬两个小文件。

### 第 5 步：`memory`（来源、整理、检索、纠正）

搬 `memory_stream.go`、`memory_evidence.go`、`memory_context.go`、`corrections.go`、`memory_api.go`（1737 行，`App` 依赖 23 个，集中在一个文件）。

- **`memory_jobs.go` 的作业生命周期留在组合根**：`memory` 只暴露"重建一步"的纯函数，`App` 负责 worker 的启动、唤醒与关闭。这一条决定了 `memory` 是否需要导出 `App` 字段。
- 同时执行 R0 保留表要求的**旧 `memory` 包逐项过筛**（167 个测试）：先确认哪些行为在新实现里已有等价覆盖，再随包删除。**迁移完成前不得删除旧包测试。**

### 第 6 步：`plot`（时间、条件、计划、生成事件）

搬 `plot.go`、`generated_events.go`、`event_dependencies.go`、`settings.go`、`behavior.go`（1277 行，`App` 依赖 12 个）。

- 前置裁定（第 3.7 节）：把"输出累积"的所有权交回 `turn`。`plot` 只返回 `plot` 自己的结果类型，不再调用 `appendHostOutcomes`/`appendNPCDecisionOutput` 这类 `turn` 的累积函数。
- 同时执行旧 `context` 包（114 个测试）与旧 `memory` 包剩余部分的过筛结论落地。

### 第 7 步：`content`（开发者内容工具）

1. **`agent` 的方向裁定不可中途改。** `context` 的裁定已由实测确定（第 3 步）；剩下的是 `agent`：人物提示词与决策需要 `turn` 的感知与阶段输入。与 `context` 同理，材料构造留在 `turn`/`agent` 侧，通用组装留在 `context` 侧，则不需要反向依赖。**必须在动第 4 步之前定一次。**

**本批次的四个工程教训**（工具已按此实现）

1. **`Set-Content` / `Get-Content -Raw` 会破坏 UTF-8。** 它们按系统代码页（本机为 GBK）解码再编码：写回后所有中文提示词与文案变成乱码，**行数、diff 规模、字节数都看不出异常**。第一版替换脚本因此损坏了 9 个文件，必须从 Git 整体恢复。结论：任何改写 Go 源码的动作都要用 Go 程序或 `edit` 工具，它们写 UTF-8。
2. **`Set-Content -NoNewline` 会把 CRLF 换成 LF**，于是字符串字面量被拆行，报"newline in string"。行尾也要显式保留。
3. **不能靠"列 0 的 `}`"找 Go 函数体结束**：第一版删除逻辑因此误删了相邻的 `metaGet`。按 `ast.Decl` 删除，输出交给 `go/printer` + `gofmt`。
4. **AST 改写要按"包"而不是"文件"判断结构体字面量。** `ContextScope` 在一个文件里声明、在另一个文件里使用；按文件收集类型名会漏掉跨文件的那一半，把 `Run: ...` 这样的**字段名**误改成 `wiaworld.Run:`。同理，判断一个标识符是不是类型，要用它绑定的 `ast.Object` 是否指向类型声明，而不是靠名字。

### 第 6 步前置：`plot` 基础类型与纯校验：2026-09-29

**归属由一次评审定下（选项 B）**，并写成一句规则：

> **`content` 负责"内容包是否合法"，`plot` 负责"剧情定义本身是否合法"；`content` 在加载/发布剧情内容时调用 `plot` 的纯校验函数。`plot` 永不 import `content`。**

依赖方向是 `content → plot`、`turn → plot`。选 B 而非"校验下沉到 content"的理由是**一种能力只有一个权威来源**：若 content 自己实现依赖/环/时间校验，运行时的 plot 又理解一遍，早晚出现"发布允许、运行拒绝"或"运行时支持新规则、content 忘了同步"。

**按评审要求把校验拆成两个**（原来是一个 `validatePlot(def, progress)`）：

| 函数 | 回答什么 |
| --- | --- |
| `plot.ValidateDefinition(def)` | 剧情图本身是否合法：revision、节点数 1..32、ID 唯一、`After` 只能引用更早的节点、`AtMinute` 非负、`Condition`/`Development`/`Audience` 必填 |

| `plot.Validate(def, progress)` | 上面两者，运行时读档用 |

**这次修掉了一处真实的设计缺陷**：`packs.go` 与 `generated_events.go` 原来为了只校验定义，不得不伪造一个进度对象——

```go
plot.Validate(*p.Plot, plot.Progress{Version: 1, Nodes: map[string]plot.NodeState{}})
```

现在直接调 `plot.ValidateDefinition(*p.Plot)`。这正是拆分的价值。

**错误词汇归 plot**：新增 `plot.ErrInvalidDefinition` 与 `plot.ErrInvalidProgress`，不再返回 `ErrStorageUnavailable`。同一个剧情校验失败，在发布入口是"内容非法"、在运行入口是"存档不可读"、在 HTTP 层是某个状态码——**映射属于各入口**。已核对：没有测试依赖原来的映射。

**工程教训（第十二条）**

12. **正则替换要避开声明本身。** 把 `packSchemaV1` 全局改成 `content.SchemaV1` 时，这串替换也命中了 `const` 块里的**声明行**，产出 `content.SchemaV1 = 1` 这种非法语句。修法不是再补一个正则，而是**删掉整个 const 块**（它已随类型搬到 `content`），再替换使用点。判断标准：替换目标如果是"名字"，先确认这个名字在哪些位置是**被声明的**，而不只是被引用的。

### memory 服务层 M3：事务端口与具名写（第一部分）：2026-09-29

**边界由评审定下（选项 C）**，写成一句可操作的判据：

> **领域名词可以进入 storage（表示"存了什么"），领域决策不能进入 storage（为什么写、什么时候写、哪些写必须在同一事务发生）。**

判据的检验方式也已记录：**"这个函数删掉 SQL、换成 PostgreSQL 后，名字和参数是否仍然合理？"** `InsertCorrection`/`UpdateMemoryJob`/`CompareAndInsertMemoryDigest` 仍然合理，所以是持久化契约；`RebuildMemory`/`ApplyCorrection` 通常不合理，所以是业务行为。

**新增 `storage.WorldTx`**（`storage/tx.go`）：一个薄包装 `*sql.Tx` 的类型，**只提供具名持久化操作，不暴露 `Exec`/`Query`/`QueryRow`**。理由：暴露裸 SQL 的"事务端口"是伪封装——看起来是边界，实际把语句放回了业务文件。未做成 interface（当前只有 SQLite 一个实现，且是 internal；等真有第二个实现再抽）。

| `WorldTx` 上的具名操作 | 说明 |
| --- | --- |
| `GetMeta` / `SetMeta` | **取代 `MetaGetTx`/`MetaSetTx`**——把 `*sql.Tx` 从 storage 的 API 表面彻底移除（过渡设计就此结束） |
| `InsertCorrection` | 写一条纠正 |
| `UpdateMemoryJob` | 按字段写 job |
| `SupersedeOpenMemoryJobs` | 把未完成的 job 标为 superseded |
| `InsertMemoryJob` | 写一条重建 job |
| `AppendMemorySourceIfAbsent` | 按来源 id 幂等追加（序号在同语句内取，避免并发抢号） |
| `CountMissingEventSources` | 前置条件查询；**表名取自固定集合**，防止退化成任意查询 |

`WorldStore.InTx(ctx, fn)` 负责 begin/commit/rollback：**fn 返回非 nil 即回滚，并把该错误原样返回**——这样调用方可以用自己的哨兵错误表达业务冲突，storage 不需要知道它们是什么意思。**事务范围由调用方决定，提交由 `InTx` 保证。**

**具名写操作允许领域名词**：`InsertCorrection`/`UpdateMemoryJob`/`InsertMemoryJob` 里的 `Correction`/`MemoryJob` 正是"数据库里有这种记录"的意思，不表示业务流程。被禁止的是 `ApplyCorrection`/`RebuildMemory` 这类名字——它们表达的是流程。

**CAS 成为 storage 原语**：`CompareAndInsertMemoryDigest`。它检查 `context_epoch`、该 scope 的当前 revision、当前 source head，然后原子插入；**前置条件不成立时返回 `MemoryDigestConflict`（结构体，不回滚错误）**，让调用方判断这是冲突、重试还是忽略。`publishDigest` 随之从 30 行 SQL 变成一次 CAS 调用 + 一句判定。选名 `CompareAndInsert` 而非 `Publish`：`Publish` 带业务语义，`CompareAndInsert` 准确表达这是持久化原语。

**`memory_jobs` 的写入改为具名操作**：三处单语句更新（completed/running/字段更新）用 `store.UpdateMemoryJob(ctx, storage.MemoryJobUpdate{...})`——**按评审建议用"一个更新方法 + 更新结构体"，而不是 `MarkRunning`/`MarkFailed`/`MarkCompleted` 一族**，避免 API 长成一串 Mark*。两处带状态前置条件的（"仅当未完成时标记失败"、"仅当已失败时重新排队"）用**具名条件写** `FailMemoryJobIfOpen`/`RequeueMemoryJobIfFailed`——`WHERE status IN (...)` 是**存储层的前置条件**，不该泄漏成业务侧的 SQL。单语句本就原子，因此这几个方法挂在 `WorldStore` 上、不额外包事务。

**migration debt 继续下降**：`Database()` 生产用法 **42 → 33**（测试 104 → 103），守卫基线同步更新。

**本单元有意未做**（下一步）：把 `MetaGetTx`/`MetaSetTx` 的**30 余处调用点**与承载它们的**7 个函数签名**（`initializeWorld`/`commitTurn`/`cloneWorld`/`updatePlayerProfile`/`promoteBystander`/`updateNarrativeSettings` 等）一次性改成 `InTx` + `WorldTx` 形参。原因：这些函数的 `tx` 参数与 11 处 `BeginTx`/`commit`/`rollback` 结构必须**同时**改造，中间态无法编译；而它们的调用方共 50 余处。这一步值得单独一个工作单元，而不是塞在本单元尾部。已尝试过一次批量改写并**回退**，就是为了守住"每一步都可编译"。

18. **不做无法编译的中间态批量改写。** 我用 `tools/txto` 一次改掉 30 余处 `MetaGetTx`/`MetaSetTx` 调用点，结果这些调用点所在的 **7 个函数签名不匹配**，而修正签名又要求同时改造 11 处 `BeginTx`/`commit`/`rollback` 结构与 50 余处调用方——**中间态根本不能编译**，也就无法验证。教训：**先确认"这一步的中间态能否编译"再动手**；不能的话，就把它拆成"新增能力（本轮提交）"与"切换调用方（下轮提交）"两步，而不是硬塞在一起。已完成的 `WorldTx`/`InTx`/CAS/具名写是本轮的可交付部分，切换留给下一轮。

### memory 服务层 M3：六个自开事务的函数切到 `InTx`：2026-09-29

**先清点再动手。** 新建 `tools/txcensus` 按**函数体**（不是文件）统计：谁自开事务、谁收 `*sql.Tx`、各自调了几次 `MetaGetTx`/`MetaSetTx` 与裸 SQL。实测 **16 个函数自开事务**，其中 **7 个在用 `MetaTx`**。文件级搜索会误报（一个文件里有一处事务，文件里每个函数都像拥有事务），**必须按函数体判定**。

本单元转换其中 6 个（`Correct`、`UpdatePlayerProfile`、`SubmitRun`、`UpdateNarrativeSettings`、`cloneWorld`、`InitializeWorld`、`commitTurn`），全部改为 `store.InTx(ctx, func(tx *storage.WorldTx) error { … })`，体内调用换成具名操作。

**顺带具名化的裸 SQL**（22 处）：

| 新增具名操作 | 原裸 SQL |
| --- | --- |
| `WorldTx.DeleteMeta` | `DELETE FROM meta WHERE key=…` |
| `WorldTx.RunStatus` | 查 `runs` 的 `status` 与 `cancel_requested`（两次查询合并为一次） |
| `WorldTx.MaxRunInputSequence` / `CountCompletedRunsWithInput` | `runs` 的两个前置条件查询 |
| `WorldTx.InsertRun` | 插入 `runs` |
| `WorldTx.InsertEvent` / `InsertEventDependency` | 插入 `events` 与 `event_dependencies` |
| `WorldTx.InsertPerceptionIfAbsent` / `InsertMemoryIfAbsent` | `INSERT OR IGNORE` 两张投影表 |
| `WorldTx.InsertMessage` | 插入 `messages` |
| `WorldTx.InsertCharacter` | 插入 `characters` |
| `WorldTx.ClearScenePresence` / `SetScenePresence` | 清空/设置 `characters.in_scene` |
| `WorldTx.CompleteRun` | 把 `runs` 标为 completed，**前置条件（running 且未请求取消）留在这里** |
| `WorldTx.MemoryProjectionCandidates` | `indexMemorySources` 的四表 UNION 候选查询 |

**两处判定改为返回"是否可行"而非错误**：`SetScenePresence` 返回 `(bool, error)`、`CompleteRun` 返回 `(bool, error)`——**"角色不存在""运行已不可完成"是存储的前置条件，由调用方决定这算哪种失败**（分别映射为 `ErrGenerationFailed` 与 `ErrWorldBusy`）。

`SubmitRun` 与 `commitTurn` 的事务体较大，采取**把事务体内聚到函数内部**的方式（`submitRunTx` 辅助函数；`commitTurn` 用闭包 + `InTx`），而不是内联重排——**避免 140 行缩进变化掩盖真正的改动**。

**新增 `tools/txnwrap`**：把一个 `BeginTx`/`Commit` 骨架改写成 `InTx` 闭包，并**按嵌套深度**决定哪些 `return 0, x` 要丢掉外层值（闭包自己的返回）而哪些要保留（内联函数字面量的返回）。工具的判据错误我改了三次，最终靠 `-debug` 打印深度才发现真实形状是"闭包体内 `if err != nil {` 之后的 return 在深度 2"。

**migration debt**：`Database()` 生产用法 **33 → 24**，`MetaGetTx`/`MetaSetTx` 从 26 处降到 **8 处**（全在 `promotion.go`）。

**本单元有意未做**：`promotion.go` 的 `PromoteCharacter`（约 140 行事务，体内有游标循环、JSON 解析与多个 for，且返回值 `entityID`/`definitionID` 在事务内产生）。它是最后一个复杂点，且**提升路人这一能力在当前交付范围之外**（见产品说明），因此单独一个单元处理更合适。另有 6 个自开事务但不用 `MetaTx` 的函数（`createWorldFromPack`、`completePublish`、`ReadUsage`、`DeleteWorld`、`SaveAs`、`performCopyLocked`）——前三个操作世界库或应用库的表结构，后三个只动 `app.db`，可后置。

**工程教训（第十九条）**

19. **统计"哪些函数自开事务"必须按函数体，不能按文件。** 我第一版 `tools/txcensus` 用文件内容判断，把 `run.go` 里每个函数都标成"自开事务"，因为它文件里有一处 `BeginTx`。改成按 `fnDecl.Body` 判定后才得到真实数字（16 个）。**批量改造前先写出能给出准确清单的工具**，因为清单错了，工作量的估计和改造范围就都错了。
