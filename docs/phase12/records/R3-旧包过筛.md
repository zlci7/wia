# R3 旧包过筛：`context` 与 `memory`

状态：第 3–9 节保留开工前的只读筛查证据；逐项裁定与当前实施状态以第 10 节为准。旧 `context`（114 个测试）与旧 `memory`（167 个测试）在 D1 删除整簇旧 Runtime 前保持原样。

## 1. 结论摘要

1. **两个旧包的外部消费者全部是旧运行时。** 实测：旧 `memory` 被 `backend/internal/agent`、`context`、`gateway`、`bootstrap`、`backend/cmd/wia` 引用；旧 `context` 只被 `backend/internal/agent` 与 `backend/cmd/wia` 引用。**新叙事链路 `storyapp` 对两者零引用**，`storyapi` 亦然（与架构方案第 2 节一致）。
2. **旧包大部分导出符号根本没有外部消费者**：旧 `memory` 导出 293 个声明，只有 87 个被其它包引用；旧 `context` 导出 176 个，只有 25 个被引用。剩下的（含旧 `context` 的整个预算引擎 `Build`/`ContextProjection`/`BudgetConfig`/`Renderer`）**没有外部使用者**。
3. **因此"迁移算法"不是把旧代码搬过去，而是逐项回答"WIA 是否需要这个行为"。** 筛查结果是**需要的有 10 项，其中 5 项优先级最高**（第 3 节）；其余属于旧运行时概念，可随包删除（第 5 节）。
4. **最严重的一项不是算法缺失，是无限增长。** 新实现**没有任何删除路径**（`storyapp` 对 `memory_sources`/`memory_digests`/`events`/`perceptions`/`memories`/`messages` 无 `DELETE`），旧实现的保留与淘汰策略在新实现没有等价物。这是数据正确性问题，不只是功能缺失。
5. **`tokenestimate` 不是待迁移项。** 它已被新 `storyapp`（`context_composer.go`、`memory_context.go`）与旧包同时引用，R0 保留表已把它标为"迁移"，无需重写。

## 3. 删除旧包前必须先迁移（按优先级）

### 3.1 保留与淘汰策略

- **旧行为**：`enforceRetention` 按 `MaxRecordsPerEntity=100`、排序 `created_at DESC, memory_id DESC` 淘汰；`PruneHistory` 在证明或预算不足时**一条都不删**。
- **新实现**：`grep 'DELETE FROM (memory_sources|memory_digests|events|perceptions|memories|messages)'` 无匹配。
- **后果**：记忆来源、摘要、事件、感知、消息表无界增长。长期存档会持续变大，且没有任何回收机制。
- **落点**：`storyapp/memory_jobs.go` + `memory_stream.go`。
- **判定**：**必须先迁移或明确决定"本轮接受无界增长"。** 后者需要写进阶段方案，不能默认。

### 3.2 摘要覆盖范围的可验证性

- **旧行为**：`summaryCoverageFingerprint` / `sealSummaryCoverage` / `canonicalSummarySources` / `readSummaryCoverage`——Manifest + sha256 + 逐条身份 + 时间序列 `DeepEqual`，摘要必须能证明它覆盖了哪些来源。
- **新实现**：`memory_context.go:publishDigest` 只校验 `context_epoch` 相等、`MAX(revision)` 等于前一版、`MAX(seq)` 等于 `d.Head` 且 `head >= d.Through`；`d.Sources` 以 JSON 列写入、`readDigest` 原样读回，**不重算不比对**。
- **判定**：覆盖范围不可验证。摘要是"角色记得什么"的权威来源，一旦某次写入把 `Sources` 写歪，没有任何机制发现。**需迁移可验证性，至少要在读回时重算并比对。**

### 3.3 检索查询的上限与排序确定性

- **旧行为**：`HistoryQueryTerms(text, maxChars, maxTerms)` 有字符上限与词数上限；检索有分页/offset 与扫描、字节、超时预算；排序破平键为 `score, sequence, field_path`。
- **新实现**：`memory_context.go:searchMemory` 有切分与排序（`score`，同分按 `Seq` 降序，`SliceStable`），但**没有字符上限、没有词数上限、没有分页、没有扫描/字节/超时预算**。查询长度只靠提示词约束（`run.go:1177` 的 `len([]rune(decision.RecallQuery)) > 256` 判定整轮失败）——**这是模型守规矩才成立的约束，不是代码约束**，与 AGENTS.md 第 6 节"需要强制执行的规则必须进入代码校验"冲突。
- **判定**：**必须补代码级查询上限与预算。**

### 3.4 同源不同内容必须报冲突

- **旧行为**：`ErrHistoryConflict` / 内容指纹，同一来源写入不同内容时明确报错。
- **新实现**：`memory_stream.go:indexMemorySources` 用 `INSERT OR IGNORE`（`UNIQUE(scope, source_id)`）**静默跳过**，先写者胜。
- **判定**：修正或事实变更后重建记忆时，旧内容会静默保留。**需迁移冲突检测。**

### 3.5 "未来记忆不可见"

- **旧行为**：`GameTimeSnapshot` / `HistoryVisibility` / `isFutureMemory` / `sameGameDay` / `gameTimeRelation`。
- **新实现**：`indexMemorySources` 只纳入 `runs.status='completed'`，`loadLongMemory` 截到 `memory_digests.source_head`。**功能相近但不等价**：同一次已完成运行内、时钟更晚的记录拦不住。
- **判定**：需要判定是否等价。新时钟是字符串（`plot.go:clockMinute`、`run.go:advanceClock` 的 `第 N 日 HH:MM`），旧实现有结构化的 `GameTimeSnapshot` 比较。**迁移前必须先决定新实现的时间模型是否需要"未来不可见"这条不变量。**

| 项 | 旧行为 | 新实现 | 判定 |

## 6. 需要显式判定的行为差异（不能写成"已等价覆盖"）

**检索去重与取前 N 条的顺序相反。**

- 旧实现由 `context/retrieval_projection_test.go:TestRetrievalFiltersDuplicatesBeforeLimitAndPreservesRankSelection` 保护：**先去重，再取前 N 条**。
- 新实现 `memory_context.go:withRecall`（第 514–548 行）：先 `searchMemory(m.Archive, query, 5)` 取前 5 条，**再**跳过 `alreadySupplied` 与已在 `RecallSources` 中的命中。

**实测后果**：当命中里有若干条已提供过时，本轮实际可用的检索结果会少于 5 条。这是"因去重而少给结果"。

**判定要求**：这可能是可接受的行为变化（宁可少给也不重复），但必须在 R0 保留表里显式写下判定与理由，**不能当作"已有等价覆盖"处理**。若判定为缺陷，修法是把去重移到限额之前。

## 7. 未能确认（不得据此下结论）

以下三项没有确认，任何一步都不得以"大概有"为前提开工：

1. 新实现是否有等价于"迁移数据 + schema 版本同事务发布 + 导入计数一致"的机制（新世界库无版本字段，见 3.6）。
2. `storyapp` 的哪些 JSON 载荷真可能出现 >2^53 的整数（见 3.6）。
3. `storyapp` 是否已有代码级的检索查询上限守卫（目前只见到提示词层面的 256 字约束，见 3.3）。

**已由本次复核排除的一项**：旧 `memory` 的 SQLite 连接配置（WAL、`synchronous=FULL`、`foreign_keys`、忙等）在新实现里有等价物——`store.go:160` 的 `sqliteDSN` 声明 `_journal_mode=wal`、`_synchronous=full`、`_busy_timeout=5000`、`_txlock=immediate`，`openAppDB` 与 `openWorldDB` 另各执行一次 `PRAGMA foreign_keys/synchronous/journal_mode`。**仍未确认的只有一处**：旧实现会读回 `PRAGMA busy_timeout` 校验实际生效值、并支持临时改忙等，新实现只声明不回读，无法证明配置真的生效。

## 9. 对 R3 执行顺序的影响

本页结论不改变[抽取顺序](R3-耦合测量与抽取顺序.md)的模块次序，但给第 5 步（`memory`）增加三个硬性前置：

1. 抽取 `memory` 的同时必须落地**保留策略**与**摘要覆盖可验证性**，否则是将一个不可验证且无限增长的记忆链换到新包里。
2. **检索查询的代码级上限与预算**必须在 `memory` 抽出时进入代码，不能继续依赖提示词。
3. 旧包的**删除动作**（R5）在 3.1–3.6 项逐项有结论之前不执行；旧包测试在此期间保持原样。

## 10. 逐项裁定（2026-09-29，用户评审）

第 3 节与第 6 节的逐项结论。**未实现的项必须写明理由与到期条件，不能默认。**

| 项 | 裁定 | 理由与到期条件 |
| --- | --- | --- |
| 3.1 保留与淘汰 | **本轮明确后置** | 旧实现是 `MaxRecordsPerEntity=100` 的机械删旧；WIA 的记忆记录同时承担纠正来源、剧情证据与后续重摘要的输入，照搬阈值会破坏这些语义。**当前开发版接受世界历史表持续增长**——这是显式拒绝把旧 Runtime 的 retention 模型误植进新 WIA，不是遗漏。Retention / Archive / Compaction 作为重构后的产品持久化能力单独设计，**必须在长期连续世界达到"可长期运行"标准之前解决**。 |
| 3.2 摘要覆盖可验证 | **已实现**（C1） | 读回 digest 后按 `scope` + `through_seq` 重建实际连续覆盖并规范化 ID，与 `digest.Sources` 比对；不一致映射为 storage unavailable。正常加载复用已读取的 archive，独立校验只查询 `scope`/`seq`/`source_id`，不重复加载来源正文。 |
| 3.3 检索查询上限与预算 | **已实现**（C2） | 查询在代码中限制为 256 字符、32 个词、最新 512 条候选、32 MiB 与 500 ms；候选搜索与完整因果组展开共用预算，超界组整组排除，受限状态进入上下文、报告与日志。存储层仍会加载完整 archive，随 3.1 的 Retention / Archive / Compaction 设计解决。 |
| 3.4 同源不同内容报冲突 | **已实现**（C3） | 不存在→插入；存在且内容一致→幂等；存在而内容不同→冲突。storage 返回三态事实，应用层把内容冲突映射为 storage unavailable。 |
| 3.5 未来记忆不可见 | **不迁移旧实现** | 旧行为建立在 `GameTimeSnapshot` 与历史时点读取之上；WIA 的模型是提交边界（`plan != fact`，计划本就不进入人物经历），当前不支持"从过去世界时间读取后来已提交的记录"。空间后台行为、离线推进或历史时间快照出现后重新评估。 |
| 第 6 节 去重与限额顺序 | **已实现**（C2） | ranking → 过滤 supplied/RecallSources 与重叠因果组 → 取最多 5 组；重复项不再占用结果名额。 |
