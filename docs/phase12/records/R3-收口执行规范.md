# R3 收口执行规范

本文件是 R3 模块拆分**剩余工作的唯一执行依据**。它规定了停止条件、剩余步骤、每步验收标准，以及**明确不做的事**。

> **本文件存在的原因**：重构进行到中段后，最大的风险不再是技术选型，而是**把重构本身当成项目目标**。因此这里先固定"什么时候算做完"，再列步骤——避免为架构纯度无限追加工作。

- 前序记录：[R3 耦合测量与抽取顺序](R3-耦合测量与抽取顺序.md)（测量、依赖图、已完成单元、工程教训 1–19）
- 旧包过筛：[R3 旧包过筛](R3-旧包过筛.md)
- 进度事实源：[开发状态](../开发状态.md)

## 1. 这次重构要解决的原始问题

不是"把代码设计得学术"，而是四个具体问题：

1. WIA 不再背着旧 Game Runtime；
2. 一眼能看出前端、后端、存储、剧本在哪里；
3. **能顺着一条主流程看懂"一轮故事怎么执行"**；
4. Agent / Context / Memory / Model / World / Plot / Content 各自只有一个清晰 owner，后续加地图、位置、NPC 状态、空间系统时不需要继续往一个巨大 `storyapp` 里塞东西。

**所有设计决策的唯一拷问**：

> **它有没有让"看懂 WIA"更容易？**

如果只是让依赖图更漂亮，却让一个新人要打开 15 个 package 才能理解一轮故事，就不做。

## 3. 明确不做（写进停止条件，违反即视为偏离）

1. **不把 `Database() = 0` 作为完成条件。** 当前生产用法 24 处，全部是各自模块的写事务；它们随所属模块迁移时自然下降。**不为清零而新建 repository abstraction。**
2. **不新增 package**，除非对下面这个问题回答"会明显降低理解力"：

   > 删掉这个 package，把代码放进最相关的现有包，会不会明显降低理解能力？

   如果答案是"不明显"，就不要建。**已知的高风险名字**：`correctionmodel`、`suggestionmodel`、`locationmodel`、`eventmodel`、`turnmodel`、`storyruntime`、`worldservice`、`memoryservice`、`memoryrepository`——**都不要建**。
3. **不为未来功能预设 storage 方法。** `WorldTx` 只提供当前真实存在的写操作；空间系统需要写位置状态时再加。
4. **不引入 interface 抽象**，除非已存在第二个实现。当前只有 SQLite 一个实现，`WorldTx` 是具体类型。
5. **不新增迁移工具**。第 0 步把工具收敛为一个模块后，后续步骤只在其中加子命令。
6. **做完第 4 步立即停止重构**，转入产品功能（地图、位置、角色状态栏、NPC 隐藏状态、成长、事件、掷骰、开放世界）。

## 4. 执行步骤

每步**独立可提交**，且必须满足全局验收（§5）。步骤之间不跳序。

### 第 0 步 · 工具收敛

**目标**：把 `tools/` 从 13 个独立 go.mod 收敛为 **1 个** `tools/refactor` 模块，用子命令区分。

**删除**（一次性且已完成，Git 历史即归档）：

| 工具 | 删除理由 |
| --- | --- |
| `coupling` | 耦合测量已完成，结论已写入记录 |
| `patch` | 一次性补丁，已被 `edit` 取代 |
| `fixup` | 一次性修字面量，已完成 |
| `txto` | 已被 `txnwrap` 的用途取代 |

**保留为子命令**（可复用）：`move`、`qualify`、`imports`、`importfix`、`api`、`callsite`、`dropfunc`、`txcensus`、`txnwrap`。

**验收**：`tools/refactor` 单个模块；`go vet ./tools/...` 通过；`tools/` 下只有一个 `go.mod`；README 或 `main.go` 用法说明列出子命令。

### 第 1 步 · `TurnSnapshot` 进 `turn`

**目标**：让"一轮回合的冻结输入"有 owner。

**搬迁**：

```text
worldSnapshot        → turn.Snapshot
SceneView            → turn.SceneView
sourceMetadata       → turn.SourceMetadata
memoryContext        → turn.MemoryContext
generatedEventState  → turn.GeneratedEventState
generatedEvent       → turn.GeneratedEvent
```

引用面共 160 处（`storyapp` 生产 118、测试 42），全部为小批。

**执行中的范围修正（已验证）**：原计划的 `loadWorldSnapshot → turn.LoadSnapshot` **本步不搬**，理由是它会成环——该加载器需要调用 `readPlot`/`readGeneratedEvents`，而这两个函数操作 `generatedEventState` 并经 `store` 读表；把它们一起搬等于把大半个 `storyapp` 搬过去。因此：

- 基础加载器留在 `storyapp`，更名为 `loadTurnSnapshot`（它构建的是 `turn.Snapshot`，但暂不能搬）；
- `context_sources.go` 里的包装器（基础快照 + 来源溯源）更名为 `loadTurnInput`；
- **它是第 2 步的一部分**：`turn.Service` 要读快照时，通过 `Host` 回调 `loadTurnInput`，或在第 2 步把它与阶段函数一起搬入 `turn`。

**验收**：`turn` 拥有快照词汇；`storyapp` 只使用不定义（已核对：无任何快照类型定义残留，含两处死类型已删除）；`turn` 的依赖守卫扩展为允许 `plot`/`story`/`memorymodel`/`storage`/`model`；行为零变化。

### 第 2 步 · `turn/service.go`——主流程搬进 turn（**最重要**）

**目标**：达成 S2。

**实现**：

```go
// turn/service.go
type Host interface {
    Logger() *log.Logger   // 或等价的日志接口
    LogStage(...)          // 阶段耗时记录
}

type Service struct{ host Host }

func (s *Service) Execute(ctx, store, run, generator) (Output, error) {
    // load → intent → characters → coordinate → resolveScene → narrate → record
}
```

**搬迁**：`executeTurn` 与 7 个阶段函数（`loadTurn`/`resolveIntentStage`/`runCharacterStages`/`coordinateStage`/`resolveSceneResult`/`narrateStage`/`notePlayerAction`/`recordPlayerExperience`，约 700 行）到 `turn/service.go` 及各 stage 文件。

**Host 的纪律（比"几个成员"更重要）**：

> **目标是 Turn 不依赖 App 的业务能力；Host 不得膨胀。具体剩余外部依赖以实际迁移的编译结果为准。**

已被证伪的乐观估计：曾以为外部依赖只有 `a.logger` 与 `a.logRunStage` 两个。**实际阶段内部还直接依赖** `prepareLongMemory`、`resolveTurnIntent`、`decideNPCs`、`coordinateTurn`、`advancePlot`、`advanceGeneratedEvents`、`narrateVisible` 等，它们又分散在 `memory_context.go`/`plot.go`/`generated_events.go`/`context_*`。因此：

1. **迁移中发现还需要 App 能力时，不要为了让它编译而不断扩 `Host`。**
2. **真正属于 Turn 的 helper 一起搬**；明显属于后续 Memory/Content 的，**不要硬吸进 Turn**。
3. **绝不接受最后得到一个十几方法的 `Host`**——那只是把 `storyapp.App` 换个接口继续藏在 Turn 后面，等于没拆。
4. 若某阶段确实需要外部能力（如 memory 维护、plot 推进），**先判断该能力是否该在这步归位**；不该归位的，本步先把该阶段留在 `storyapp`，只搬主流程骨架与已自洽的阶段。**允许分两次搬完 `executeTurn`。**

**第 2 步下半：接线完成，S2 达成（2026-09-29）**

阶段之间的交接改为**通过 `turn.Output`**，而不是通过返回值——这是关键改动：

- 新增 `Output.VisibleEvents`（`json:"-"`），承载"玩家可见事件"这一步交接；
- `resolveSceneResult` 改为把事件写入 `output.VisibleEvents`、**返回 error**；
- `narrateStage` 从 `output.VisibleEvents` 读取，不再接收参数。

理由写在代码注释里：**阶段边界正是这类值会丢失的地方**。之前 `Host` 的分段无法传递它，只能传 `nil`——那会让玩家可见投影静默变空。把交接放进产出累加器后，`Host` 的分段才成立，**且不需要加宽 Host**。

**管道按实现照实调整**：`AdvanceWorld` 从 `Host` 中删除（7 → **6** 个方法）。因为本应用是在场景结果里推进世界（`resolveSceneResult` 内调 `advancePlot` + `advanceGeneratedEvents`），把它列为独立阶段会让叙述在它渲染的事件存在之前运行。设成 no-op 就是让代码撒谎。**管道描述实现，实现不迁就管道的形状。**

**`LoadInput` 增加两个参数**（`run`、`generator`）：实测加载器还要做 `prepareLongMemory`（需要 generator），原签名不够。这正是"以编译结果为准"。

**接线**：`runWorker` 改调 `a.turnService().Execute(...)`；`turnHost` adapter（`storyapp/turn_adapter.go`）实现 `Host`，逐个调用原有私有阶段函数；死代码 `App.executeTurn` 删除。

**一次被测试抓住的遗漏**：我在 `TurnIntent` 上新增了 `Input` 字段（供 `recordPlayerExperience` 使用），但没人填它——`TestCoreTurnKeepsPrivatePerceptionAndCommitsAtomically` 立刻报"私密消息内容为空"。已在 `Execute` 中设 `intent.Input = run.Input`。**这是"接线时静默丢字段"的实例，与上一轮 `visibleEvents` 是同一类风险。**

**S2 判定（达成）**：

- `turn/service.go` 的 `Execute` 可通读一轮故事；
- **运行路径确实走它**（`runWorker` → `turnService().Execute`），不是并行存在的第二份实现；
- `App.executeTurn` 已删除。

**S2 的诚实边界**：`turn` 现在拥有**顺序**与阶段交接，但各阶段**实现**仍是 `storyapp` 的私有函数（经 Host 调用）。所以"打开一个文件读懂一轮故事"已成立——`service.go` 里有完整的 `load → intent → characters → coordinate → narrate → record` 与每步的注释；但各步的内部实现仍散在 `storyapp`，那是第 3 步（清空 `storyapp`）的工作。

### 第 3 步 · 清空 `storyapp`

**目标**：达成 S3。**这是本次重构剩余的最大单元**，已按子系统量清规模（`storyapp` 现有生产代码 **11670 行 / 44 文件**）：

| 子系统 | 文件 | 行数 | 归属 |
| --- | --- | --- | --- |
| content 侧（`content*.go`/`packs.go`/`pack_*.go`/`publish.go`） | 7 | **3021** | `content` |
| memory 侧（`memory_*.go`/`corrections.go`） | 6 | **1505** | `memory`（`memorymodel` 并入） |
| context 组装（`context_*.go`/`scene_context.go`） | 4 | **808** | `turn` 或独立的 `context` |
| 提示词构造（`settings.go`/`behavior.go`） | 2 | **258** | `turn` |
| JSON 生成与诊断（`json.go`/`generation_diagnostic.go`） | 2 | **138** | 取决于错误词汇归属，见下 |

**执行顺序（每一步都以"能否编译"为界，且必须能独立提交）**：

**3.1 · 解开 `contextGenerator` 对 `App` 的持有（前置，已勘明）**

`contextGenerator` 对 `App` **只有一处依赖**：`g.app.meteredText(...)`（`context_composer.go:242`）。把它改成一个小接口字段（只需要 `meteredText` 这一个能力），`contextGenerator` 就不再持有 `App`。**这是其余各项的前置**：只要组装器还持有 `App`，任何搬迁都会绕回 `storyapp`。

**3.2 · context 组装 → `turn`（或独立 `context`）**

已知障碍（实测，非推测）：材料构造器依赖**六个子系统**的成员——`behaviorPolicy`、提示词构造器（`narrativePerspectiveInstruction` 等）、`plotContext`、`eventOpportunityContract`、`withLongMemory`、`dialogueSections`、`sceneFor`、`formatBystanders`、`joinPerceptions`。因此顺序必须是：

```text
先将提示词构造（3.4）与 plot/event 上下文（属 turn）就位
再搬 composeIntent / composeCoordination / composeNarration / composeNPC
最后搬 ContextComposer（纯预算与装配，本来就自洽）
```

**不要**试图一次性搬 `context_material.go`——它一行都不自洽，且每个依赖都要先归位。

**3.3 · JSON 生成与诊断**

`generationJSONError` 实现 `Is(target error)` 并与 `ErrGenerationFailed` 比较，而 `ErrGenerationFailed` 是 `storyapi` 的公开发布错误。**先裁定该错误词汇的归属**：若坚持 `turn` 不依赖应用错误，则必须为生成失败引入 `turn` 自己的哨兵，并在 `storyapp` 做映射。这一步会触及公开错误语义，**需要单独确认**，不要顺手改。

**3.4 · 提示词构造 → `turn`**

`settings.go`/`behavior.go` 的指令构造器回答"怎么把设置与策略翻译给模型看"，按 `ARCHITECTURE` §6.8 属 `turn`。`DefaultBehaviorPolicies()` 内含 Prompt 文本，同理。`migrateWritingPreference()` 是旧字段兼容迁移，属 storage migration 或 application 兼容层。

**3.5 · memory 侧 → `memory`**

`memory_*.go`/`corrections.go` 归位，`memorymodel` **并入 `memory`**（临时路径到期）。注意 `readMemorySources` 仍缠着纠正语义，两者必须一起搬。

**3.6 · content 侧 → `content`**

`content*.go`/`packs.go`/`pack_*.go`/`publish.go` 归位；`loadedPack`/`StoryPack`/`PackNPC`/`PackIssue` 随之；`App` 的目录/封面 API 拆成 `content` 服务或留在 app 层。

**3.7 · `App` 拆解**

剩下的是生命周期、HTTP 接线与世界操作：拆成 `turn.Service` 的宿主、`content.Service` 与应用装配（`app`），`storyapp` 目录删除。

**验收（S3）**：`backend/internal/storyapp` 目录不存在。

### 第 4 步 · 删旧 Runtime（R5）

**目标**：达成 S4。

删除 `gateway`、`task`、`tool`、旧 `agent`、旧 `context`、旧 `memory`、`protocol`；把 `memorymodel` 并入 `memory`。

**验收（S4）**：`backend/internal/` 下每一条都属于 WIA；`go build ./...` 通过。

## 6. 工作方法（来自前序 19 条工程教训）

**必须遵守**：

1. **不要用 PowerShell 改 Go 源码。** 用 `edit`/`write`，或写 Go 程序。已因 PowerShell 破坏中文与跨行替换误伤踩坑两次。
2. **每一步都要能编译。** 中间态不能编译的批量改写不要做——要么拆成"新增能力"与"切换调用方"两步，要么先确认整体可编译。
3. **搬迁前先写清点工具。** 清单错了，工作量与范围就都错了（`txcensus` 第一版按文件统计，把 16 个函数报成 80 个）。
4. **搬运不手工抄写。** 长字面量与函数用工具逐字搬移；schema 等从 Git 原文提取并验证包含关系。
5. **批量操作要限定文件范围。** "删除旧副本"不能对整个目录按名字匹配（新旧同名时会误删新实现）。
6. **搬家后必须 `go build` + `go vet`。** AST 改名不做类型检查（变量名遮蔽包名、正则命中声明行都只有编译器能发现）。
7. **新代码不得落进第 4 步要删的旧包目录。** 两代实现可能同名（都是 `package memory`），编译与 `go doc` 都不报冲突。
8. **文档与实际状态一致。** 完成度不夸大；未验证的写"未支持"；已交付的不回填改写。

**判断归属的两个判据**：

```text
纯 ≠ 领域         纯函数按职责归属，不按"没有副作用"归属
领域名词 ≠ 领域决策  storage 可以有 Correction/MemoryJob 这类名词（表示"存了什么"），
                    但不能有 ApplyCorrection/RebuildMemory（表示"为什么写、何时写"）
```
